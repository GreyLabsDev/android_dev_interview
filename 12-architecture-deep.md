# 1. Главная мысль: архитектура — это ответ на вопрос «что меняется»

Провальный ответ на «расскажите про вашу архитектуру» звучит как перечисление слоёв: «у нас
Clean Architecture, presentation, domain, data, всё через UseCase». Это описание, а не решение.
Собеседующий не может понять, вы так спроектировали или так было до вас.

Сильный ответ строится вокруг того, **какие изменения архитектура делает дешёвыми**, и чем
за это заплачено. Например: «состояние экрана — одна immutable data class, потому что у нас
частые баги на комбинациях флагов; за это платим тем, что при частичных обновлениях копируем
объект целиком, и в списках это пришлось оптимизировать через стабильные ключи».

Полезно держать в голове три вопроса, на которые отвечает любое архитектурное решение:

1. **Где источник правды** для этих данных и кто имеет право их менять.
2. **Что происходит при пересоздании и при смерти процесса** — то есть что восстанавливается,
   а что перезапрашивается.
3. **Как это тестируется** — если ответа нет, решение недоделано.

Дальше в этом файле каждый раздел устроен так же: механика, выбор, цена.

# 2. MVVM, MVI и «MVVM с UDF»

## 2.1. Что означают эти слова на практике

Определения на интервью почти бесполезны, потому что все три термина размыты. Разница, которую
стоит проговаривать, лежит в трёх измерениях.

| Измерение | «Классический» MVVM | MVI |
| --- | --- | --- |
| Состояние | несколько независимых потоков (`LiveData`/`StateFlow` на каждое поле) | одно состояние, одна `data class` |
| Вход | публичные методы ViewModel: `onLikeClick()`, `onRefresh()` | одна точка: `fun onIntent(intent: Intent)` |
| Переход | произвольная мутация внутри метода | явная функция `(State, Intent) -> State` (редьюсер) |

**UDF (unidirectional data flow)** — не четвёртая архитектура, а свойство: данные текут вниз
(состояние в UI), события текут вверх (в state holder). Оно есть и в MVI, и в аккуратном MVVM.
Именно поэтому современный Android-код чаще всего описывают как «MVVM с UDF»: одна
`StateFlow<UiState>`, методы вместо sealed-интентов, никакого формального редьюсера.

## 2.2. Что реально даёт единый редьюсер

Ключевое преимущество MVI не в «чистоте», а в двух вещах:

- **Невозможность несогласованного состояния.** Если состояние — одна структура, а менять её
  можно только целиком, то комбинация «`isLoading = true` и при этом `error != null`» либо
  невозможна по типам, либо видна в одном месте.
- **Воспроизводимость.** Редьюсер — чистая функция, значит любой баг воспроизводится списком
  интентов. Это очень дёшево логировать и прикладывать к крэшу.

Цена тоже конкретная:

- Больше кода на каждое действие: sealed-класс интента, ветка в `when`, иногда отдельный эффект.
- Sealed-иерархия интентов растёт и становится «мусорной корзиной» на больших экранах.
- Асинхронность всё равно не помещается в `(State, Intent) -> State`, поэтому появляется
  третья сущность — эффекты (side effects), и вся «чистота» превращается в ещё один слой.

## 2.3. Как отвечать на «что выберете для большого Compose-приложения»

Хороший ответ содержит выбор, критерий и границу применимости. Например:

> По умолчанию — MVVM с UDF: одна `StateFlow<UiState>` и обычные методы вместо интентов. Причина
> в том, что 80 % экранов простые, и формальный редьюсер там даёт только boilerplate. Но там, где
> состояние действительно сложное — экран с фильтрами, мастер из нескольких шагов, редактор, —
> я перехожу на явный редьюсер, потому что там окупается воспроизводимость и невозможность
> несогласованных комбинаций. Единообразие всей кодовой базы я считаю менее ценным, чем
> соответствие сложности задачи.

Что делает этот ответ сильным: он не догматичный, у него есть критерий переключения, и в нём
названа отвергнутая альтернатива (единообразие). Дальше почти наверняка спросят follow-up
«где ваш выбор проигрывает» — и здесь честный ответ: разные экраны выглядят по-разному, новому
человеку в команде нужно объяснять, когда какой подход, и без code review это расползается.

# 3. Проектирование UI State

## 3.1. Одна data class или sealed-иерархия

Самый частый вопрос блока, потому что по ответу сразу видно, проектировал человек экраны или нет.

**Sealed-иерархия** (`Loading | Content | Error`) хороша, когда состояния действительно взаимно
исключающие и у них разный набор данных:

```kotlin
sealed interface ProfileUiState {
    data object Loading : ProfileUiState
    data class Content(val profile: Profile) : ProfileUiState
    data class Error(val message: String) : ProfileUiState
}
```

Она ломается на первом же реальном требовании: «показывай старые данные, пока грузятся новые»,
«ошибка обновления поверх контента», «pull-to-refresh при уже загруженном списке». В
`ProfileUiState.Error` данных нет, значит показать их невозможно, и начинается
`Error(previousData: Profile?)` — то есть иерархия разваливается.

**Одна data class** справляется с этим естественно:

```kotlin
data class ProfileUiState(
    val profile: Profile? = null,
    val isRefreshing: Boolean = false,
    val error: UiMessage? = null,
)
```

Но у неё своя болезнь — невозможные комбинации: `profile == null && isRefreshing == false &&
error == null` (что это за экран?) или `error != null && isRefreshing == true`.

## 3.2. Практичный компромисс, который стоит назвать

Комбинировать: **sealed-иерархия для взаимоисключающего «тела» экрана, плоские поля для того,
что накладывается сверху**.

```kotlin
data class ProfileUiState(
    val content: ContentState,
    val isRefreshing: Boolean = false,
    val message: UiMessage? = null,      // снекбар поверх любого content
) {
    sealed interface ContentState {
        data object Loading : ContentState           // первая загрузка, показывать скелетон
        data class Loaded(val profile: Profile) : ContentState
        data class Failed(val reason: FailureReason) : ContentState  // нечего показать вообще
    }
}
```

Здесь «загружаю новую страницу, но старые данные показываю» выражается честно:
`content = Loaded(old)` плюс `isRefreshing = true`. А «совсем ничего нет» — это `Failed`.
Именно эту формулировку и ждут в вопросе 67 банка.

## 3.3. Ещё три вещи, которые отличают продуманное состояние

**Строки не должны быть в состоянии.** `error = "Не удалось загрузить"` — это локализация в
ViewModel, невозможность протестировать и невозможность поменять текст дизайнеру. Правильно —
идентификатор сообщения, который UI превращает в строку:

```kotlin
sealed interface UiMessage {
    data object NetworkUnavailable : UiMessage
    data class ServerError(val code: Int) : UiMessage
}
```

**Состояние должно быть стабильным для Compose.** `List<T>` формально нестабилен, поэтому либо
`ImmutableList` из `kotlinx.collections.immutable`, либо `@Immutable` на модели. Детали —
в `07-compose-deep.md`, раздел про стабильность. И никогда `MutableList` внутри state: разбор
этой конкретной ошибки — в Compose-гайде.

**Состояние — это не «данные из репозитория как есть».** Если во ViewModel лежит
`StateFlow<List<UserDto>>`, вы просто протащили сеть в UI. Маппинг в UI-модель — это то место,
где решается, что показывать при `null`, как форматировать дату и что делать с полем, которого
в этой версии API нет.

## 3.4. Одноразовые события: официальная позиция и практика

Тема, где полезно знать, что **официальная рекомендация Google жёстче, чем то, что делают в
большинстве проектов**, — и умение это проговорить сразу выделяет.

Позиция Google: **не отправлять события из ViewModel в UI вообще**. Событие следует обработать
в самой ViewModel и выразить результат состоянием, а UI после показа сообщает, что потребил его:

```kotlin
data class UiState(val userMessage: UiMessage? = null)

fun onMessageShown() {
    _state.update { it.copy(userMessage = null) }
}
```

Аргументация: `Channel` не гарантирует, что событие будет обработано (коллектор может исчезнуть
в момент доставки), а `SharedFlow` может эмитить в пустоту, когда подписчиков нет. Оба не
являются наблюдаемыми держателями данных, а UI-слой рассчитан именно на них.

Навигацию Google относит к **логике UI**, а не к событиям из ViewModel: решение о переходе
принимает экран, а ViewModel в лучшем случае выставляет флаг «валидация прошла», на который
экран реагирует.

Практика при этом расходится: `Channel` для навигации и снекбаров остаётся распространённым
решением, потому что он проще и в большинстве случаев работает (таблица компромиссов —
в `07-compose-deep.md`, раздел 9.3). Сильный ответ на интервью выглядит так: назвать
официальную рекомендацию, объяснить её причину, назвать, что используете вы, и честно сказать,
какой у вашего варианта недостаток. Ответ «мы используем Channel», без осознания того, что
это противоречит рекомендации и почему, — слабее.

# 4. Repository и границы слоёв

## 4.1. Зачем нужен Repository, кроме «слой абстракции»

Ответ «чтобы можно было подменить источник данных» слабый: на практике источник данных меняют
раз в никогда. Реальные причины другие, и их три.

1. **Он владеет решением «откуда взять».** Именно репозиторий знает, что список читается из Room,
   а сеть — это фоновое обновление, а не источник для UI. Без него это решение расползается по
   ViewModel'ям, и каждый экран решает по-своему.
2. **Он владеет согласованностью.** Запись в БД, инвалидация кэша и постановка задачи в outbox
   должны происходить вместе. Если это делает ViewModel, то при добавлении второго экрана с той
   же операцией логика дублируется — и рано или поздно разъезжается.
3. **Он даёт границу для тестов.** ViewModel тестируется с фейковым репозиторием, а репозиторий —
   с реальной in-memory Room и `MockWebServer`. Это две разные по стоимости категории тестов,
   и граница между ними должна быть где-то проведена.

Признак того, что репозиторий бесполезен: он состоит из методов вида
`suspend fun getUser(id: String) = api.getUser(id)`. Такой слой действительно стоит удалить —
и это хороший честный ответ, если спросят «а бывает, что репозиторий не нужен».

## 4.2. Где проходит граница domain и data

Простое рабочее правило: **в domain нет ничего, что знает про хранение и транспорт**. Ни `Dto`,
ни `Entity`, ни `Response`, ни аннотаций `@Serializable`/`@Entity`. Модель domain описывает
понятия предметной области, а не форму данных на проводе.

Отсюда следует необходимость трёх наборов моделей — `Dto`, `Entity`, доменная модель — и
маппинга между ними. Это самая критикуемая часть подхода, и критика справедлива: на CRUD-экране
три одинаковых класса и два маппера выглядят абсурдно.

Честная позиция для интервью: разделять модели там, где формы **действительно расходятся**
(поле называется иначе, сервер отдаёт строку вместо даты, в БД нужен составной ключ), и не
плодить их там, где расхождения нет. Аргумент «а вдруг разойдутся потом» — плохой: когда
разойдутся, тогда и разделите, это механическое изменение.

## 4.3. Нужен ли слой UseCase

Вопрос 71 просит защитить обе позиции, поэтому важно уметь именно это, а не выбрать сторону.

**За:**

- Логика, которая нужна двум и более ViewModel, должна жить где-то одна. UseCase — очевидное место.
- Операция, которая координирует **несколько** репозиториев (например, «оформить заказ» — это
  корзина, профиль, оплата и аналитика), не принадлежит ни одному из них.
- Имя UseCase документирует бизнес-операцию. `ObserveCartTotalUseCase` читается лучше, чем
  разбросанный по ViewModel подсчёт.
- Тестировать чистую операцию проще, чем ViewModel с её состоянием и диспетчерами.

**Против:**

- В большинстве случаев UseCase оказывается однострочной делегацией в репозиторий — то есть
  чистый boilerplate плюс лишний файл и лишний биндинг в DI.
- Слой добавляет косвенность: чтобы понять, что делает экран, нужно открыть на один файл больше.
- Он часто вводится «по фреймворку», а не по потребности, и тогда его правила никто не соблюдает:
  UseCase начинают вызывать друг друга, и получается второй слой репозиториев.

**Формулировка, которая звучит зрело:** вводить UseCase не по умолчанию, а по триггеру — когда
операция нужна второму потребителю или когда она координирует больше одного источника. При этом
не запрещать ViewModel обращаться к репозиторию напрямую для тривиального чтения. Главное —
чтобы правило было записано и одинаково понималось командой, иначе слой деградирует в любом случае.

# 5. Модуляризация

## 5.1. По слоям или по фичам

Деление по слоям (`:ui`, `:domain`, `:data`) даёт три огромных модуля, которые пересобираются
почти на любое изменение. Оно не решает главную задачу модуляризации — сокращение объёма
пересборки — и почти не помогает с конфликтами в PR.

Деление **по фичам** (`:feature:cart`, `:feature:profile`) решает обе задачи, поэтому это
современный дефолт. Внутри фичи слои остаются, но уже как пакеты, а не как модули.

Практическая раскладка, которую можно нарисовать на доске:

```
:app                       — сборка, DI-граф, навигационный хост
:feature:cart:api          — только контракты: маршрут, публичные модели
:feature:cart:impl         — экраны, ViewModel, реализация
:core:ui                   — дизайн-система, темы, общие компоненты
:core:data                 — сеть, БД, общие репозитории
:core:common               — утилиты, диспетчеры, Result
:core:testing              — фейки, правила, тестовые утилиты
```

## 5.2. api/impl-разделение: что даёт и чем платите

**Даёт:** модуль-потребитель зависит только от `:api`, поэтому изменение внутренностей `:impl`
не вызывает его пересборку. На большом проекте это основной источник ускорения инкрементальной
сборки. Плюс это физически запрещает обращаться к внутренностям чужой фичи.

**Платите:** удвоением числа модулей, необходимостью связывать `:api` с `:impl` через DI
(обычно мультибиндингом в `:app`), и тем, что навигация между фичами становится косвенной.
На проекте из 30 модулей это оправдано, на проекте из 5 — почти наверняка нет.

Обязательно назовите цену конфигурации: сотни Gradle-модулей сами по себе замедляют
configuration phase, и в какой-то момент выигрыш от гранулярности съедается. Это реальный
эффект, и упоминание его показывает, что вы это видели, а не читали.

## 5.3. Стратегия распила монолита (вопрос 72)

Сценарий в банке: 600k строк, инкрементальная сборка 12 минут, конфликты в PR. Ответ должен
начинаться не с модулей, а с измерения.

**Шаг 0. Измерить и зафиксировать базу.** Build scan, `--profile`, Build Analyzer. Нужно понять,
что именно занимает 12 минут: configuration phase, KAPT/KSP, dex, или пересборка всего из-за
одного «божественного» модуля. Часто выясняется, что половина времени — это одна аннотационная
обработка, и её замена даёт больше, чем полгода модуляризации.

**Шаг 1. Определить метрики успеха заранее.** Иначе через три месяца невозможно доказать, что
стало лучше. Разумный набор: медиана и p90 инкрементальной сборки локально, время PR-пайплайна,
доля PR, задевающих больше N модулей, число конфликтов в неделю.

**Шаг 2. Вынести `:core`-слои первыми.** Дизайн-система, сеть, БД, общие утилиты — у них меньше
всего входящих зависимостей от фич, и они нужны всем остальным шагам.

**Шаг 3. Резать по вертикали, по одной фиче.** Выбирать надо не самую важную, а ту, где
пересечение с остальным кодом минимально, — первая фича должна доказать схему, а не героически
преодолеть её. И сразу закрепить границу инструментом, а не договорённостью (раздел 5.4).

**Шаг 4. Запретить рост монолита.** Правило «новый код — только в новых модулях» важнее скорости
распила: без него вы пилите с одного конца, а с другого дописывают.

Follow-up «что если через три месяца стало хуже» — важная часть вопроса. Хуже действительно
бывает: выросла configuration phase, граф стал широким, но плоским (все зависят от всех), а
`:core:common` превратился в помойку. Правильная реакция — не откатывать всё, а укрупнить
слишком мелкие модули и разрезать `:core:common` по смыслу. И это ещё один аргумент за шаг 1:
без метрик вы даже не узнаете, что стало хуже.

## 5.4. Как удерживать границы механически (вопрос 74)

Вопрос сформулирован жёстко: «механизмы принуждения, а не договорённости». Значит, ответ
«код-ревью» — неполный. Инструменты, от дешёвых к дорогим:

1. **Сам граф Gradle.** Если `:feature:cart` не объявляет зависимость на `:core:data:impl`,
   заимпортить оттуда физически невозможно. Это самый сильный механизм, и он бесплатный —
   поэтому модуляризация и есть главный инструмент контроля границ.
2. **`implementation` вместо `api`.** Зависимость не протекает транзитивно к потребителям.
   Массовое использование `api` — частая причина того, что «модули есть, а границ нет».
3. **Тесты архитектуры.** Позволяют написать проверку вида «ни один класс из пакета `ui` не
   импортирует `data`» и гонять её как обычный тест. Два инструмента, и разница между ними
   существенна: **ArchUnit** анализирует JVM-байткод (активно развивается, но не видит
   Kotlin-специфику вроде top-level функций и `internal`, и не покрывает не-JVM таргеты KMP);
   **Konsist** читает исходники Kotlin и потому понимает язык лучше — но релизов у него нет
   с конца 2024 года, так что закладываться на него в новом проекте рискованно. Стоит знать
   оба и честно сказать про состояние каждого.
4. **Свои Lint-правила.** Дороже в написании, но работают прямо в IDE — разработчик видит
   ошибку до коммита, что гораздо дешевле, чем красный CI.
5. **Convention plugins.** Правила подключения модулей централизованы, и «случайно» добавить
   не ту зависимость сложнее. Подробнее — в `13-di-build-deep.md`.

Сильный ответ ранжирует их по стоимости обратной связи: чем раньше разработчик узнаёт о нарушении,
тем дешевле. IDE → локальная сборка → CI → ревью, именно в таком порядке.

## 5.5. Дизайн-система как модуль

Отдельный модуль `:core:ui` с токенами (цвета, типографика, отступы), компонентами и темами.
Три вещи, которые стоит упомянуть, потому что они превращают «папку с кнопками» в систему:

- **Токены, а не значения.** В коде фичи не должно быть `Color(0xFF2196F3)` и `16.dp`; должно
  быть `AppTheme.colors.accent` и `AppTheme.spacing.medium`. Иначе редизайн — это правка тысячи мест.
- **Скриншот-тесты на сами компоненты.** Дизайн-система — единственное место, где скриншот-тесты
  окупаются почти всегда: компонентов немного, они меняются редко, а регрессия в них задевает
  всё приложение.
- **Запрет на прямое использование Material внутри фич.** Если фичи ходят в `androidx.material3`
  напрямую, вы не сможете ни сменить версию Material, ни отойти от него. Обёртка стоит дёшево,
  а свободу даёт большую.

## 5.6. Feature flags (вопрос 78)

Сценарий: 100 млн MAU, работа офлайн, постепенная раскатка, не блокирует старт. Каркас ответа:

- **Источник правды — сервер, но чтение — всегда локальное.** Значения кэшируются на диск
  (DataStore), приложение читает только кэш. Фетч — асинхронный, при старте и по расписанию,
  результат применяется к **следующему** запуску или через явный «мягкий» апдейт.
- **Никогда не блокировать старт.** Это прямо в условии, и это же главная ошибка. Если флаги
  нужны для первого экрана, у каждого флага обязано быть значение по умолчанию, вшитое в сборку.
- **Фиксация значения на сессию.** Флаг, меняющийся посреди сессии, ломает и UX, и аналитику,
  и воспроизводимость багов. Значения читаются один раз на старте в снапшот.
- **Раскатка на стороне сервера.** Клиент не должен вычислять «попал ли я в 5 %»: иначе вы не
  сможете ни изменить когорту, ни объяснить расхождение с аналитикой. Сервер отдаёт уже
  вычисленное значение для этого пользователя, клиент его только применяет.
- **Kill switch отдельно от экспериментов.** Аварийное выключение фичи должно доезжать быстро и
  не зависеть от расписания экспериментов — обычно это отдельный лёгкий эндпоинт или push.
- **Обязательная уборка.** Флаг без срока жизни навсегда остаётся в коде и превращается в
  комбинаторный взрыв непротестированных состояний. Практика — срок годности и напоминание.

Отдельно назовите проблему, о которой обычно забывают: **флаги умножают число конфигураций**.
Двадцать булевых флагов — это миллион теоретических комбинаций, из которых вы тестируете одну.
Отсюда правило: флаги должны быть независимыми, а зависимые — объединяться в одно перечисление.

# 6. Состояние и его время жизни

Тема, которая за последнее время заметно изменилась, и знание этого изменения хорошо выделяет.
Раньше уровней было два: `remember` и `rememberSaveable`. Сейчас их **четыре**, и разница между
ними — ровно то, о чём спрашивают в вопросе 69 про process death.

| Механизм | Переживает рекомпозицию | Переживает пересоздание Activity | Переживает смерть процесса |
| --- | --- | --- | --- |
| `remember` | да | нет | нет |
| `retain` | да | **да**, тот же экземпляр | нет |
| `rememberSaveable` | да | да, но восстановленная **копия** | да |
| `SavedStateHandle` (во ViewModel) | — | да | да |
| ViewModel целиком | — | да | нет |

Что здесь нового и почему это важно:

- **`retain`** появился как отдельный механизм в свежих версиях Compose. Он держит **тот же
  самый объект** через пересоздание Activity — то есть решает задачу, для которой раньше
  приходилось заводить ViewModel: сохранить нечто несериализуемое (плеер, соединение, большой
  вычисленный объект). Важное ограничение, которое надо назвать сразу: в `retain` **нельзя**
  класть `Context` и `View` — это прямая утечка, ровно как в ViewModel.
- **Разница между `retain` и `rememberSaveable`** — это разница между «тот же объект» и «равная
  копия». `rememberSaveable` сериализует значение в `Bundle` и восстанавливает новый экземпляр:
  для `Int` разницы нет, для объекта с идентичностью — принципиальная.
- **`rememberSaveable` упирается в лимит `Bundle`.** Это тот же транзакционный лимит Binder,
  что и у `onSaveInstanceState` (разбор — в `10-android-sdk-deep.md`, раздел 8.3). Класть туда
  список на тысячу элементов нельзя.

**Как отвечать на «что кладёте в `SavedStateHandle`, а что перезапрашиваете».** Правило: туда
идёт то, что **нельзя восстановить** и что **мало весит** — идентификаторы, введённый пользователем
текст, позиция скролла, выбранные фильтры. Всё, что можно перезапросить у сервера или прочитать
из базы, туда не кладётся: это данные, а не состояние экрана. Смерть процесса — не редкость,
а нормальный сценарий: система убивает фоновые приложения постоянно, и воспроизводить это надо
специально (как именно — в `10-android-sdk-deep.md`, раздел 3.2).

# 7. Навигация

## 7.1. Расстановка сил, которую нужно понимать

На середину 2026 года картина такая, и это первое, что стоит сказать:

- **Navigation 2 (Navigation Compose)** переведён в **режим поддержки**: критические
  исправления есть, новых возможностей не планируется. Это официальный статус, и он меняет
  тональность ответа «что выбрать для нового проекта».
- **Navigation 3** — стабилен и активно развивается: это то, куда идёт платформа. Основная
  идея — вы **владеете back stack'ом** сами.

При этом «всё срочно мигрировать» — неправильный вывод, и его не стоит делать. Nav2 работает,
на нём написано огромное количество кода, а миграция — это переписывание всего навигационного
слоя. Правильная формулировка: **новый проект — Nav3; существующий — по потребности**.

## 7.2. Type-safe маршруты в Nav2 (вопрос 60)

До версии 2.8 маршруты были строками (`"profile/{userId}"`), с ручной сборкой и разбором.
Отсюда весь класс ошибок: опечатка в имени аргумента, забытый параметр, неверный тип — всё
падало в рантайме.

Type-safe вариант использует `@Serializable`-классы как маршруты:

```kotlin
@Serializable
data class Profile(val userId: String, val showEditButton: Boolean = false)

// граф
composable<Profile> { backStackEntry ->
    val route: Profile = backStackEntry.toRoute()
    ProfileScreen(userId = route.userId)
}

// переход — обычный вызов конструктора, а не сборка строки
navController.navigate(Profile(userId = "42"))

// во ViewModel аргументы достаются из SavedStateHandle
class ProfileViewModel(handle: SavedStateHandle) : ViewModel() {
    private val args: Profile = handle.toRoute()
}
```

Как это работает изнутри: `kotlinx.serialization` даёт описание полей класса, а Navigation по
нему генерирует шаблон маршрута и правила разбора аргументов. Поэтому `@Serializable`
обязателен — без него компилятор не сгенерирует описание, и навигация не заработает.

Ограничения, которые стоит знать, потому что о них спрашивают:

- Из коробки поддерживаются примитивы, строки, их nullable-варианты, массивы и списки
  примитивов. **Любой свой тип требует собственного `NavType`**, который вы регистрируете при
  объявлении маршрута.
- Аргумент без значения по умолчанию обязателен: не передадите — упадёт в рантайме.
- Deep links объявляются отдельно и требуют **руками написанного `intent-filter`** в манифесте:
  автоматическая генерация из графа работала только со старыми XML-графами.

## 7.3. Что решает Navigation 3 (вопрос 62)

Фундаментальная проблема Nav2, которую стоит уметь сформулировать: **back stack спрятан внутри
`NavController`**. Вы им не владеете, а только просите его измениться. Отсюда:

- невозможно нормально выразить состояние, когда на экране **два места назначения сразу**
  (список и деталь на планшете) — модель «стек с одной вершиной» этого не предполагает;
- состояние навигации нельзя просто сохранить и восстановить как обычные данные;
- «источник правды» о том, где находится пользователь, живёт отдельно от остального состояния
  приложения, и синхронизировать их приходится вручную.

В Nav3 back stack — это **обычный список, которым владеете вы**:

```kotlin
@Serializable data object Home : NavKey
@Serializable data class Detail(val id: String) : NavKey

@Composable
fun App() {
    val backStack = rememberNavBackStack(Home)   // это просто список ключей

    NavDisplay(
        backStack = backStack,
        onBack = { backStack.removeLastOrNull() },
        entryProvider = entryProvider {
            entry<Home> { HomeScreen(onOpen = { backStack.add(Detail(it)) }) }
            entry<Detail> { key -> DetailScreen(id = key.id) }
        },
    )
}
```

Переход — это `backStack.add(...)`, возврат — `removeLastOrNull()`. Никакого скрытого состояния.
Из этого следуют главные выигрыши:

- **Мультипейн становится естественным.** Стратегия отображения решает, показать последний
  элемент стека или несколько рядом. Именно для этого в Nav3 есть механизм сцен: он смотрит на
  стек и на размер окна и решает, как разложить содержимое. Это то самое место, где Nav3
  выигрывает у Nav2 радикально.
- **Состояние навигации сохраняется как данные** — стек сериализуем, поэтому переживает смерть
  процесса штатно, а не через отдельный механизм.
- **ViewModel можно привязать к записи стека** (вопрос 63) — для этого запись оборачивается
  декоратором, который держит для неё `ViewModelStore`. Зачем: у ViewModel появляется ровно то
  время жизни, что и у экрана в стеке, — она создаётся при входе и очищается при снятии со
  стека, а не живёт до конца Activity. Порядок декораторов важен: тот, что отвечает за
  сохраняемое состояние, должен идти раньше того, что отвечает за ViewModel.

**Чего в Nav3 не хватает (follow-up к вопросу 62).** Отвечать надо аккуратно, потому что
ситуация меняется быстро:

- **Анимации есть** — переходы, в том числе для predictive back и shared element, поддержаны.
  Утверждение «в Nav3 нет анимаций» устарело.
- **Deep links** появились, но пока в предварительных версиях, а не в стабильной ветке. Это
  сегодня главный аргумент «подождать», если приложение живёт на внешних ссылках.
- **Экосистема меньше.** Меньше готовых рецептов, меньше ответов на форумах, часть библиотек
  ещё не имеет интеграции.

Честный итог, который хорошо звучит: «для нового проекта я бы взял Nav3, потому что Nav2 уже не
развивается; для существующего — мигрировал бы, когда появится конкретная причина, чаще всего
это мультипейн на планшетах».

## 7.4. Навигация в мультимодульном проекте (вопрос 61)

Самый важный вопрос блока, потому что это архитектура, а не API. Задача: `:feature:cart`
должен уметь открыть экран из `:feature:profile`, не зная о нём.

**Схема, которая считается образцовой** (и используется в официальном примере Google):

1. **У каждой фичи есть `:api`-модуль, в котором лежат только навигационные ключи** — маленькие
   `@Serializable`-классы, описывающие «куда», плюс, возможно, расширения для навигатора.
   Экранов и ViewModel там нет.
2. **`:impl`-модуль содержит реализацию** и регистрирует свои экраны.
3. **Правило зависимостей:** `:api` фичи не зависит ни от чего чужого; `:impl` может зависеть
   только от **чужих `:api`**. Тогда `:feature:cart:impl` видит ключ `ProfileKey`, но не видит
   ни одного класса из `:feature:profile:impl`.
4. **Сборка графа происходит в `:app` через мультибиндинг.** Каждая фича вносит в общий набор
   свою функцию-регистратор, а хост навигации собирает их все:

```kotlin
// общий тип, объявленный в :core:navigation
typealias EntryProviderInstaller = EntryProviderScope<NavKey>.() -> Unit

// в :feature:profile:impl — фича сама регистрирует свои экраны
@Module
@InstallIn(ActivityRetainedComponent::class)
object ProfileNavModule {
    @Provides
    @IntoSet
    fun provideEntries(navigator: Navigator): EntryProviderInstaller = {
        entry<ProfileKey> { key -> ProfileScreen(userId = key.userId) }
    }
}
```

`:app` получает `Set<EntryProviderInstaller>` и применяет все. Добавление новой фичи не требует
правок в `:app` — это и есть проверка качества схемы.

**Навигатор** — тонкая абстракция в `:core`, у которой есть метод «перейти по ключу». Фича
зависит от неё и от чужих ключей, но не от чужих экранов.

Что сказать про альтернативы, если спросят: раньше это решали через строковые маршруты
(`navigate("profile/$id")`) — фича не зависит от чужого кода, но и типобезопасности нет:
опечатка обнаруживается пользователем. Ключи в `:api` дают то же разделение, но с проверкой
компилятором.

## 7.5. Deep links и восстановление стека (вопрос 64)

Пользователь приходит по ссылке сразу на глубокий экран. Если просто открыть его, кнопка
«назад» закроет приложение — и это ощущается сломанным.

Что нужно сказать:

- **Стек надо построить синтетически.** Не «открыть экран», а «положить в стек путь до него»:
  главная → раздел → нужный экран. В Nav3 это буквально несколько `add` в список, что заметно
  проще, чем в Nav2, где для этого есть отдельный механизм построения.
- **Сколько уровней восстанавливать — продуктовое решение.** Полный путь не всегда правильный:
  иногда достаточно «назад» на главную. Важно, что решение осознанное.
- **Ссылка — недоверенный ввод.** Её параметры надо валидировать, а переходы по внешним
  адресам — проверять по allowlist (разбор — в `16-security-deep.md`, раздел 7).
- **Отличие deep link от App Link:** App Link верифицируется по домену (`assetlinks.json` на
  сайте), поэтому открывается сразу в приложении без диалога выбора. Обычный deep link такой
  гарантии не даёт и может быть перехвачен другим приложением, объявившим тот же фильтр.

## 7.6. Альтернативные библиотеки

Стоит знать, что они есть, и понимать, зачем:

- **Decompose** — навигация, не зависящая от Compose и от Android, с компонентной моделью и
  честным жизненным циклом. Основной выбор в KMP-проектах, где навигация должна быть общей.
- **Voyager**, **Circuit** и подобные — упрощают типовые задачи и дают свои модели экранов.
- **Самописный навигатор** — вариант, который в мультимодульных проектах встречается чаще, чем
  кажется, и после появления Nav3 стал заметно проще: back stack как список — это и есть
  большая часть самописного навигатора.

Вывод, который стоит произнести: с появлением Nav3 разрыв между «официальной» и «своей»
навигацией сократился, потому что официальный API стал устроен так же, как самописные решения,
— список, которым вы владеете.
