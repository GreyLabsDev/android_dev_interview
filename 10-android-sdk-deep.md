# 1. Модель приложения

## 1.1. Что такое приложение с точки зрения системы

Приложение — это не «программа с функцией main», а набор **компонентов**, объявленных в манифесте,
которые система запускает по своим правилам:

| Компонент | Что это | Точка входа |
| --- | --- | --- |
| Activity | экран | `Intent` от системы или другого приложения |
| Service | работа без UI | `startService`/`bindService` |
| BroadcastReceiver | реакция на событие | broadcast от системы или приложения |
| ContentProvider | структурированные данные для других приложений | `ContentResolver` |

Ключевое следствие, которое надо произнести на интервью: **любой компонент может быть создан
системой в новом процессе, в произвольном порядке, без вашей Activity**. Поэтому вся инициализация
приложения обязана быть идемпотентной, а компонент не имеет права рассчитывать, что кто-то другой
уже что-то проинициализировал.

## 1.2. Процесс и `Application`

Один процесс на приложение по умолчанию, форкается из Zygote. `Application.onCreate()` вызывается
один раз на процесс — и это самый дорогой участок холодного старта, потому что выполняется до первого кадра.

```kotlin
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        // ❌ здесь не должно быть: чтения с диска, сети, инициализации всех SDK подряд
        // ✅ только то, без чего не откроется первый экран
    }
}
```

Что должно уходить из `Application.onCreate()`: инициализация аналитики, тяжёлых SDK, прогрев кэшей —
через `androidx.startup` (`Initializer`) с ленивой инициализацией, либо по требованию из фичи.
Отдельная антипрактика — библиотеки, которые прячут инициализацию в собственный `ContentProvider`
(он создаётся до `Application.onCreate()` и потому невидимо удлиняет старт).

Многопроцессность (`android:process=":remote"`) даёт изоляцию (например, для `WebView` или тяжёлого SDK),
но каждый процесс — это свой `Application.onCreate()`, свой DI-граф и свои синглтоны.
Классический баг: инициализация выполняется дважды, а разработчик этого не ожидает.

## 1.3. Манифест как контракт

Что в нём принципиально:

- `<uses-permission>` — то, что вы просите. Отсутствие записи = тихий отказ или крэш.
- `android:exported` — обязателен явно для компонентов с intent-filter начиная с Android 12. Экспортированный компонент — это публичный API вашего приложения, к которому может обратиться любое приложение.
- `<queries>` — с Android 11 действует package visibility filtering: без объявления вы не «видите» другие приложения через `queryIntentActivities`/`getPackageInfo`. `QUERY_ALL_PACKAGES` ограничен политикой Play.
- `<uses-feature>` — влияет на доступность в Play.
- `<property>` — современный способ передавать платформе флаги совместимости.
- Manifest merger склеивает манифесты библиотек; `tools:node="remove"`, `tools:replace` — инструменты разрешения конфликтов. Хорошая практика senior — периодически смотреть итоговый merged manifest: там регулярно обнаруживаются разрешения, которых вы не просили.

# 2. Context

## 2.1. Виды и время жизни

| Context | Живёт | Для чего |
| --- | --- | --- |
| `Application` | всё время процесса | всё долгоживущее: DI, репозитории, БД, загрузчики изображений |
| `Activity` | до пересоздания/закрытия экрана | тема, диалоги, `startActivity`, инфляция вью |
| `Service` | пока живёт сервис | системные вызовы внутри сервиса |
| `ContextWrapper`/`ContextThemeWrapper` | обёртки | подмена темы и ресурсов |

Два вопроса, которые задают почти всегда:

- **Почему нельзя показать диалог с application context?** Обычному диалогу нужен window token, чтобы прикрепиться к окну, а токен есть у Activity. С application context вы получите `BadTokenException`. Формулировка «окно бывает только у Activity» при этом слишком сильная: окно поверх приложений (`TYPE_APPLICATION_OVERLAY` с разрешением `SYSTEM_ALERT_WINDOW`) создаётся и без Activity — так работают всплывающие плееры и оверлеи. Это другой класс окон, с другим UX и с отдельным разрешением, которое Play выдаёт неохотно.
- **Почему хранить Activity context в синглтоне — утечка?** Потому что синглтон живёт дольше экрана. Механика — в `09-jvm-memory-deep.md`, раздел 4.

В Compose внутри composable доступен `LocalContext.current` — как правило это activity context,
и его действует то же правило: не сохранять в долгоживущих объектах.

# 3. Activity

## 3.1. Жизненный цикл

`onCreate` → `onStart` → `onResume` → (работа) → `onPause` → `onStop` → `onDestroy`.

Что важно понимать точнее, чем «список методов»:

- `onPause` — экран **частично** перекрыт (диалог, входящий звонок). Ещё видим.
- `onStop` — полностью скрыт.
- Между `onStop` и `onDestroy` может быть `onSaveInstanceState` — состояние сохраняется до уничтожения.
- `onDestroy` может не быть вызван вообще, если процесс убит системой. Поэтому в `onDestroy` нельзя размещать критичную для данных логику.

## 3.2. Поворот экрана: что происходит по шагам

`onPause` → `onStop` → `onSaveInstanceState` → `onDestroy` → новый экземпляр →
`onCreate(savedInstanceState)` → `onStart` → `onRestoreInstanceState` → `onResume`.

`ViewModel` при этом **не** пересоздаётся: `onCleared()` не вызывается, тот же экземпляр
подключается к новой Activity через `ViewModelStore`. Удерживает его не «система сама по себе»,
а `ComponentActivity` — она отдаёт `ViewModelStore` в `onRetainNonConfigurationInstance()`, и
`ActivityThread` передаёт этот объект в новый экземпляр Activity. Знать этот механизм полезно, потому
что из него сразу следует граница: при **смерти процесса** передавать некому, поэтому ViewModel
не выживает, и нужен `SavedStateHandle`. Это и есть причина существования ViewModel — её стоит
формулировать именно так.

`android:configChanges` позволяет отказаться от пересоздания, но тогда вы обязаны сами обработать
смену конфигурации (ресурсы, размеры, локаль). Легитимно для OpenGL/видео, в остальных случаях — способ спрятать баг.

## 3.3. Configuration change против process death

| | Configuration change | Process death |
| --- | --- | --- |
| Что умирает | Activity и её View | весь процесс: Activity, ViewModel, синглтоны, кэши в памяти |
| Что выживает | ViewModel, `ViewModelStore` | только `SavedStateHandle`/`Bundle` и то, что на диске |
| Как воспроизвести | поворот, смена темы, языка, размера шрифта, «Don't keep activities» | `adb shell am kill <pkg>` в фоне или кнопка терминирования процесса в Android Studio |

Про «Don't keep activities» важно не ошибиться, потому что это популярное заблуждение: опция
уничтожает только Activity, когда та уходит с экрана. Процесс, ViewModel-граф приложения, синглтоны
и кэши в памяти при этом **живы**. То есть так проверяют восстановление из `savedInstanceState`,
но не process death. Настоящий process death воспроизводится убийством процесса, пока приложение
в фоне.

Правило, за которое дают senior-балл: в `SavedStateHandle`/`onSaveInstanceState` кладут **ключи и позицию**
(id открытой сущности, текст в поле ввода, скролл), а не данные. Данные перезапрашивают
или читают из БД. `Bundle` идёт через Binder, поэтому большой объём даёт `TransactionTooLargeException`.

## 3.4. Задачи, back stack, launch modes

- `standard` — новый экземпляр всегда.
- `singleTop` — если Activity уже на вершине задачи, интент доставляется в `onNewIntent()` вместо создания нового экземпляра.
- `singleTask` — единственный экземпляр в задаче; при повторном запуске интент приходит в `onNewIntent()`, а всё, что выше него, снимается со стека. Если подходящей задачи нет, Activity становится **корнем новой задачи** — этот момент чаще всего и упускают.
- `singleInstance` — единственный экземпляр в отдельной задаче, в которой не может быть других Activity.
- `singleInstancePerTask` (API 31+) — единственный экземпляр в пределах каждой задачи, но задач может быть несколько. Нужен для многооконных сценариев, где один и тот же экран открыт в двух окнах.

Плюс флаги интента (`FLAG_ACTIVITY_NEW_TASK`, `CLEAR_TOP`, `SINGLE_TOP`) и `taskAffinity`.
Практический ориентир: `singleTop` для главного экрана и обработки deep link,
`singleTask` — для входной точки, к которой нужно возвращаться из уведомлений.

## 3.5. Activity Result API

`onActivityResult` устарел. Современный способ — контракты, которые сами переживают пересоздание:

```kotlin
private val pickImage = registerForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri -> uri?.let(::onImagePicked) }

private val requestPermission = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted -> if (granted) start() else showRationale() }
```

Почему это лучше: типизированный результат, регистрация до `STARTED`, корректное восстановление после
смерти процесса, отсутствие ручных request-кодов.

## 3.6. Splash screen

С Android 12 splash рисует система (`SplashScreen` API, `core-splashscreen` для совместимости).
Отдельная `SplashActivity` — антипаттерн: она добавляет к старту лишний экран и лишнюю инициализацию.
Правильный способ задержать первый кадр (если действительно нужно) — `setKeepOnScreenCondition`,
и держать его как можно короче, потому что это прямая надбавка к TTID.

# 4. Fragment

## 4.1. Два жизненных цикла

Фрагмент имеет собственный жизненный цикл и **отдельный** жизненный цикл своего `View`.
Фрагмент живёт дольше вью: при попадании в back stack `onDestroyView` вызывается, а сам фрагмент остаётся.

Отсюда два обязательных правила:

```kotlin
// 1. Наблюдать с viewLifecycleOwner, а не с this
viewModel.state.observe(viewLifecycleOwner) { render(it) }

// 2. Обнулять binding
private var _binding: FragmentBinding? = null
private val binding get() = _binding!!
override fun onDestroyView() { super.onDestroyView(); _binding = null }
```

Нарушение первого даёт множественные подписки и обновление уничтоженной вью;
нарушение второго — утечку всей иерархии вью (механика утечки и почему `onDestroyView` вызывается
без `onDestroy` — в `09-jvm-memory-deep.md`, раздел 4.2, пункт 5).

## 4.2. Обмен результатами

`Fragment Result API` (`setFragmentResult`/`setFragmentResultListener`) вместо интерфейсов и
прямых ссылок между фрагментами: результат переживает пересоздание и не создаёт связности.

## 4.3. Нужны ли фрагменты в 2026

Ответ, который ждут: в Compose-приложении фрагменты не нужны как единица экрана — достаточно одной
Activity и Compose-навигации. Фрагменты остаются в проектах с большим легаси и там, где нужен интероп.
Уверенное «фрагменты не нужны никогда» без учёта миграционного контекста звучит как отсутствие опыта с легаси.

# 5. Intent и взаимодействие компонентов

## 5.1. Explicit и implicit

- **Explicit** — указан конкретный класс: навигация внутри приложения.
- **Implicit** — описано действие, система ищет обработчик: открыть ссылку, поделиться, выбрать файл.

Для implicit обязательна проверка обработчика и осознанная работа с chooser:

```kotlin
val intent = Intent(Intent.ACTION_VIEW, uri)
runCatching { startActivity(intent) }
    .onFailure { /* ActivityNotFoundException: обработчика нет */ }
```

С Android 14 ужесточена доставка implicit-интентов внутренним (не экспортированным) компонентам —
для внутренней коммуникации используйте explicit-интенты.

## 5.2. PendingIntent

Токен, который вы отдаёте системе или другому приложению, чтобы оно выполнило интент **от вашего имени**
и с вашими правами. Отсюда требования безопасности:

```kotlin
PendingIntent.getActivity(
    context, requestCode, intent,
    PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT,
)
```

- С Android 12 мутабельность указывается **явно**, и «по умолчанию» больше не существует: при таргете API 31+ отсутствие `FLAG_IMMUTABLE` или `FLAG_MUTABLE` даёт `IllegalArgumentException` при создании. До Android 12 неявный дефолт был **mutable** — то есть небезопасный, ровно поэтому правило и ввели. Выбирайте `FLAG_IMMUTABLE` всегда, кроме случаев, когда получатель обязан дополнить интент (например, `Notification.Action` с прямым ответом или `RemoteInput`).
- `FLAG_UPDATE_CURRENT` против `FLAG_CANCEL_CURRENT` и роль `requestCode`: одинаковый `requestCode` с «равным» интентом переиспользует существующий PendingIntent — источник классического бага «уведомления открывают не тот экран».

## 5.3. Background Activity Launch

Тонкость senior-уровня, о которой мало кто знает:

- Если приложение таргетит **Android 14+**, оно при отправке PendingIntent больше **не** делится своими правами на запуск Activity из фона по умолчанию.
- Если приложение таргетит **Android 15+**, создатель PendingIntent тоже не делится этими правами по умолчанию.
- Чтобы запуск сработал, нужен явный opt-in: `ActivityOptions.setPendingIntentBackgroundActivityStartMode(...)`, рекомендуемый режим — `MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE` (добавлен в SDK 36).

Практический вывод: «запустить экран из фона» — не право приложения, а исключение. Правильный
пользовательский путь — уведомление, по которому пользователь сам переходит.

## 5.4. Deep links и App Links

- **Deep link** — intent-filter на схему/хост; система может показать диалог выбора приложения.
- **App Link** — верифицированная ссылка (`android:autoVerify="true"` плюс `assetlinks.json` на домене), открывается сразу в приложении без чужого выбора.

Что спрашивают дальше: как восстановить осмысленный back stack при входе в глубокий экран
(синтетический стек через `TaskStackBuilder` в Views, собственная реконструкция стека в Compose-навигации)
и как не потерять параметры при пересоздании (обработка в `onNewIntent` и сохранение в `SavedStateHandle`).

# 6. Фоновая работа

## 6.1. Матрица выбора

| Задача | Инструмент |
| --- | --- |
| Отложенная, гарантированная, с констрейнтами (синк, выгрузка) | `WorkManager` |
| Идёт сейчас и видима пользователю (навигация, плеер, запись, загрузка по кнопке) | Foreground Service с корректным типом |
| Точное время (будильник, напоминание) | `AlarmManager` с exact alarm и соответствующим разрешением |
| Пока пользователь на экране | корутина в `viewModelScope` |
| Долгоживущее соединение при активном приложении | bound service либо app-scoped scope |

Что нужно сказать про устаревшее: `IntentService` устарел в API 30, `JobIntentService` — вслед за ним.
Если кандидат пересказывает разницу между ними как актуальную, это красный флаг для интервьюера.

## 6.2. Foreground Service: жёсткие правила

- Тип обязателен с Android 14: `android:foregroundServiceType` плюс соответствующее разрешение. Тип определяет, что вам разрешено делать.
- `startForeground()` нужно вызвать быстро после старта, иначе ANR/исключение.
- Запуск FGS **из фона** запрещён, кроме перечня исключений.
- Android 15: `dataSync` и `mediaProcessing` ограничены **6 часами в сутки**, после чего система вызывает `Service.onTimeout()`; лимиты считаются по типам отдельно. `shortService` ограничен ещё жёстче.
- Android 15: `BOOT_COMPLETED`-ресивер не может запускать ряд типов FGS; исключение для `SYSTEM_ALERT_WINDOW` сузилось до наличия видимого оверлея.

Правильная реакция на эти ограничения — не искать обход, а переносить работу в `WorkManager`.
Именно этот ответ ждут.

## 6.3. WorkManager

```kotlin
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .build()
    )
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
    .build()

WorkManager.getInstance(context)
    .enqueueUniqueWork("sync", ExistingWorkPolicy.KEEP, request)
```

Что должно быть в ответе про гарантии:

- Очередь хранится в собственной БД WorkManager, поэтому работа переживает **смерть процесса и перезагрузку**.
- Работа **не** переживает force stop: приложение помечается остановленным, и фоновое исполнение блокируется, пока пользователь сам не откроет приложение.
- Планирование делегируется системному `JobScheduler` для констрейнтов и отложенности; немедленную работу без констрейнтов берёт внутренний `GreedyScheduler`.
- Исполнение всегда происходит **в вашем процессе**; система только будит приложение.
- Периодическая работа неточна по времени, пропущенные интервалы не копятся, а **минимальный интервал — 15 минут**. Просьба «синкать раз в минуту» через WorkManager невыполнима by design, и это правильный ответ вместо попытки обойти.
- Констрейнты событийные, а не опрашиваемые: система и так наблюдает за состоянием устройства.
- Долгая работа требует `setForeground()`, то есть фактически FGS с уведомлением. С Android 14 при этом обязателен объявленный `foregroundServiceType` — иначе получите исключение при попытке уйти в foreground.
- **Expedited work** (`setExpedited(OutOfQuotaPolicy...)`) — для «нужно сейчас, но это не UI»: система выполняет её вне обычной очереди, но в пределах квоты приложения, зависящей от App Standby bucket. Когда квота исчерпана, политика решает, деградировать до обычной работы или упасть. Это ответ на «а если надо срочно, но FGS не оправдан».
- Уникальные цепочки: `ExistingWorkPolicy.KEEP`/`REPLACE`/`APPEND_OR_REPLACE` — обязательный инструмент, чтобы не наплодить дублирующих синков.

## 6.4. AlarmManager и точное время

Exact alarms — привилегия, а не API по умолчанию: `SCHEDULE_EXACT_ALARM` для приложений,
таргетящих Android 13+, по умолчанию не выдан; `USE_EXACT_ALARM` доступен только приложениям,
у которых точное время — суть продукта (будильники, календари), и это отдельно контролируется политикой Play.
Для всего остального — `setAndAllowWhileIdle`, `WorkManager` или уведомления по расписанию сервера.

## 6.5. Doze, App Standby, ограничения фона

- **Doze**: устройство неподвижно и не заряжается — сеть и джобы группируются в окна обслуживания. Высокоприоритетные FCM-сообщения пробивают Doze, но их бюджет ограничен и злоупотребление наказывается.
- **App Standby buckets**: система классифицирует приложения по частоте использования (active/working set/frequent/rare/restricted), от бакета зависит доступ к джобам и алармам.
- **Battery optimization whitelist** существует, но требование пользователю отключить оптимизацию — плохой ответ и рискованно с точки зрения политики Play.

Формулировка senior-уровня: «мы не боремся с системными ограничениями, мы проектируем фичу так,
чтобы она не требовала их обхода».

# 7. BroadcastReceiver

## 7.1. Почему стал почти бесполезен

Неявные широковещательные сообщения нельзя принимать через манифест начиная с Android 8
(кроме короткого списка исключений). Отсюда практика: динамическая регистрация на время жизни экрана
либо отказ в пользу `WorkManager`/`Flow`.

С Android 14 при динамической регистрации для не системных broadcast обязателен явный флаг:

```kotlin
ContextCompat.registerReceiver(
    context, receiver, filter,
    ContextCompat.RECEIVER_NOT_EXPORTED,   // или RECEIVER_EXPORTED, осознанно
)
```

## 7.2. Правила внутри `onReceive`

Выполняется на главном потоке; ANR наступает примерно через 10 секунд для foreground-ресивера
и до 60 для background-ресивера, а после возврата из `onReceive` процесс может быть убит.
Значит: никакой длительной работы, никаких корутин «на потом» — только постановка задачи
в `WorkManager`.

`goAsync()` продлевает жизнь ресивера, но **не даёт нового бюджета**: тот же таймаут продолжает
идти, вы лишь получаете право уйти с главного потока и обязанность вызвать `finish()` на
`PendingResult`. Забыли `finish()` — получите ANR. Поэтому `goAsync()` уместен для работы на секунды
(записать флаг, дёрнуть один запрос), а всё, что длиннее, всё равно уходит в `WorkManager`.

Для внутриприложенческих событий broadcast — неправильный инструмент: используйте `Flow`/`SharedFlow`.

# 8. Главный поток, Binder и IPC

## 8.1. Как устроен главный поток

Главный поток — это бесконечный цикл обработки сообщений:

- `Looper` — цикл, привязанный к потоку (`Looper.prepare()` + `Looper.loop()`; для главного потока это делает система).
- `MessageQueue` — упорядоченная по времени очередь сообщений.
- `Handler` — способ положить в очередь `Message`/`Runnable`, привязанный к конкретному `Looper`.
- `Choreographer` — источник сигналов vsync: именно он планирует обработку ввода, анимаций и отрисовки на каждый кадр.

Отсюда прямое следствие для производительности: **всё**, что попадает в очередь главного потока,
выполняется между кадрами. Любая задача длиннее бюджета кадра (≈16 мс при 60 Гц, ≈8 мс при 120 Гц)
превращается в пропущенный кадр. Джанк — это не «медленный код» абстрактно, а конкретно занятый главный поток.

Что стоит знать про `Handler` дополнительно: он держит ссылку на внешний объект, если объявлен
нестатическим внутренним классом, а отложенное сообщение удерживает `Handler` — классическая утечка
Activity через `postDelayed` (механика — в `09-jvm-memory-deep.md`, раздел 4). Отменять — `removeCallbacks`.

Свежая деталь: приложения, таргетящие Android 17, получают lock-free реализацию `MessageQueue` —
быстрее и меньше пропущенных кадров, но ломается код, который рефлексией лазит в её приватные поля
(встречается в старых библиотеках профилирования и хаках вокруг главного потока).

## 8.2. ANR

ANR — это не «приложение зависло», а конкретные системные таймауты:

| Тип | Порог |
| --- | --- |
| Ввод не обработан | ≈5 с |
| `BroadcastReceiver.onReceive` не вернулся | ≈10 с (foreground) / до 60 с (background) |
| `Service` не стартовал (`onCreate`/`onStartCommand` не вернулись) | ≈20 с (foreground) / ≈200 с (background) |
| `ContentProvider` не ответил | ≈10 с |

Отдельно и **не про ANR**: если после `startForegroundService()` вы не вызвали `startForeground()`
примерно за **10 секунд**, приложение падает с `ForegroundServiceDidNotStartInTimeException`,
а не получает ANR. Это разные механизмы с разными таймаутами, и вопрос «сколько у вас времени
на `startForeground`» задают именно чтобы проверить, различаете ли вы их. Для типа `shortService`
правила ещё жёстче — там ограничено и общее время работы.

Типовые причины, которые ждут в ответе: блокирующий IO на главном потоке, `runBlocking`,
ожидание блокировки (deadlock), синхронный Binder-вызов к занятому системному сервису,
инициализация SDK в `Application.onCreate`, огромный `Bundle`.

Инструменты: Play Console Vitals (ANR rate — влияет на выдачу в Play),
`ActivityManager.getHistoricalProcessExitReasons()` с API 30 — он отдаёт причину смерти процесса
и ANR-трейс через `traceInputStream`, то есть работает в проде, в отличие от `/data/anr/traces.txt`,
Perfetto, а на этапе разработки — `StrictMode`:

```kotlin
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectDiskReads().detectDiskWrites().detectNetwork()
            .penaltyLog()
            .build()
    )
    StrictMode.setVmPolicy(
        StrictMode.VmPolicy.Builder()
            .detectLeakedClosableObjects()
            .detectActivityLeaks()
            .penaltyLog()
            .build()
    )
}
```

Хороший senior-ответ включает не только «нашёл и починил», но и профилактику: `StrictMode` в дебаге,
контроль ANR rate в Vitals как метрики релиза, запрет блокирующих вызовов на уровне ревью и линтов.

## 8.3. Binder

Основной механизм IPC в Android: обращения к системным сервисам (`ActivityManager`, `PackageManager`)
идут через него.

Что нужно знать на интервью:

- Транзакция копирует данные через ограниченный буфер (порядка 1 МБ **на процесс**, разделяемый всеми одновременными транзакциями). Отсюда `TransactionTooLargeException` — типично при передаче большого `Bundle` в `onSaveInstanceState` или больших списков в интенте.
- Вызовы синхронные и блокируют вызывающий поток: обращение к системным сервисам в цикле на главном потоке — реальная причина джанка.
- Есть асинхронный вариант: метод, помеченный в AIDL как **`oneway`**, возвращает управление сразу и не ждёт ответа (поэтому не может иметь возвращаемого значения и `out`-параметров). Это ответ на follow-up «а как не блокироваться на IPC».
- **Пул binder-потоков в процессе ограничен** (порядка 16 потоков). Входящие транзакции обслуживаются именно из него, поэтому если ваш сервис блокирует binder-потоки долгой работой, вызовы к нему начнут ждать в очереди, а при исчерпании пула — весь IPC в процесс встанет. Отсюда правило: в реализации AIDL-метода не делайте блокирующую работу, а сразу уходите в свой executor.
- `DeathRecipient` — способ узнать о смерти удалённого процесса.
- Каждый межпроцессный вызов — это сериализация: `Parcelable` предпочтительнее `Serializable`, потому что не использует рефлексию.
- Уровни абстракции над Binder, которые стоит уметь расположить: **AIDL** — полноценный интерфейс с многопоточным обслуживанием; **`Messenger`** — очередь сообщений в один `Handler`, то есть проще и последовательно; **`ContentProvider`** — тот же Binder, но с CRUD-семантикой и правами на URI.

## 8.4. ContentProvider и FileProvider

`ContentProvider` — способ отдать данные другим приложениям (контакты, медиа) и точка расширения
для системных механизмов. Внутри одного приложения он почти всегда лишний слой.

`FileProvider` — обязательный способ делиться файлами: вместо `file://` (запрещён) выдаётся `content://`
с временными правами:

```kotlin
val uri = FileProvider.getUriForFile(context, "$packageName.fileprovider", file)
val share = Intent(Intent.ACTION_SEND).apply {
    type = "image/jpeg"
    putExtra(Intent.EXTRA_STREAM, uri)
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}
```

# 9. Разрешения и приватность

## 9.1. Категории

| Категория | Как получают |
| --- | --- |
| Normal (интернет, вибро) | автоматически по объявлению в манифесте |
| Dangerous (камера, локация, контакты) | runtime-запрос у пользователя |
| Special (`SYSTEM_ALERT_WINDOW`, `MANAGE_EXTERNAL_STORAGE`, exact alarm, полноэкранные интенты) | отдельный системный экран настроек |
| Signature | только приложениям с той же подписью |

## 9.2. Правила работы с runtime-разрешениями

- Запрашивать **в момент нужды**, а не на старте, и объяснять зачем (rationale) до системного диалога.
- Всегда проектировать деградацию: пользователь может отказать навсегда, и приложение обязано остаться полезным.
- Разрешения **автоматически сбрасываются** у давно не используемых приложений — код обязан переспрашивать, а не считать разрешение вечным.
- Есть одноразовый доступ («только сейчас») и приблизительная локация — обрабатывайте оба варианта.
- Background location — отдельный запрос вторым шагом и отдельная проверка Play.

## 9.3. Тренд: доступ к выборке вместо доступа ко всему

Направление, которое стоит проговорить как принцип: платформа последовательно заменяет широкие
постоянные разрешения на **системные пикеры**, которые отдают только выбранное пользователем.

- **Photo Picker** вместо `READ_MEDIA_IMAGES` — доступ только к выбранным элементам, разрешение не нужно.
- Android 14: `READ_MEDIA_VISUAL_USER_SELECTED` — частичный доступ к медиа.
- Android 17: `ACCESS_LOCAL_NETWORK` обязателен для обращения к устройствам локальной сети (умный дом, каст); альтернатива — системный device picker, который позволяет обойтись без разрешения. Contact Picker — тот же подход для контактов.

Кандидат, который на вопрос «как получить доступ к галерее» отвечает «запрошу `READ_MEDIA_IMAGES`»,
демонстрирует знание 2022 года.

# 10. Хранилища и файлы

## 10.1. Что выбрать

| Инструмент | Когда |
| --- | --- |
| `DataStore` (Preferences/Proto) | настройки, флаги, мелкое состояние; асинхронный, транзакционный |
| Room | структурированные данные, запросы, реактивность через `Flow` |
| Файлы во внутреннем хранилище | кэш, медиа приложения, `cacheDir` для удаляемого |
| `MediaStore` | пользовательское медиа в общих коллекциях |
| SAF (`ACTION_OPEN_DOCUMENT`) | произвольные пользовательские файлы и папки |
| `SharedPreferences` | легаси; `commit()` синхронный и блокирует, `apply()` асинхронный |

`SharedPreferences` считается устаревшим подходом: нет транзакционности, нет реактивности,
первое чтение блокирует поток и загружает весь файл. Ответ «мы миграцию на DataStore сделали
и вот как жили с двумя источниками во время миграции» — хороший senior-сигнал.

## 10.2. Scoped storage

Приложение свободно работает со своим каталогом; к общим коллекциям обращается через `MediaStore`,
к произвольным файлам — через SAF. Широкое `MANAGE_EXTERNAL_STORAGE` требует обоснования перед Play
и почти никогда не проходит для обычного приложения.

Отдельно про `cacheDir`: система вправе его чистить, а код обязан выживать после этого.

# 11. Уведомления

Что должно быть в ответе:

- **Каналы** обязательны с Android 8: важность, звук и поведение задаёт пользователь, а не вы. Менять можно имя, описание и группу; **важность и звук после создания — нельзя**. И главная ловушка: удалить канал и создать заново с тем же id не помогает — система помнит прежние пользовательские настройки и восстанавливает их. Обходной путь — новый id канала, но тогда пользователь теряет свои настройки. Отсюда практический вывод: дизайн каналов надо продумать до первого релиза.
- **`POST_NOTIFICATIONS`** — runtime-разрешение с Android 13. Уведомления могут просто не показываться, и код обязан это учитывать.
- **Полноэкранные интенты** (`USE_FULL_SCREEN_INTENT`) с Android 14 доступны фактически только звонилкам и будильникам.
- **FGS-уведомление** нельзя убрать программно, но пользователь **с Android 13 может смахнуть его** — сервис при этом продолжает работать. Плюс появился FGS Task Manager («Активные приложения»), откуда пользователь может остановить ваш сервис принудительно. Несмахиваемыми остаются отдельные случаи: звонки, медиа, `mediaProjection`, а также уведомления на заблокированном экране. Ответ «пользователь не может его убрать» — устаревший, и на нём легко поймать.
- **Notification trampoline запрещён с Android 12**: уведомление не может вести в `BroadcastReceiver` или `Service`, который затем стартует Activity, — система такой запуск блокирует. `PendingIntent` должен вести в Activity напрямую.
- Уведомление, открывающее экран, — через `PendingIntent` с `FLAG_IMMUTABLE` и с корректной реконструкцией back stack.
- Android 17 добавляет более строгие проверки памяти для уведомлений с кастомными view.

# 12. Окна, конфигурации, адаптивность

## 12.1. Edge-to-edge и insets

Для приложений, таргетящих Android 16 (API 36), отключить edge-to-edge **невозможно**:
`windowOptOutEdgeToEdgeEnforcement` задеприкейчен и не работает. Значит, работа с инсетами обязательна.

```kotlin
// Views
enableEdgeToEdge()
ViewCompat.setOnApplyWindowInsetsListener(view) { v, insets ->
    val bars = insets.getInsets(WindowInsetsCompat.Type.systemBars())
    v.updatePadding(bottom = bars.bottom)
    insets
}

// Compose
Modifier.windowInsetsPadding(WindowInsets.safeDrawing)
```

Типовая проблема, которую ищут: кнопка под жестовой панелью остаётся видимой, но перестаёт нажиматься.
Проверять нужно все состояния: клавиатура (`ime`), вырезы (`displayCutout`), навигация жестами и кнопками.

## 12.2. Predictive back

Для приложений, таргетящих API 36, predictive back включён по умолчанию: `onBackPressed()`
не вызывается, `KeyEvent.KEYCODE_BACK` не доставляется. Миграция — на `OnBackPressedDispatcher`
(AndroidX) или `OnBackInvokedDispatcher` (платформа); временный отказ — `android:enableOnBackInvokedCallback="false"`.

```kotlin
// AndroidX, работает на всех версиях
val callback = object : OnBackPressedCallback(enabled = hasUnsavedChanges) {
    override fun handleOnBackPressed() = showDiscardDialog()
}
onBackPressedDispatcher.addCallback(this, callback)

// enabled вычисляется ОДИН раз при создании callback, поэтому дальше его надо обновлять:
viewModel.hasUnsavedChanges
    .onEach { callback.isEnabled = it }
    .launchIn(lifecycleScope)
```

Здесь легко написать нерабочий код: короткая форма `addCallback(this, enabled = hasUnsavedChanges) { … }`
выглядит опрятнее, но `enabled` в ней — обычное значение, посчитанное в момент регистрации.
Если пользователь начал вводить текст уже после этого, callback останется выключенным, и диалог
о несохранённых изменениях не появится. Управлять нужно через `callback.isEnabled`, и это ровно
тот вопрос, который задают следом: «а как ваш callback узнаёт, что состояние изменилось».

## 12.3. Ориентация и адаптивность: главное изменение последних версий

- **Android 16 (API 36)**: на экранах с `smallestWidth >= 600dp` система **игнорирует** `screenOrientation`, `resizeableActivity="false"`, `minAspectRatio`/`maxAspectRatio` и соответствующие рантайм-вызовы. Приложение занимает всё окно в любой ориентации. Исключения: игры (`android:appCategory="game"`), экраны меньше sw600dp, явный выбор пользователя. Временный отказ — свойство манифеста `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY`.
- **Android 17 (API 37)**: этот отказ больше не действует. Адаптивность становится обязательной.

Практический вывод для интервью: «заблокировать портрет» перестало быть архитектурным решением.
Нужны `WindowSizeClass`, адаптивные раскладки, сохранение состояния при изменении размера окна,
и тестирование в multi-window и desktop windowing.

## 12.4. Multi-window и Picture-in-Picture

Два механизма, про которые спрашивают именно в связке с адаптивностью, потому что оба ломают
привычное «мой экран один и он на переднем плане».

**Multi-window.** В режиме разделённого экрана видимыми и `RESUMED` могут быть **две Activity
одновременно** (multi-resume). Из этого следует практическое: нельзя считать, что `onResume`
означает «пользователь смотрит именно на меня». Для камеры, микрофона и плеера нужен колбэк
`onTopResumedActivityChanged()` — он говорит, кто получил «настоящий» фокус, и именно по нему
захватывают и отпускают эксклюзивные ресурсы.

**Picture-in-Picture.** Режим маленького окна поверх других приложений:

```kotlin
// современный способ: система сама переводит в PiP при уходе с экрана
setPictureInPictureParams(
    PictureInPictureParams.Builder()
        .setAutoEnterEnabled(true)          // Android 12+: без этого переход рваный
        .setAspectRatio(Rational(16, 9))
        .setSeamlessResizeEnabled(true)     // для видео, а не для обычного UI
        .build()
)
```

Что нужно знать: до Android 12 в PiP уходили вручную из `onUserLeaveHint()`, и переход выглядел
дёргано; `setAutoEnterEnabled(true)` решает это за вас. В PiP окно крошечное — Activity обязана
скрыть всё управление, для этого есть `onPictureInPictureModeChanged()`. Действия в окне
добавляются только как `RemoteAction` (не свои View), и их число ограничено
(`getMaxNumPictureInPictureActions()`). Требуется `android:supportsPictureInPicture="true"`,
и учтите, что PiP — это не пауза: Activity остаётся видимой, поэтому `onPause` не значит
«можно остановить плеер».

## 12.5. Ресурсы и конфигурации

Квалификаторы (`-night`, `-sw600dp`, `-ru`, `-land`, плотности), `Configuration`, тёмная тема,
масштаб шрифта, RTL. Отдельно — **per-app language**: пользователь выбирает язык конкретного
приложения (`AppCompatDelegate.setApplicationLocales` / `LocaleManager`), и приложение обязано это поддерживать.

Проверка на зрелость: тестируете ли вы на 200 % шрифте и в RTL. Большинство приложений там ломается.

# 13. Версии платформы и требования Play

## 13.1. Три числа

- `minSdk` — минимальная версия, на которую установится.
- `targetSdk` — версия, чьё **поведение** вы принимаете (behavior changes применяются по нему).
- `compileSdk` — против какого SDK компилируетесь; должен быть не ниже targetSdk.

Поднятие `targetSdk` не поднимает `minSdk`. Проверки версий в рантайме — через `Build.VERSION.SDK_INT`
и `@RequiresApi`, но в первую очередь через AndroidX-обёртки (`ContextCompat`, `WindowInsetsCompat`),
которые прячут ветвления.

## 13.2. Требования Google Play

- С **31 августа 2026** новые приложения и обновления обязаны таргетить **Android 16 (API 36)**; продление по заявке — до 1 ноября 2026. Для Wear OS и Automotive порог ниже (API 35), для TV и XR — API 34.
- Отдельное требование — **доступность**, и его часто путают с предыдущим. Существующее приложение должно таргетить минимум **API 35**, иначе перестаёт быть видимым новым пользователям на устройствах с ОС новее вашего таргета. Уже установившие приложение не затронуты: они могут его находить, переустанавливать и пользоваться. Пороги доступности для остальных форм-факторов свои: Wear OS — API 34, TV — API 33, XR — API 34, Automotive — API 32 (12L).
- С **1 ноября 2025** новые приложения и обновления, таргетящие Android 15+, обязаны поддерживать **16 КБ страницы памяти** на 64-битных устройствах. Чисто Kotlin/Java-приложения совместимы автоматически; проблема только у нативных библиотек, включая приходящие из SDK. Лечится так: AGP 8.5.1+ (выравнивает упаковку в бандле) плюс NDK r28+, который собирает `.so` с 16 КБ-выравниванием по умолчанию. На NDK r27 выравнивание надо включить руками (`APP_SUPPORT_FLEXIBLE_PAGE_SIZES := true` для ndk-build, `-DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON` для CMake), на более старых — линкерными флагами `-Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384`. Проверяется выравниванием LOAD-сегментов в ELF: должно быть `2**14`, а не `2**12`.
- Дальше цикл повторяется с шагом в год: порог сдвигается на предыдущую мажорную версию, то есть следующим ожидается API 37 к концу августа 2027. Полезный ответ на интервью — не дата, а вывод: поднятие `targetSdk` должно быть плановой ежегодной задачей в роадмапе, а не авралом в августе.

# 15. «Что не так с этим кодом»

## 15.1

```kotlin
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        Analytics.init(this); Ads.init(this); Maps.init(this)   // ❌
        prefs = getSharedPreferences("app", MODE_PRIVATE)       // ❌ блокирующее чтение
    }
}
```

Всё это выполняется до первого кадра. Инициализацию — лениво или через `androidx.startup`,
настройки — в `DataStore` и асинхронно.

## 15.2

```kotlin
override fun onSaveInstanceState(outState: Bundle) {
    outState.putParcelableArrayList("items", ArrayList(allItems))   // ❌
}
```

`Bundle` идёт через Binder, поэтому упирается в буфер транзакции (разбор — в разделе 8.3).
Сохраняйте ключи и позицию, данные перезапрашивайте.

## 15.3

```kotlin
val pi = PendingIntent.getActivity(context, 0, intent, 0)   // ❌
```

Не указана мутабельность — с Android 12 это исключение. Нужен `FLAG_IMMUTABLE`.
И `requestCode = 0` для всех уведомлений означает, что они могут переиспользовать один
PendingIntent. Механика тут тоньше, чем «одинаковый requestCode → коллизия»: равенство
PendingIntent определяется по `Intent.filterEquals`, то есть по action, data, type, component
и categories — **extras в сравнении не участвуют**. Поэтому два уведомления с одинаковым
requestCode и одинаковым `Intent(context, DetailActivity::class.java)`, различающиеся только
`putExtra("id", …)`, считаются одним и тем же: второе перезапишет первое (с `FLAG_UPDATE_CURRENT`)
или отдаст старые extras (без него). А если у интентов различается `data` — например, вы кладёте
id в `Uri` — коллизии не будет даже при одинаковом requestCode. Отсюда два рабочих решения:
уникальный requestCode на уведомление либо уникальный `data` в интенте.

## 15.4

```kotlin
class SyncReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        CoroutineScope(Dispatchers.IO).launch { repository.syncAll() }   // ❌
    }
}
```

После возврата из `onReceive` процесс может быть убит, корутина не завершится.
Правильно — поставить `WorkManager`-задачу.

## 15.5

```xml
<activity android:name=".MainActivity" android:screenOrientation="portrait" />   <!-- ❌ -->
```

При таргете API 36 на экранах ≥ sw600dp игнорируется, при таргете 37 отказаться уже нельзя.
Нужны адаптивные раскладки.

## 15.6

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(binding.root)      // контент под системными барами  // ❌
}
```

При таргете API 36 edge-to-edge принудительный: без обработки инсетов элементы уезжают под панели.

## 15.7

```kotlin
private val receiver = object : BroadcastReceiver() { /* ... */ }
// в onCreate:
registerReceiver(receiver, filter)   // ❌ при таргете 34+ нужен флаг exported
```

Нужен `ContextCompat.registerReceiver` с `RECEIVER_NOT_EXPORTED`. И симметричный `unregisterReceiver`.

## 15.8

```kotlin
// ❌ так не работает и так не надо
if (!powerManager.isIgnoringBatteryOptimizations(packageName)) {
    startActivity(Intent(Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS))
}
```

Здесь две проблемы. Техническая: этот интент требует ещё и разрешения
`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` в манифесте, и `data = Uri.parse("package:$packageName")`,
иначе диалога по вашему приложению не будет. Продуктовая, и она важнее: просить отключить
оптимизацию батареи как штатный сценарий — плохой UX и прямой риск по политике Play, которая
разрешает это лишь узкому классу приложений (будильники, трекеры активности и подобные).

Если запрос действительно оправдан, безопаснее вести пользователя в системный экран списком:
`Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` — он не требует разрешения. Но правильный
первый шаг — пересмотреть архитектуру фоновой работы: в большинстве случаев нужен WorkManager
с корректными constraints, а не исключение из Doze.
