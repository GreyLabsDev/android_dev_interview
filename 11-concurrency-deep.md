# 1. Три свойства, которые надо различать

Почти любой вопрос про многопоточность сводится к тому, какое из трёх свойств нарушено.

| Свойство | Вопрос | Чем обеспечивается |
| --- | --- | --- |
| **Visibility** | увидит ли другой поток мою запись | `volatile`, монитор, атомики, happens-before |
| **Atomicity** | может ли операция наблюдаться частично или потерять обновление | локи, CAS, атомики |
| **Ordering** | в каком порядке операции могут быть переупорядочены | барьеры памяти, `volatile`, монитор |

Ключевая ошибка на интервью — считать, что `@Volatile` решает всё. Он даёт **visibility и ordering
для одного поля**, но не делает `counter++` атомарным: это чтение, инкремент и запись, между которыми
может вклиниться другой поток.

## 1.1. Happens-before

Отношение, которое гарантирует: всё, что было сделано до действия A, видно после действия B.
Основные источники:

- освобождение монитора → последующий захват **того же** монитора;
- запись в `volatile` → последующее чтение **того же** поля;
- всё, что было до `Thread.start()` → всё внутри запущенного потока;
- всё в потоке → возврат из `join()`;
- запись в `final`/`val` поле в конструкторе → чтение через корректно опубликованную ссылку;
- контракты конкурентных коллекций: «положил в очередь» → «взял из очереди».

Если между двумя действиями нет happens-before, компилятор, JIT и процессор вправе их переупорядочить,
а поток вправе никогда не увидеть чужую запись. То, что «на моём устройстве работает», — не аргумент.

## 1.2. Почему это особенно больно на Android

x86 имеет достаточно сильную модель памяти и многие некорректные программы на нём случайно работают.
**ARM переупорядочивает агрессивнее.** Практический вывод, который стоит произнести вслух:
гонка, не воспроизводящаяся на эмуляторе x86, спокойно воспроизводится на реальном телефоне —
особенно на big.LITTLE, где потоки разъезжаются по ядрам с разными характеристиками.

## 1.3. Data race против race condition

- **Data race** — конкурентный доступ к одной ячейке памяти, хотя бы один доступ на запись, без синхронизации. Это дефект уровня памяти.
- **Race condition** — результат зависит от порядка событий. Это дефект уровня логики.

Они независимы. Можно устранить все data race и сохранить гонку: два запроса корректно
пишут состояние под локом, но старый ответ приходит последним и затирает новый. Лечится это не локом,
а версионированием, отменой устаревшего запроса или `flatMapLatest`.

# 2. Потоки

## 2.1. Что стоит знать про `Thread`

Поток в JVM/ART — это поток ОС: на Android его стек по умолчанию порядка мегабайта, создание стоит дорого.
Отсюда пулы и корутины.

Состояния: `NEW`, `RUNNABLE`, `BLOCKED` (ждёт монитор), `WAITING`/`TIMED_WAITING` (`wait`, `join`, `park`), `TERMINATED`.
Уметь читать их важно: в thread dump и в ANR-трейсе именно по ним видно, кто кого ждёт.

## 2.2. Прерывание — это кооперация, а не убийство

`Thread.stop()` удалён, потому что оставлял объекты в неконсистентном состоянии.
Единственный корректный механизм — **флаг прерывания**:

```kotlin
while (!Thread.currentThread().isInterrupted) {
    try {
        queue.take()          // блокирующие методы бросают InterruptedException
    } catch (e: InterruptedException) {
        Thread.currentThread().interrupt()   // флаг сброшен исключением — восстанавливаем
        break
    }
}
```

Два правила, которые проверяют: перехватив `InterruptedException`, вы обязаны либо восстановить флаг,
либо завершить работу. Проглотить его молча — значит сделать поток неостанавливаемым.
Прямая аналогия в корутинах — запрет проглатывать `CancellationException`.

Daemon-потоки не мешают процессу завершиться; на Android это менее значимо, чем на сервере,
но всплывает в вопросах про пулы.

# 3. `synchronized` изнутри

## 3.1. Что это такое

`synchronized` — это захват **монитора**, связанного с объектом. Байт-код: `monitorenter`/`monitorexit`,
монитор реентерабельный (один поток может войти повторно), освобождение гарантировано и при исключении.

```kotlin
class Counter {
    private val lock = Any()      // ✅ приватный объект-лок
    private var value = 0

    fun increment() = synchronized(lock) { value++ }
}
```

Почему `private val lock = Any()`, а не `synchronized(this)`: лочась на `this`, вы делаете свой лок
частью публичного API — любой внешний код может залочиться на вашем объекте и создать взаимоблокировку,
о которой вы не узнаете. Тем более нельзя лочиться на строковых литералах и на боксированных числах:
они интернируются, и «ваш» лок окажется общим на всё приложение.

## 3.2. Как это устроено в ART

Хороший ответ на «а что там под капотом» (и заодно связка с `09-jvm-memory-deep.md`):

- У каждого объекта в заголовке есть 32-битный **lock word**. Он может быть в одном из состояний: unlocked/**thin locked**, **fat locked**, hash code, forwarding address (последнее использует перемещающий GC).
- **Thin lock** — быстрый случай без конкуренции: прямо в lock word пишутся идентификатор потока-владельца и счётчик рекурсии. Никаких дополнительных структур и системных вызовов.
- **Инфляция в fat lock** происходит, когда одного слова не хватает: при реальной конкуренции (сначала ART некоторое время спинит, порядка полусотни итераций), при вызове `Object.wait()` и при необходимости сохранить identity hash code у залоченного объекта. Тогда выделяется структура `Monitor`, а в lock word остаётся `MonitorId`.
- Fat lock уже умеет очередь ожидающих и уход в ядро. Обратный процесс — дефляция — тоже существует.

Практический вывод: неконкурентный `synchronized` дёшев, дорогой он именно в момент конкуренции.
Поэтому «убрать synchronized ради скорости» — почти всегда преждевременная оптимизация,
а вот «сузить критическую секцию» — настоящая.

Забавное следствие, которое любят как follow-up: lock word делится между блокировкой и identity hash code,
поэтому вызов `hashCode()` у залоченного объекта может спровоцировать инфляцию монитора.

## 3.3. `wait` / `notify`

Низкоуровневый механизм ожидания условия. Требования, которые проверяют:

```kotlin
synchronized(lock) {
    while (!conditionMet) {        // ✅ именно while, не if
        lock.wait()                // вызывается только под своим монитором
    }
    // ...
}
```

- Вызывать можно только владея монитором, иначе `IllegalMonitorStateException`.
- Проверка условия — в цикле: возможны **spurious wakeups**, и состояние могло измениться, пока поток стоял в очереди.
- `notifyAll` безопаснее `notify`: с `notify` легко разбудить «не того» ждущего и получить зависание.
- Классическая беда — **потерянный notify**: сигнал послан до того, как ожидающий встал в `wait`.

В новом коде это писать не нужно: есть `BlockingQueue`, `Condition`, а в корутинах — `Channel` и `Flow`.
Знать надо, чтобы читать чужой и старый код.

# 4. Явные локи

## 4.1. `ReentrantLock`

Даёт то, чего нет у `synchronized`:

```kotlin
private val lock = ReentrantLock()

fun tryUpdate(): Boolean {
    if (!lock.tryLock(100, TimeUnit.MILLISECONDS)) return false   // ждать не вечно
    try {
        // критическая секция
        return true
    } finally {
        lock.unlock()      // ✅ обязательно в finally
    }
}
```

- `tryLock()` — с таймаутом и без блокировки навсегда: главный инструмент против взаимоблокировок.
- `lockInterruptibly()` — ожидание можно прервать.
- Честность (`ReentrantLock(true)`) — FIFO-порядок вместо произвола; убирает голодание, но сильно снижает пропускную способность. По умолчанию нечестный, и это обычно правильно.
- `newCondition()` — несколько независимых очередей ожидания на один лок (например, «не пусто» и «не полно» для буфера), чего `wait/notify` не умеет.

Цена: `unlock()` нужно писать руками. В Kotlin — `lock.withLock { }`.

## 4.2. `ReadWriteLock` и `StampedLock`

`ReentrantReadWriteLock` разрешает много читателей одновременно либо одного писателя.
Выигрывает только при действительно преобладающем чтении и небыстрых критических секциях;
на коротких операциях накладные расходы съедают выигрыш, и обычный лок оказывается быстрее.
`StampedLock` добавляет оптимистичное чтение (прочитали, потом проверили штамп), но он не реентерабельный
и легко используется неправильно.

Честный senior-ответ: сначала подумать, нельзя ли обойтись **immutable-снимком** состояния
и атомарной заменой ссылки. Это чаще всего быстрее и проще любых read-write локов.

## 4.3. Когда что выбирать

| Ситуация | Инструмент |
| --- | --- |
| Короткая критическая секция, простой инвариант | `synchronized` |
| Нужен таймаут, `tryLock`, прерывание, несколько условий | `ReentrantLock` |
| Одна переменная, простой переход | атомик/CAS |
| Много чтений, редкие записи | immutable-снимок + `AtomicReference`, во вторую очередь `ReadWriteLock` |
| Асинхронный код с suspend внутри секции | `kotlinx.coroutines.sync.Mutex` |

# 5. Атомики и CAS

## 5.1. Как работает CAS

Compare-and-swap — аппаратная инструкция: «запиши новое значение, только если текущее равно ожидаемому».
Вокруг неё строится неблокирующий цикл:

```kotlin
val counter = AtomicInteger(0)

// как выглядит incrementAndGet изнутри
while (true) {
    val current = counter.get()
    if (counter.compareAndSet(current, current + 1)) break
}
```

Отсюда важное свойство, которое надо проговорить: **лямбда в `updateAndGet` может выполниться несколько раз**
при конкуренции. Значит, внутри неё не должно быть побочных эффектов — только чистое преобразование.
Ровно то же правило действует для `MutableStateFlow.update` (это тот же CAS-цикл) и для reducer'ов.

```kotlin
val state = AtomicReference(UiState())
state.updateAndGet { it.copy(count = it.count + 1) }   // ✅ чистая функция
```

## 5.2. Проблема ABA

CAS проверяет **значение**, а не историю. Пока поток спал, значение могло стать B и снова A —
CAS пройдёт, хотя мир изменился. На уровне бизнес-логики лечится версионированием
(`AtomicStampedReference` или счётчик поколений в самом состоянии). Для обычного прикладного кода
это редкость, но вопрос любят задавать как проверку глубины.

## 5.3. Что есть в наличии

| Инструмент | Когда |
| --- | --- |
| `AtomicInteger`/`AtomicLong` | счётчики, генерация id |
| `AtomicBoolean` | однократная инициализация, флаги: `compareAndSet(false, true)` |
| `AtomicReference<T>` | атомарная замена immutable-состояния целиком |
| `LongAdder` | счётчик при высокой конкуренции: разносит инкременты по ячейкам, точная сумма только в `sum()` |
| `AtomicIntegerFieldUpdater` | экономия памяти на множестве объектов; редко нужно |
| `kotlin.concurrent.atomics` (`AtomicInt`, `AtomicLong`, `AtomicBoolean`, `AtomicReference`) | мультиплатформенные атомики в stdlib; появились в Kotlin 2.1.20, всё ещё под `@ExperimentalAtomicApi`, в 2.2 добавили `update`/`fetchAndUpdate`/`updateAndFetch` |
| `kotlinx-atomicfu` | атомики для библиотек с KMP; компиляторный плагин, на JVM разворачивается в обычные атомики без обёрток |

Идиома однократного действия, которая часто нужна на практике:

```kotlin
private val initialized = AtomicBoolean(false)

fun initOnce() {
    if (initialized.compareAndSet(false, true)) {
        doInit()      // выполнится ровно один раз, даже при гонке
    }
}
```

## 5.4. `@Volatile`

Нужен там, где важна **видимость одиночного** чтения/записи: флаг остановки, ссылка в double-checked locking,
поле, которое пишет один поток и читают многие. Не даёт атомарности составных операций.
На ARM компилятор вставляет вокруг него барьеры памяти — то есть это не бесплатно, но дёшево.

# 6. Безопасная публикация

## 6.1. В чём проблема

Объект можно сконструировать корректно, но опубликовать так, что другой поток увидит его
частично инициализированным. Классический источник — **утечка `this` из конструктора**:

```kotlin
class Widget(bus: EventBus) {
    init {
        bus.register(this)     // ❌ this ушёл наружу до завершения конструктора
    }
}
```

`val` компилируется в `final` поле, а у final-полей есть особые гарантии: если ссылка на объект
опубликована после завершения конструктора, читатель увидит корректно инициализированные final-поля.
Утечка `this` эту гарантию ломает.

Важная оговорка: `val` не делает граф иммутабельным. `val list: MutableList<T>` — изменяемое содержимое
за неизменяемой ссылкой, и оно требует собственного протокола синхронизации.

## 6.2. Double-checked locking

Каноническая ловушка на интервью. Корректный вариант **требует** `@Volatile`:

```kotlin
class Holder {
    @Volatile private var instance: Heavy? = null      // ❌ без @Volatile сломано

    fun get(): Heavy =
        instance ?: synchronized(this) {
            instance ?: Heavy().also { instance = it }
        }
}
```

Без `volatile` другой поток может увидеть ненулевую ссылку на ещё не достроенный объект:
запись ссылки и инициализация полей могут быть переупорядочены.

В Kotlin это писать почти никогда не нужно:

```kotlin
object Singleton                    // потокобезопасен по семантике инициализации класса
val heavy by lazy { Heavy() }       // режим SYNCHRONIZED по умолчанию
```

Режимы `lazy`: `SYNCHRONIZED` (по умолчанию, один вычисляющий поток), `PUBLICATION` (инициализатор
может выполниться несколько раз, опубликуется одно значение), `NONE` (без синхронизации — только
для гарантированно однопоточного доступа, например внутри UI-потока).

# 7. Потокобезопасные коллекции

## 7.1. Почему обёртки не спасают

```kotlin
val map = Collections.synchronizedMap(HashMap<String, Int>())

// ❌ каждая операция атомарна, но их пара — нет
if (!map.containsKey(key)) map[key] = compute()

// ❌ итерация вообще не защищена
for ((k, v) in map) { }        // ConcurrentModificationException
```

Синхронизированная обёртка защищает **отдельные вызовы**, а не составные операции и не обход.
Это первый вопрос-ловушка в теме коллекций.

## 7.2. `ConcurrentHashMap`

Правильный инструмент для конкурентной карты:

```kotlin
val cache = ConcurrentHashMap<String, Value>()

val value = cache.computeIfAbsent(key) { loadValue(it) }   // ✅ атомарно
cache.putIfAbsent(key, value)

// merge удобен для счётчиков — но тип значения должен совпадать
val hits = ConcurrentHashMap<String, Int>()
hits.merge(key, 1) { old, new -> old + new }               // ✅ инкремент или вставка 1
```

Что нужно знать про её свойства:

- Чтения не блокируются вообще; записи блокируют только «корзину», а не всю карту.
- Итератор **слабо согласован**: он не бросает `ConcurrentModificationException`, но и не даёт снимка — может отразить часть изменений, сделанных во время обхода.
- `size()` приблизителен и его нельзя использовать в инвариантах.
- `null` в качестве ключа и значения запрещён — именно чтобы `get() == null` однозначно означало отсутствие.
- Внутри функции `computeIfAbsent` нельзя изменять ту же карту: это приводит к зависанию.

## 7.3. Остальное

| Коллекция | Для чего | Цена |
| --- | --- | --- |
| `CopyOnWriteArrayList` | списки слушателей: много чтений, редкие записи, безопасная итерация | каждая запись копирует массив целиком |
| `ConcurrentLinkedQueue` | неблокирующая очередь | нет блокирующего ожидания |
| `LinkedBlockingQueue` / `ArrayBlockingQueue` | producer-consumer с блокировкой; **обязательно ограниченные**, иначе очередь съест память | `put`/`take` блокируют поток |
| `SynchronousQueue` | передача из рук в руки без буфера | используется в кэширующих пулах |
| `ConcurrentSkipListMap` | конкурентная сортированная карта | медленнее хэш-карты |

Отдельно про Android: `SparseArray`, `ArrayMap`, `LruCache` — экономят память, но
**`SparseArray` и `ArrayMap` не потокобезопасны** (`LruCache` синхронизирован внутри).
Их регулярно используют из нескольких потоков «потому что маленькие» — и получают повреждение структуры.

Альтернатива, которую стоит назвать первой: `kotlinx.collections.immutable` (`persistentListOf`)
плюс `AtomicReference`. Неизменяемый снимок читается без синхронизации вообще, а запись —
это атомарная замена ссылки. Для UI-состояния это почти всегда лучше конкурентных коллекций.

# 8. Координация потоков

| Примитив | Смысл | Аналог в корутинах |
| --- | --- | --- |
| `CountDownLatch` | дождаться N событий; **одноразовый** | `awaitAll`, `Job.join` |
| `CyclicBarrier` | N потоков ждут друг друга, переиспользуемый | — |
| `Semaphore` | ограничить число одновременных доступов | `kotlinx.coroutines.sync.Semaphore`, `limitedParallelism` |
| `Phaser` | барьер с переменным числом участников | — |
| `Exchanger` | обмен значениями между двумя потоками | `Channel` |

Главное отличие, которое надо озвучить: все они **блокируют поток**, а корутиновые аналоги — приостанавливают
корутину, освобождая поток. На Android с его ограниченным числом потоков это принципиально.

В тестах `CountDownLatch` до сих пор уместен — как раз чтобы дождаться колбэка из другого потока.

# 9. Пулы потоков

## 9.1. `ThreadPoolExecutor` и его параметры

```kotlin
ThreadPoolExecutor(
    corePoolSize, maximumPoolSize, keepAliveTime, unit,
    workQueue,              // ограниченная очередь
    threadFactory,          // именованные потоки: спасает при чтении ANR-трейсов
    rejectedExecutionHandler,
)
```

Неочевидная механика, которую любят спрашивать: пул сначала растёт до `corePoolSize`, затем
складывает задачи **в очередь**, и только когда очередь заполнена, увеличивает число потоков
до `maximumPoolSize`. Отсюда следствие: с неограниченной очередью `maximumPoolSize` не будет
достигнут никогда, а очередь будет расти до `OutOfMemoryError`.

Политики отказа: `AbortPolicy` (по умолчанию, исключение), `CallerRunsPolicy` (задачу выполняет
вызывающий поток — естественный backpressure), `DiscardPolicy`, `DiscardOldestPolicy`.

Почему `Executors.newFixedThreadPool` и `newCachedThreadPool` считаются опасными: у первого
неограниченная очередь, у второго неограниченное число потоков. Оба «работают» до пика нагрузки.

## 9.2. Что это значит для Android

- `AsyncTask` удалён, `Loader` устарел — в новом коде их нет.
- `HandlerThread` — поток с собственным `Looper`; ещё встречается для последовательной обработки (камера, сенсоры).
- В Kotlin-коде явные пулы почти не нужны: `Dispatchers.Default` — по числу ядер (минимум 2), для CPU-работы; `Dispatchers.IO` — до 64 потоков по умолчанию, делит общий пул с `Default`; `limitedParallelism(n)` — правильный способ ограничить конкретную подсистему, не создавая новый пул.
- Если оборачиваете чужой executor: `asCoroutineDispatcher()` плюс обязательный `close()`, иначе потоки останутся жить.

# 10. `ThreadLocal`

Значение, своё для каждого потока: типичные применения — `SimpleDateFormat` (он не потокобезопасен),
контекст трассировки, ссылка на текущую транзакцию.

Главная опасность на Android: `ThreadLocal` в потоке из пула живёт столько, сколько живёт **поток**,
а не задача. Положили туда что-то, ссылающееся на `Activity`, — получили утечку до конца процесса.
Правило: чистить в `finally` либо не использовать вовсе.

В корутинах поток не закреплён за корутиной, поэтому `ThreadLocal` напрямую не работает.
Мост — `asContextElement()`:

```kotlin
val traceId = ThreadLocal<String>()
withContext(traceId.asContextElement("abc")) { /* значение видно на любом потоке */ }
```

# 11. Классические проблемы

## 11.1. Deadlock

Нужны одновременно четыре условия (Коффмана): взаимное исключение, удержание с ожиданием,
отсутствие вытеснения, циклическое ожидание. Ломать проще всего последнее.

```kotlin
// ❌ два потока берут локи в разном порядке
fun transfer(a: Account, b: Account) = synchronized(a) { synchronized(b) { /* ... */ } }

// ✅ глобальный порядок захвата
fun transfer(a: Account, b: Account) {
    val (first, second) = if (a.id < b.id) a to b else b to a
    synchronized(first) { synchronized(second) { /* ... */ } }
}
```

Другие способы: не вызывать чужой код под локом (частая причина — колбэк, который лезет обратно),
использовать `tryLock` с таймаутом, а лучше — не брать два лока сразу.

Как ловить: thread dump (`jstack`, «Dump Java threads» в профайлере) или ANR-трейс — там видно
`BLOCKED`-потоки и на каком мониторе они стоят и кто им владеет.

## 11.2. Остальное

- **Livelock** — потоки активны, но прогресса нет: взаимно уступают. Лечится рандомизированной задержкой.
- **Starvation** — поток не получает ресурс; лечится честными локами, ценой пропускной способности.
- **Lock convoy** — все потоки выстраиваются в очередь на один горячий лок; лечится дроблением состояния или переходом на неблокирующие структуры.
- **False sharing** — независимые переменные в одной кэш-линии, ядра гоняют её туда-сюда. Именно поэтому существует `LongAdder`.

## 11.3. Особая ловушка Android: `runBlocking`

`runBlocking` на главном потоке блокирует его и даёт ANR, а если работа, которую он ждёт,
запланирована на тот же главный диспетчер — получается гарантированный дедлок.
Kotlin, кстати, защищает от родственной ошибки на уровне компиляции: вызвать `suspend`-функцию
внутри `synchronized { }` нельзя. Причина не в том, что лямбда «не suspend» — `synchronized`
инлайновая, и внутри inline-лямбд suspend-вызовы в принципе разрешены (`list.forEach { delay(1) }`
компилируется). Запрет обеспечивает отдельная диагностика компилятора
`SUSPENSION_POINT_INSIDE_CRITICAL_SECTION`: монитор принадлежит **потоку**, а корутина после
точки приостановки может возобновиться на другом — и тогда освобождать монитор будет не тот
поток, который его захватил. Парная диагностика `SYNCHRONIZED_ON_SUSPEND` запрещает `@Synchronized`
на suspend-функции. Обход через `runBlocking` внутри критической секции — прямой путь
к взаимоблокировке. Правильный инструмент — `Mutex`, он владеет не потоком, а корутиной.

# 12. Соответствие «классика → корутины»

| Классика | Корутины | Разница |
| --- | --- | --- |
| `synchronized` / `ReentrantLock` | `Mutex().withLock` | `Mutex` **не реентерабельный**: рекурсивный `withLock` — дедлок |
| `Semaphore` (JUC) | `kotlinx.coroutines.sync.Semaphore`, `limitedParallelism` | приостановка вместо блокировки |
| `CountDownLatch` | `Job.join`, `awaitAll` | структурная отмена |
| `BlockingQueue` | `Channel` | backpressure через suspension |
| `volatile` + слушатели | `StateFlow` | конфляция и текущее значение |
| `ExecutorService` | `Dispatchers` + scope | отмена и иерархия |
| потоко-локальное состояние | confinement через `withContext`/`limitedParallelism(1)` | нет привязки к потоку |

Иерархия предпочтений, которую стоит озвучить как принцип:

1. **Не разделять изменяемое состояние вообще** — immutable-данные и однонаправленный поток.
2. **Confinement** — состояние принадлежит одной корутине/диспетчеру.
3. **Атомарная замена** — `AtomicReference`/`StateFlow.update` с чистым преобразованием.
4. **`Mutex`** — если нужна составная критическая секция с suspend внутри.
5. **`synchronized`** — короткие несуспендящие участки, интероп с Java.

И обязательная оговорка: корутины гонки **не устраняют**. Внутри одной корутины код последователен,
но несколько дочерних корутин работают параллельно и на разных потоках.

## 12.1. `Mutex`: семантика и правильное применение

`kotlinx.coroutines.sync.Mutex` — coroutine-friendly взаимное исключение. Свободный mutex захватывается
сразу, а при занятом mutex вызывающая корутина приостанавливается, освобождая поток для другой работы.
Это главное отличие от `synchronized` и `ReentrantLock.lock()`, которые блокируют поток ожидания.

Предпочтительный API — `withLock`:

```kotlin
private val mutex = Mutex()

suspend fun changeState() {
    mutex.withLock {
        // Критическая секция.
    }
}
```

Ручная пара `lock()`/`unlock()` нужна редко: легко забыть `unlock()` на ветке ошибки. `withLock`
гарантирует освобождение через `finally`. Ожидание `lock` cancellable, но после успешного входа
защищённый код подчиняется обычным правилам cancellation.

На JVM успешный `unlock` happens-before последующего успешного `lock` того же mutex. Это обеспечивает
видимость записей между критическими секциями. Неуспешный `tryLock` такого memory effect не даёт.

В отличие от `synchronized`, `Mutex` не реентерабельный. Правильная композиция — один раз взять mutex,
а внутреннюю работу вынести в функцию, которая предполагает уже захваченный lock:

```kotlin
class Inventory {
    private val mutex = Mutex()
    private val quantities = mutableMapOf<String, Int>()

    suspend fun add(
        sku: String,
        amount: Int,
    ) {
        require(amount > 0)
        mutex.withLock {
            addLocked(sku, amount)
        }
    }

    suspend fun addAndGetTotal(
        sku: String,
        amount: Int,
    ): Int {
        require(amount > 0)
        return mutex.withLock {
            addLocked(sku, amount) // не пытается взять mutex повторно
            quantities.values.sum()
        }
    }

    // Вызывать только из mutex.withLock.
    private fun addLocked(
        sku: String,
        amount: Int,
    ) {
        quantities[sku] =
            quantities.getOrDefault(sku, 0) + amount
    }
}
```

### Пример 1. Ровно одно обновление токена

Иногда suspend-вызов под mutex — осознанная часть инварианта. Пока один запрос обновляет токен,
остальные должны дождаться того же результата, а не запустить параллельный refresh:

```kotlin
class TokenRepository(
    private val api: AuthApi,
    private val clock: Clock,
) {
    private val mutex = Mutex()
    private var token: Token? = null

    suspend fun validToken(): Token =
        mutex.withLock {
            token
                ?.takeIf { it.expiresAt > clock.now() }
                ?: api.refreshToken().also { refreshed ->
                    token = refreshed
                }
        }
}
```

Здесь network-вызов намеренно удерживает mutex: это гарантирует один refresh. Цена — все чтения токена
сериализованы. Для независимых ключей или сложного lifecycle лучше keyed mutex/single-flight, чтобы
одна медленная операция не останавливала несвязанные запросы.

### Пример 2. Чужой код вызывается после критической секции

Callback, listener или пользовательскую suspend-функцию не следует вызывать под mutex без строгой
необходимости: неизвестный код может долго выполняться или попытаться войти в тот же объект.
Под lock создают согласованный snapshot, а уведомляют снаружи:

```kotlin
class SettingsStore {
    private val mutex = Mutex()
    private val values = mutableMapOf<String, String>()

    suspend fun update(
        key: String,
        value: String,
        onChanged: suspend (Map<String, String>) -> Unit,
    ) {
        val snapshot = mutex.withLock {
            values[key] = value
            values.toMap()
        }

        // Mutex уже освобождён: callback не удерживает критическую секцию.
        onChanged(snapshot)
    }
}
```

Такой код защищает mutable map, минимизирует время удержания mutex и не допускает утечки изменяемой
коллекции наружу. При этом порядок завершения callbacks уже не сериализован — если он важен как часть
контракта, нужна отдельная модель доставки событий (`Channel`, actor/confinement или явно
спроектированная очередь).

`Mutex` выбирают для составного mutable-инварианта в coroutine-коде. Для одной переменной часто лучше
atomic/CAS, для ограничения параллелизма — `Semaphore`, для последовательного владельца состояния —
confinement/actor, а для короткого несуспендящего Java-кода — `synchronized`.

# 13. Android-специфика

- **Главный поток — не просто «UI-поток», а модель владения.** `View` можно трогать только из потока, который создал иерархию, иначе `CalledFromWrongThreadException`. Оговорка для follow-up: это проверяется у присоединённой иерархии, поэтому редкие «работает и из фонового» случаи — это неудачное совпадение, а не разрешение.
- **`Bitmap`, `Canvas`, `Matrix`** не потокобезопасны; параллельная обработка требует своей копии.
- Аннотации `@MainThread`, `@WorkerThread`, `@AnyThread` — часть контракта API; линт их проверяет, и в общем коде их стоит расставлять.
- **Room** сериализует записи; чтение с `Flow` уведомляет об изменениях. Запросы с главного потока по умолчанию запрещены — и это правильное поведение, а не помеха.
- **`SharedPreferences`** потокобезопасен, но `apply()` откладывает запись, и система ждёт завершения этих записей при остановке компонентов: пачка `apply()` умеет превратиться в ANR. Ещё один довод за `DataStore`.
- **Синглтоны и DI**: инициализация графа должна быть потокобезопасной, потому что компоненты могут создаваться системой параллельно (`ContentProvider` до `Application.onCreate`, ресивер в другом процессе).

# 14. Как это тестировать

Обычный юнит-тест конкурентность не ловит: он проходит на x86, при одном сценарии планировщика.
Что отвечать:

1. **Стресс-тест** — N потоков, общий барьер старта, проверка инварианта в конце. Ловит грубые ошибки, но недетерминирован.

```kotlin
@Test
fun `counter is thread safe`() {
    val counter = AtomicInteger()
    val threads = 8
    val perThread = 10_000
    val start = CountDownLatch(1)
    val done = CountDownLatch(threads)

    repeat(threads) {
        thread {
            start.await()
            repeat(perThread) { counter.incrementAndGet() }
            done.countDown()
        }
    }
    start.countDown()
    done.await(10, TimeUnit.SECONDS)

    assertEquals(threads * perThread, counter.get())
}
```

2. **Lincheck** (JetBrains) — то, что отличает знающего человека. Тест описывает операции структуры данных, а инструмент сам перебирает переплетения: stress-режим и model checking с проверкой линеаризуемости. При падении он печатает конкретный интерливинг, который ломает инвариант, — то, чего стресс-тест не даёт.

```kotlin
class CounterTest {
    private val counter = Counter()

    @Operation fun increment() = counter.increment()
    @Operation fun get() = counter.get()

    @Test fun modelCheckingTest() = ModelCheckingOptions().check(this::class)
}
```

3. **`Dispatchers.setMain` + `TestDispatcher`** — не про гонки, а про детерминизм: `runCurrent`/`advanceUntilIdle` позволяют воспроизвести конкретный порядок. Подробнее — в `08-coroutines-android.md`, раздел 2.
4. **Проверка на реальном ARM-устройстве** — обязательна для кода, где вы полагаетесь на модель памяти.

# 15. «Что не так с этим кодом»

## 15.1

```kotlin
@Volatile private var counter = 0
fun increment() { counter++ }   // ❌
```

`@Volatile` даёт видимость, но не атомарность: `counter++` — три операции. Нужен `AtomicInteger`.

## 15.2

```kotlin
class Cache {
    private val map = HashMap<String, Value>()
    @Synchronized fun get(key: String): Value? = map[key]
    fun put(key: String, v: Value) { map[key] = v }   // ❌ без синхронизации
}
```

Защищена половина доступов. `HashMap` при конкурентной записи может испортить внутреннюю структуру
(исторически — вплоть до зацикливания). Нужен `ConcurrentHashMap` либо синхронизация обоих методов.

## 15.3

```kotlin
private var instance: Heavy? = null    // ❌ нет @Volatile
fun get(): Heavy = instance ?: synchronized(this) {
    instance ?: Heavy().also { instance = it }
}
```

Сломанный double-checked locking: без `@Volatile` виден частично сконструированный объект.

## 15.4

```kotlin
fun addUnique(item: Item) {
    if (!list.contains(item)) list.add(item)     // ❌
}
```

Составная операция «проверил и добавил» не атомарна, даже если сама коллекция потокобезопасна.
Нужен лок вокруг обеих операций либо структура с атомарным `putIfAbsent`.

## 15.5

```kotlin
private val mutex = Mutex()
suspend fun outer() = mutex.withLock { inner() }
suspend fun inner() = mutex.withLock { /* ... */ }   // ❌ дедлок
```

`Mutex` не реентерабельный, в отличие от `synchronized`.

## 15.6

```kotlin
synchronized(this) {
    listener?.onChanged(newValue)     // ❌ чужой код под локом
}
```

Колбэк может обратиться обратно в ваш объект или взять второй лок — классический источник
взаимоблокировок и неожиданной рекурсии. Значение вычисляют под локом, уведомляют — снаружи.

## 15.7

```kotlin
val executor = Executors.newFixedThreadPool(4)   // ❌ неограниченная очередь
```

При всплеске нагрузки очередь растёт до OOM. Нужен `ThreadPoolExecutor` с ограниченной очередью
и осмысленной политикой отказа — либо корутины с `limitedParallelism`.

## 15.8

```kotlin
private val formatter = SimpleDateFormat("dd.MM.yyyy", Locale.getDefault())   // ❌ общий на всех
```

`SimpleDateFormat` не потокобезопасен: конкурентное использование даёт неверные даты и исключения.
Либо `ThreadLocal`, либо (правильнее) `java.time`/`kotlinx-datetime`, где форматтеры иммутабельны.

## 15.9

```kotlin
fun loadSync(): Data = runBlocking { repository.load() }   // ❌ вызывается с main
```

Блокировка главного потока и потенциальный дедлок, если работа планируется на тот же диспетчер.

## 15.10

```kotlin
try {
    queue.take()
} catch (e: InterruptedException) {
    // ❌ проглотили
}
```

Флаг прерывания сброшен, поток стал неостанавливаемым. Нужно восстановить флаг или выйти из цикла.
