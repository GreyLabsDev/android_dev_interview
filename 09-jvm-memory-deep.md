# 1. Память процесса Android-приложения

## 1.1. ART — это не HotSpot

Отвечая на вопросы про «JVM под капотом» на Android-интервью, важно сразу обозначить: приложение
исполняет **ART**, а не JVM. Различия, которые нужно назвать:

- ART исполняет **DEX**, а не class-файлы. Пайплайн: Kotlin → JVM bytecode → **D8 или R8** → dex2oat на устройстве. Важно, что это не два последовательных шага: R8 **заменяет** D8 в release-сборке и сам делает desugaring, dexing, шринк, оптимизацию и обфускацию за один проход из class-файлов. D8 — путь debug-сборки, где шринк не нужен. Ответ «сначала D8 сделал DEX, потом R8 его оптимизировал» неверен и его любят ловить.
- В ART **нет настройки `-Xmx`** в привычном виде и нет выбора сборщика вроде G1/ZGC. Лимиты задаёт система на уровне устройства.
- Нет PermGen и Metaspace. Классы и DEX-код **mmap'ятся** из файлов, поэтому неизменённые страницы кода система может выгрузить из RAM.
- Процесс форкается из **Zygote**, поэтому фреймворк и его классы разделяются между приложениями через copy-on-write.
- GC оптимизирован под другой критерий: не пропускная способность, а отсутствие джанка. Отсюда обязательная конкурентная компакция.

## 1.2. Из чего состоит память процесса

| Область | Что там | Освобождается |
| --- | --- | --- |
| Java heap | объекты Kotlin/Java | GC |
| Native heap | `malloc` из NDK, пиксели Bitmap (API 26+), Skia, движки БД | вручную / через `NativeAllocationRegistry` |
| Стеки потоков | по стеку на поток, порядка 1 МБ виртуального адресного пространства | при завершении потока |
| Code | mmap'нутый DEX, OAT/ODEX, `.so` | может быть выгружено ядром |
| Graphics | буферы поверхностей, текстуры GPU | системой |
| Ashmem / mmap-файлы | шаренные буферы, БД | системой |

Практический вывод: «утечка памяти» может не быть видна в Java heap вообще. Если Java heap ровный,
а `dumpsys meminfo` показывает рост — смотрите native heap и графику.

## 1.3. PSS, RSS, USS

- **RSS** — все резидентные страницы процесса, включая шаренные, посчитанные целиком.
- **PSS** — шаренные страницы поделены между процессами, которые их используют.
- **USS** — только приватные страницы, то есть сколько освободится, если процесс убить.

На интервью достаточно уметь сказать: PSS отвечает на вопрос «сколько мы стоим системе»,
USS — «сколько реально наше», RSS — «сколько физической памяти занято прямо сейчас».

Полезное уточнение, которое показывает, что вы следите за платформой: **инструменты сместились
с PSS на RSS**. Считать PSS дорого — нужно обойти все шаренные страницы, — поэтому Perfetto
работает с RSS, а `ActivityManager` на Android 14+ тоже отдаёт RSS в ряде API. PSS остался там,
где важна «справедливая» атрибуция общей памяти между процессами. Практический вывод: если
сравниваете замеры из разных инструментов, сначала убедитесь, что это одна и та же метрика,
иначе расхождение в полтора раза примете за регрессию.

## 1.4. Лимит heap и `largeHeap`

Лимит на Java heap задаётся устройством (`dalvik.vm.heapgrowthlimit` — обычный лимит для приложений,
`dalvik.vm.heapsize` — лимит с `largeHeap`) и различается от устройства к устройству: типично десятки—сотни МБ.

```kotlin
val am = getSystemService<ActivityManager>()!!
am.memoryClass       // лимит в МБ, например 192
am.largeMemoryClass  // лимит с android:largeHeap="true", например 512
```

**Подвох на follow-up:** «поставим `largeHeap` и проблема решится?» Нет. `largeHeap` не убирает
утечку, увеличивает время GC, повышает шанс быть убитым low memory killer'ом и маскирует настоящую
причину. Это инструмент для приложений, которым действительно нужны большие данные в памяти
(редакторы изображений, карты), а не средство от `OutOfMemoryError`.

# 2. Как работает сборка мусора в ART

## 2.1. Reachability и GC roots

GC освобождает объекты, до которых **нет пути от корней**. Не «на которые нет ссылок» — это
принципиально разные вещи.

Типичные GC roots:

- локальные переменные и параметры в стеках **живых** потоков;
- статические поля загруженных классов (и сами объекты `Class`/загрузчики);
- JNI global и local references;
- объекты, на которых удерживается монитор (`synchronized`);
- сами объекты `Thread` живых потоков.

Отсюда два классических ответа:

- **Циклические ссылки не мешают сборке.** Два объекта, ссылающиеся друг на друга, но недостижимые от корней, будут собраны. Подсчёт ссылок ART не использует.
- **Живой поток — это корень.** Поэтому запущенный `Thread` (или корутина в вечном scope), захвативший `Activity`, удерживает её независимо от того, что экран закрыт.

## 2.2. История сборщиков ART

Уметь пересказать эволюцию — сильный сигнал, потому что показывает понимание причин, а не заучивание.

1. **Dalvik**: mark-sweep со «стоп-мир» паузами, без компакции. Фрагментация приводила к OOM при наличии свободной памяти.
2. **ART CMS** (Concurrent Mark Sweep, Android 5–7): free-list аллокатор RosAlloc, компакция только при уходе приложения в фон (homogeneous space compaction, semi-space) — с паузой потоков.
3. **CC** (Concurrent Copying, дефолт с Android 8): region-based куча (RegionSpace), аллокация через bump pointer в потоковом буфере (RegionTLAB), **конкурентная компакция при каждом GC**. Google на момент анонса заявлял порядок улучшений «куча в среднем на треть меньше, аллокации примерно вдвое-втрое быстрее»; важнее самих цифр то, что паузы перестали зависеть от размера кучи. Точные проценты цитировать на интервью не стоит — они относились к конкретным замерам 2015 года.
4. **Generational CC** (Android 10): деление на young/old, чтобы не сканировать всю кучу.
5. **CMC** (Concurrent Mark Compact, с Android 14): компактирующий сборщик «на месте», в стиле Compressor, построенный на `userfaultfd` ядра. Используется на устройствах, где ядро поддерживает uffd; иначе остаётся CC.
6. **Generational CMC**: доводился до состояния дефолта флагом `use_generational_cmc` в AOSP; в анонсах Android 17 заявлен как стандарт для CMC.

## 2.3. Барьеры

Это любимый follow-up на тему «а как компакция может быть конкурентной, если приложение в это время меняет ссылки».

- **Write barrier** (card marking): при записи ссылки в поле помечается «карта» — участок кучи, который изменился. Нужен, чтобы отслеживать ссылки old → young и из boot image в перемещаемые области, не сканируя всю кучу.
- **Read barrier** (Baker-style, у CC): при **каждом** чтении ссылки из кучи выполняется небольшая проверка, которая гарантирует, что мутатор видит согласованное состояние во время копирования. Цена — накладные расходы на каждое чтение поля.
- **`userfaultfd`** (у CMC): вместо read barrier используется механизм ядра. Страницы, ещё не перенесённые, защищаются, обращение к ним вызывает фолт, который обрабатывает GC. Главный выигрыш CMC — **отсутствие read barrier**, то есть меньше накладных расходов на обычное исполнение кода.

## 2.4. Поколения

Гипотеза поколений: большинство объектов умирает молодыми. Поэтому young-сборка дешевле full.

В генерационном CMC деление многоступенчатое: свежеаллоцированные объекты составляют молодое
поколение, пережившие сборку постепенно продвигаются в старшие, и young-сборка обходит только
молодую часть плюс то, на что указывают запомненные ссылки из старого поколения. Точное число
ступеней и правила продвижения — деталь реализации AOSP, которая менялась между версиями, поэтому
на интервью её лучше не называть числом: если спросят, честнее сказать «продвижение по числу
переживших сборок, точные пороги — деталь реализации», чем назвать конкретную схему и ошибиться.

Для разработчика вывод простой и его стоит произнести: **краткоживущие объекты дешёвы**, дорогое —
это долгоживущие структуры и «средневозрастные» объекты, которые постоянно переживают сборку.
Классический антипаттерн — кэш, который держит объекты чуть дольше, чем нужно.

## 2.5. Чтение GC-логов

В logcat встречаются строки такого вида:

```
I art: Background concurrent mark compact GC freed 123456(12MB) AllocSpace objects,
       32(1MB) LOS objects, 29% free, 45MB/64MB, paused 1.203ms total 156.121ms
```

Что читать:

- **Причина**: `Background` (по достижении порога), `Alloc` (аллокация не прошла — приложение ждёт, худший случай), `NativeAlloc`, `Explicit` (кто-то позвал `System.gc()`), `HeapTrim`.
- **freed / LOS objects**: сколько освободили; LOS — large object space, куда попадают крупные объекты (порог измеряется килобайтами и зависит от версии рантайма), например большие массивы и примитивные буферы.
- **`45MB/64MB`**: текущее использование и целевой footprint.
- **paused vs total**: пауза потоков против общей длительности сборки. Именно `paused` влияет на джанк.

Красный флаг в логах — частые `Alloc` GC: это значит, что конкурентный сборщик не успевает
за скоростью аллокации, и потоки приложения блокируются.

Сборкой занимается выделенный поток `HeapTaskDaemon`. Но если куча исчерпана, первый поток,
которому не хватило памяти, выполняет сборку сам — отсюда фризы на аллокации.

## 2.6. `System.gc()`

Почему это почти всегда неправильный ответ:

- это лишь **подсказка**, рантайм не обязан её выполнять;
- явная сборка ломает эвристики генерационного сборщика и продвигает молодые объекты в старшее поколение;
- она не освобождает то, что достижимо от корней, то есть настоящую утечку не лечит;
- на слабых устройствах вызывает заметный фриз.

Единственное легитимное применение — детект утечек в инструментах (например, LeakCanary
принудительно инициирует сборку, чтобы проверить, попала ли слабая ссылка в очередь).

# 3. Ссылки

## 3.1. Четыре силы

| Тип | Когда собирается | Применение |
| --- | --- | --- |
| Strong (обычная) | никогда, пока достижима от корня | по умолчанию |
| `SoftReference` | когда рантайм считает, что не хватает памяти | «кэш» — но не на Android, см. ниже |
| `WeakReference` | на следующей сборке, если нет ни сильных, ни soft-ссылок | наблюдение за объектом без удержания |
| `PhantomReference` | после того как объект признан недостижимым; `get()` всегда возвращает `null` | освобождение внешних ресурсов |

## 3.2. Почему `SoftReference` — плохой кэш на Android

ART освобождает soft-ссылки агрессивно и без учёта полезности объекта: сборщик не знает,
какой элемент вам нужнее. В итоге кэш либо пустеет в самый неподходящий момент, либо мешает GC.
Официальная рекомендация — `LruCache` с явным лимитом по размеру.

```kotlin
val bitmapCache = object : LruCache<String, Bitmap>(maxSizeBytes) {
    override fun sizeOf(key: String, value: Bitmap) = value.allocationByteCount
}
```

На интервью это хороший ответ: «границы кэша должны быть решением продукта, а не побочным эффектом сборщика мусора».

## 3.3. `WeakReference` по делу

```kotlin
class ImageTask(view: ImageView) {
    private val viewRef = WeakReference(view)

    fun onLoaded(bitmap: Bitmap) {
        viewRef.get()?.setImageBitmap(bitmap)   // может быть уже null — это нормально
    }
}
```

**Подвох:** `WeakReference` — не средство от утечек, а средство от удержания. Если вы обёрнули
`Activity` в `WeakReference`, но сама задача живёт вечно, вы не устранили проблему,
а лишь сделали её невидимой для LeakCanary. Правильное решение — привязать время жизни задачи к владельцу.

Отдельная ловушка — `WeakHashMap`: ключи слабые, но если **значение** ссылается на ключ,
запись не будет удалена никогда.

## 3.4. `ReferenceQueue` и `PhantomReference`

`ReferenceQueue` — механизм уведомления: после того как объект собран, сама ссылка помещается в очередь.

```kotlin
val queue = ReferenceQueue<Heavy>()

fun watch(heavy: Heavy): PhantomReference<Heavy> = PhantomReference(heavy, queue)

// важно: сам объект нигде не должен удерживаться сильной ссылкой, иначе он никогда
// не станет недостижим и queue.remove() заблокируется навсегда
val ref = watch(createHeavy())

// в отдельном потоке:
val collected = queue.remove()   // объект стал недостижим → можно освободить внешний ресурс
```

Тонкость, на которой ломаются самодельные эксперименты: если объект лежит в локальной переменной
того же метода, где вы ждёте очередь, он остаётся сильно достижимым и уведомление не придёт
никогда. Поэтому в примере он создаётся и передаётся так, чтобы сильной ссылки не осталось.

На этой же механике — но на **слабых** ссылках, не на phantom — построено обнаружение утечек:
LeakCanary заводит `KeyedWeakReference` на объект и после принудительной сборки смотрит очередь.
Если ссылка в очереди не появилась, объект жив, то есть утёк. Phantom-ссылки для этого не
используются: они нужны там, где важно освободить внешний ресурс строго после того, как объект
уже недостижим.

## 3.5. `finalize()`, `Cleaner`, `NativeAllocationRegistry`

`finalize()` устарел и его не следует использовать: момент вызова не гарантирован, финализаторы
исполняются отдельным демоном (`FinalizerDaemon`), а `FinalizerWatchdogDaemon` уронит приложение
с `TimeoutException`, если финализатор не успел за отведённое время. Это причина реальных крэшей
в проде у библиотек с тяжёлыми финализаторами.

Что есть взамен — и здесь важно различать, что доступно **вам**, а что только фреймворку:

- `java.lang.ref.Cleaner` — регистрация действия по факту недостижимости. На Android доступен
  только с API 33, поэтому при реальном `minSdk` 24–26 это не вариант без обходных путей.
- `NativeAllocationRegistry` — сообщает GC, сколько нативной памяти «стоит» объект, чтобы сборщик
  учитывал это давление. Именно так учитываются пиксели Bitmap. Но это `libcore.util`,
  **не публичный SDK API**: им пользуется фреймворк, приложению он недоступен. Знать про него нужно
  для ответа «как ART узнаёт о нативной памяти Bitmap», а не как про свой инструмент.

Поэтому самый правильный ответ на интервью — детерминированное освобождение: `close()`, `use`,
`AutoCloseable`, освобождение на стороне NDK. Всё, что опирается на момент сборки мусора,
на Android ненадёжно по определению.

## 3.6. Кто кого держит

Механика, которую нужно понимать наизусть:

```kotlin
class MyActivity : Activity() {
    // ❌ анонимный объект держит ссылку на внешний this = на Activity
    private val listener = object : SensorEventListener { /* ... */ }

    // ❌ non-static inner class держит внешний this
    inner class Loader { /* ... */ }

    // ✅ вложенный класс без inner не держит внешний объект
    class Parser { /* ... */ }
}
```

Про лямбды в Kotlin: лямбда **без захвата** компилируется в синглтон и ничего не держит;
лямбда **с захватом** создаёт объект, который держит захваченные значения, включая неявный `this`.

Здесь легко ошибиться в популярную сторону, поэтому разберём точно. Если `viewModel` — свойство
Activity, то `view.setOnClickListener { viewModel.onClick() }` внутри Activity **держит Activity**:
чтобы прочитать поле, лямбда захватывает внешний `this`. Байткод обращается к
`this.getViewModel()`, а не к самому объекту ViewModel.

```kotlin
// в Activity
view.setOnClickListener { viewModel.onClick() }   // ❌ захватывает this (Activity)
view.setOnClickListener { finish() }              // ❌ тоже this

val vm = viewModel                                 // локальная переменная
view.setOnClickListener { vm.onClick() }           // ✅ захвачена только ссылка на ViewModel
```

Правило формулируется так: захватывается не то, что вы называете, а то, через что вы к этому
идёте. Обращение к полю или методу класса всегда тянет `this`; не тянет только захват локальной
переменной. На практике для слушателей View это не утечка — View умирает вместе с Activity, — но
ровно та же механика становится утечкой, когда лямбда уходит в синглтон, в статический кэш или
в долгоживущий `Handler`.

# 4. Утечки памяти

## 4.1. Что такое утечка на Android

Объект, который должен был умереть вместе со своим жизненным циклом (Activity, Fragment, View,
ViewModel, экран Compose), остаётся достижимым от GC root. Особенность Android: утечка одной
`Activity` тянет за собой всё дерево `View`, ресурсы и часто битмапы — то есть цена одной утечки
измеряется мегабайтами.

## 4.2. Таксономия типовых утечек

**1. Статическая ссылка на Context**

```kotlin
object AppHolder { var context: Context? = null }        // ❌ если положили Activity
```
Фикс: хранить только `applicationContext`, а лучше — не хранить.

**2. Синглтон, подписанный на короткоживущий объект**

```kotlin
object EventBus { private val listeners = mutableListOf<Listener>() }  // ❌ без remove
```
Фикс: симметричная отписка, привязанная к жизненному циклу; `Flow` вместо ручных слушателей.

**3. `Handler` и отложенные сообщения**

```kotlin
Handler(Looper.getMainLooper()).postDelayed({ updateUi() }, 60_000)   // ❌ держит Activity минуту
```

Фикс — и вот здесь спрятан подвох, который стоит проговорить: `removeCallbacks` к этому коду
**неприменим**, потому что лямбда превратилась в `Runnable`, ссылку на который никто не сохранил,
а `removeCallbacks` требует ровно тот же экземпляр. Работающие варианты:

```kotlin
private val handler = Handler(Looper.getMainLooper())
private val updateRunnable = Runnable { updateUi() }      // ссылку храним

override fun onDestroy() {
    handler.removeCallbacks(updateRunnable)               // ✅ тот же экземпляр
    // или проще, если на этом Handler больше ничего нет:
    // handler.removeCallbacksAndMessages(null)
    super.onDestroy()
}
```

Ещё лучше — не заводить `Handler` вовсе: `lifecycleScope.launch { delay(60_000); updateUi() }`
отменится сам, и забыть отписку негде.

**4. Поток или корутина вне scope**

```kotlin
GlobalScope.launch { repeat(1000) { delay(1000); updateUi() } }       // ❌ живой корень
```
Фикс: `viewModelScope`/`lifecycleScope`, app-scoped scope только осознанно.

**5. `ViewBinding` во фрагменте**

```kotlin
private var _binding: FragmentBinding? = null
override fun onDestroyView() { super.onDestroyView(); _binding = null }  // ✅ обязательно
```
Фрагмент живёт дольше своего `View` — забытое обнуление держит всю иерархию.

**6. ViewModel, держащая `View` или `Activity`**

Прямое нарушение контракта: ViewModel переживает пересоздание Activity, значит гарантированно утечёт.

**7. Незакрытые системные регистрации**

`BroadcastReceiver`, `SensorManager`, `LocationManager`, `ContentObserver`, `Animator`,
`ViewTreeObserver` — каждая регистрация требует парной отмены. `DisposableEffect` в Compose существует ровно для этого.

**8. Неограниченные кэши и коллекции**

`mutableMapOf` без лимита, растущий список сообщений, кэш битмапов без `LruCache`.
Формально не утечка (объекты достижимы «по делу»), практически — тот же OOM.

**9. `ThreadLocal` в пуле потоков**

Поток из пула живёт вечно, значит и значение в `ThreadLocal` тоже. Требуется явный `remove()`.

**10. Внешние SDK и `WebView`**

Классика: `WebView` исторически течёт из-за системных ссылок; тяжёлые SDK держат Context.
Ответ senior-уровня: изолировать в отдельный процесс или строго ограничивать время жизни.

**11. Compose-специфичные**

Отдельная группа, про которую спрашивают всё чаще, потому что интуиция из мира View здесь подводит:

- **`LocalContext.current`, сохранённый в долгоживущем объекте.** Внутри композиции это Activity
  context. Положить его в ViewModel, синглтон или в объект, созданный через `remember` и переданный
  наружу, — прямая утечка Activity.
- **`remember` без ключей, удерживающий тяжёлый объект.** `remember` живёт, пока жива композиция;
  если объект требует освобождения, нужен `DisposableEffect` или `RememberObserver`, иначе он
  просто останется в slot table.
- **Подписка, поднятая в неправильном месте.** `LaunchedEffect(Unit) { collect() }` привязан
  к композиции, а `rememberCoroutineScope().launch` — к call site, и второй переживает первый
  (разбор — в Compose-гайде, раздел 22.14).
- **`collectAsState()` вместо `collectAsStateWithLifecycle()`.** Формально не утечка объекта, но
  upstream остаётся активным на скрытом экране, то есть удерживает ресурсы и жжёт батарею —
  и в отчётах это выглядит как «растёт память в фоне».

## 4.3. Как работает LeakCanary

Знание внутренностей — частый вопрос, потому что оно проверяет понимание ссылок сразу.

1. `ObjectWatcher` при уничтожении Activity/Fragment/ViewModel/View оборачивает объект в `WeakReference`, зарегистрированную в `ReferenceQueue`.
2. Через некоторое время инициируется сборка мусора и проверяется очередь: если ссылка в очередь **попала**, объект собран, утечки нет.
3. Если не попала — объект считается **retained**. По достижении порога (по умолчанию 5 удержанных объектов) снимается heap dump. Момент снятия планируется через `MessageQueue.addIdleHandler`, чтобы не конкурировать с активным взаимодействием пользователя.
4. Дамп в формате HPROF разбирается библиотекой **Shark**, которая ищет **кратчайший путь сильных ссылок** от удержанного объекта до GC root.
5. В отчёте показывается эта цепочка — по ней и чинят.

Практический совет, который стоит проговорить: читать цепочку нужно не целиком, а искать в ней
**свой** код. LeakCanary сам подсвечивает подозрительный узел — место, где ссылка ведёт из
долгоживущего объекта в короткоживущий, — и почти всегда починка именно там. Длина цепочки о
приоритете ничего не говорит: длинная цепочка через фреймворк может упираться в одну вашу строку,
а короткая — оказаться ложным срабатыванием известной системной утечки (для них в LeakCanary есть
список исключений). Если один и тот же узел появляется в нескольких отчётах — вот это настоящий
признак, что чинить надо с него.

## 4.4. Чтение heap dump руками

Ключевые понятия:

- **Shallow size** — размер самого объекта.
- **Retained size** — сколько освободится, если удалить этот объект (то есть он плюс всё, что достижимо только через него).
- **Dominator** — объект, через который единственным путём достижима группа других.

Практика: сортируйте по retained size, ищите свои классы, экземпляров которых больше, чем должно
быть (две `MainActivity` — уже диагноз), затем смотрите цепочку до корня.

## 4.5. Чего LeakCanary не найдёт

- Утечки в native heap (NDK, Skia, сторонние `.so`).
- Растущие, но «легальные» кэши и коллекции.
- Утечки в другом процессе.
- Постепенный рост из-за фрагментации.

Вывод, который ждут на интервью: сначала определите, **где** растёт — в Java heap или в native, —
и только потом выбирайте инструмент. Смешивать два тулчейна без этого разделения — верный способ
потерять день. Что брать для native, разобрано в разделе 5.2.

# 5. Native-память и графика

## 5.1. Bitmap

- До Android 8.0 пиксели битмапа лежали в **Java heap** — отсюда исторические OOM на картинках и практика `recycle()`.
- С Android 8.0 (API 26) пиксели живут в **native heap**, а связь с Java-объектом учитывается через `NativeAllocationRegistry`, чтобы GC понимал реальную стоимость объекта.

Следствие: битмапы больше не так легко видны в Java heap, а профилировать их нужно как нативную память.
`recycle()` сегодня почти никогда не нужен вручную — этим занимаются библиотеки загрузки.

Самая частая практическая ошибка — декодировать изображение в полном разрешении для маленькой вьюхи.
Фото 4000×3000 в ARGB_8888 — это 48 МБ. Отсюда `inSampleSize`, `BitmapFactory.Options`,
а на практике — Coil/Glide с указанием целевого размера.

Что стоит знать помимо `BitmapFactory`, потому что это следующий вопрос:

- **`ImageDecoder`** (API 28) — современная замена `BitmapFactory`: умеет масштабировать при
  декодировании одним вызовом, поддерживает анимированные форматы и HEIF, работает точнее, чем
  `inSampleSize` (тот умеет только степени двойки).
- **`Bitmap.Config.HARDWARE`** — пиксели живут в графической памяти и не занимают ни Java, ни
  обычный native heap. Идеально для картинок, которые вы только показываете; ограничение —
  их нельзя читать и рисовать в них (`getPixel`, `Canvas`), поэтому для обработки не подходит.
- **`BitmapRegionDecoder`** — декодирование фрагмента большого изображения. Ответ на вопрос
  «как показать карту или скан на 100 мегапикселей»: вы никогда не держите его целиком.
- **`ARGB_8888` против `RGB_565`**: половина памяти за счёт потери альфы и градиентов. Сегодня это
  редко оправданный компромисс, но знать про него нужно — на очень слабых устройствах он всё ещё
  используется.

## 5.2. Инструменты для native

```bash
adb shell dumpsys meminfo <package>     # разбивка по областям: Java Heap, Native Heap, Code, Graphics
adb shell dumpsys gfxinfo <package>     # кадры и графическая память
```

Для профилирования нативных аллокаций — Perfetto с `heapprofd` (кто и сколько аллоцировал,
со стеками), `malloc_debug` для поиска порчи и двойных освобождений, GWP-ASan и MTE для выборочного
обнаружения ошибок памяти на живых устройствах. Это уровень, на котором большинство кандидатов
останавливается, поэтому одно упоминание уже выделяет.

# 6. OOM и завершение процесса

## 6.1. `OutOfMemoryError`

Сообщение в ART выглядит примерно так:

```
java.lang.OutOfMemoryError: Failed to allocate a 4194320 byte allocation with
1048576 free bytes and 1024KB until OOM, target footprint 201326592, growth limit 201326592
```

Как это читать по полям:

- **запрошено** 4194320 байт, то есть чуть больше 4 МБ (обычно это `IntArray` или буфер битмапа);
- **free bytes** — сколько всего свободно внутри текущего footprint, здесь 1 МБ;
- **until OOM** — сколько ещё можно вырасти до жёсткого лимита, здесь 1024 КБ;
- **target footprint** — текущий целевой размер кучи, **growth limit** — потолок для приложения.

Ключ к диагностике — соотношение этих чисел. Когда `target footprint` уже равен `growth limit`,
расти больше некуда: «free bytes» и «until OOM» считаются от одного значения и совпадают, а причина
именно в том, что куча исчерпана — ищите утечку или слишком крупные объекты. Другая картина —
когда «until OOM» велик, но аллокация всё равно не прошла: тогда речь о невозможности выделить
**непрерывный** блок нужного размера, то есть о фрагментации или об аллокации в Large Object Space.
Обратите внимание, что «free bytes» — общий объём свободного, а не размер наибольшего непрерывного
блока, поэтому вывод про фрагментацию делают не из этой строки, а из сопоставления размера запроса
с «until OOM».

Для компактирующего сборщика фрагментация — редкость. И учтите, что классический подозреваемый
здесь уже не работает: с API 26 пиксели Bitmap живут в native heap, поэтому Java-heap OOM они
больше не вызывают. Остаются крупные массивы и собственные буферы; нехватка нативной памяти
выглядит иначе — как `abort` в логе или как убийство процесса системой, а не как этот стектрейс.

Важный тезис: OOM почти всегда симптом, а не причина. Настоящие причины — утечка, неограниченный кэш,
декодирование изображений в полном разрешении, загрузка всей коллекции в память вместо пагинации.

## 6.2. Low memory killer и приоритеты

Порядок такой: сначала приоритет, потом объём. `lmkd` смотрит на `oom_score_adj` и выбирает группу —
foreground → visible → perceptible → service → cached/background, — а **внутри одной группы жертвой
становится самый крупный процесс**. Отсюда и следствие про `largeHeap` из раздела 1: он не меняет
вашу группу, но делает вас самым толстым в ней, то есть первым кандидатом на отстрел.

Поэтому «нас убили в фоне» — не баг, а нормальный режим работы, и приложение обязано корректно
восстанавливаться (см. process death в блоке 5 чеклиста).

Что действительно стоит уметь назвать — как узнать причину смерти процесса **в проде**, а не
догадываться. С API 30 для этого есть `ActivityManager.getHistoricalProcessExitReasons()`:

```kotlin
val am = getSystemService(ActivityManager::class.java)
val reasons = am.getHistoricalProcessExitReasons(packageName, /* pid = */ 0, /* maxNum = */ 5)
reasons.firstOrNull()?.let { info ->
    // REASON_LOW_MEMORY, REASON_ANR, REASON_CRASH_NATIVE, REASON_SIGNALED,
    // REASON_USER_REQUESTED (пользователь смахнул), REASON_EXCESSIVE_RESOURCE_USAGE
    log(info.reason, info.description, info.pss, info.rss)
}
```

Это прямой ответ на вопрос «как вы отличаете убийство по памяти от краша и от ANR» и на «как вы
собираете статистику по process death». Для ANR тот же API отдаёт трейс через `info.traceInputStream`,
что заметно удобнее устаревшего похода в `/data/anr/traces.txt`.

## 6.3. `onTrimMemory`

Актуальное состояние API, которое стоит знать точно:

- `onLowMemory()` **устарел** (deprecated в API 35) и не вызывается **начиная с API 34**.
- Ровно пять уровней устарели в API 35 и не доставляются с API 34: `TRIM_MEMORY_RUNNING_MODERATE`,
  `RUNNING_LOW`, `RUNNING_CRITICAL`, `MODERATE`, `COMPLETE`.
- Живыми остались два: `TRIM_MEMORY_UI_HIDDEN` (UI скрылся) и `TRIM_MEMORY_BACKGROUND`
  (процесс попал в LRU-список фоновых). Они не задепрекейчены, и именно на них строится реакция.

```kotlin
override fun onTrimMemory(level: Int) {
    if (level >= ComponentCallbacks2.TRIM_MEMORY_BACKGROUND) {
        releaseBackgroundResources()   // ушли в LRU-список фоновых: отпускаем всё некритичное
        imageCache.evictAll()
    } else if (level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN) {
        imageCache.evictAll()          // UI не виден: чистим то, что относится к отображению
    }
}
```

Про идиому `level >= КОНСТАНТА` стоит знать, почему она вообще работает: значения констант
**не упорядочены по срочности**. `TRIM_MEMORY_RUNNING_CRITICAL` равен 15, то есть **меньше**
`TRIM_MEMORY_UI_HIDDEN` (20), хотя критичнее. Сравнение через `>=` уцелело только потому, что из
доставляемых уровней остались лишь `UI_HIDDEN` (20) и `BACKGROUND` (40), и они упорядочены верно.
Порядок ветвей при этом важен: сначала более тяжёлый `BACKGROUND`, иначе `else if` до него
не дойдёт. Именно так написан пример в официальной документации.

Ответ, который выделяет: знание того, что большая часть уровней уже не приходит. Кандидаты часто
пересказывают документацию пятилетней давности с полным списком уровней и рассуждают о реакции
на `RUNNING_LOW`, которого не будет.

# 7. Как исполняется код: ART, JIT, AOT, dexopt

## 7.1. Гибридная модель

С Android 7 ART комбинирует интерпретацию, JIT и AOT, и AOT управляется профилями:

1. Установка. Если рядом с APK есть `.dm` с профилем (baseline или cloud), ART компилирует
   перечисленные в нём методы фильтром **`speed-profile`**. Если профиля нет — фильтр **`verify`**,
   то есть только верификация DEX, без AOT.
2. Первые запуски. Не скомпилированные методы **интерпретируются**; горячие — компилируются **JIT**
   в code cache. Параллельно рантайм пишет локальный профиль.
3. Фоновый dexopt. Раз в сутки, когда устройство простаивает и заряжается, ART Service
   (с Android 14 отвечает за dexopt) перекомпилирует приложение с `speed-profile`,
   используя накопленный локальный профиль, объединённый с облачным.

Фильтры компиляции, которые стоит знать: `verify` (только верификация), `speed-profile`
(AOT по профилю плюс оптимизация загрузки классов), `speed` (AOT всего).

## 7.2. Откуда берутся профили

- **Локальный** — собран рантаймом на устройстве по фактическому использованию.
- **Cloud Profile** — агрегированный Google Play по данным пользователей; появляется не сразу после релиза.
- **Baseline Profile** — тот, который вы генерируете сами и кладёте в сборку. Единственный, который работает **для первых пользователей новой версии**, пока облачный ещё не набрался.

Это и есть точный ответ на вопрос «зачем Baseline Profile, если есть Cloud Profile»:
облачный профиль требует времени на агрегацию, а baseline доступен с первого запуска после установки.

## 7.3. Проверка на устройстве

```bash
# статус dexopt: секция "Dexopt state" в выводе, строки вида
# [status=speed-profile] [reason=install-dm] — reason показывает, откуда взялся профиль
adb shell dumpsys package dexopt | grep -A 3 com.example

# на Android 14+ то же, но подробнее и в читаемом виде
adb shell pm art dump com.example

# принудительная компиляция по профилю и сброс профилей для чистого замера
adb shell cmd package compile -m speed-profile -f com.example
adb shell cmd package compile --reset com.example
```

Что искать: если статус остался `verify`, а не `speed-profile`, значит профиль не применился и
baseline profile в релизе не работает. Значение `reason` не менее полезно: `install-dm` означает,
что профиль приехал вместе с установкой (то есть ваш baseline profile попал в артефакт), а `bg-dexopt`
— что это результат фоновой перекомпиляции по локальному профилю, и на первых запусках у
пользователя его не было.

Точные имена полей и команд между версиями Android менялись, поэтому надёжнее всего смотреть
`dumpsys package dexopt` целиком и `pm art dump`, а не грепать по конкретному полю. Сам факт, что вы
проверяете применение профиля на устройстве, а не верите сборке, — это и есть хороший ответ
на «как я проверяю, что оптимизация реально доехала».

## 7.4. Смежные факты

- Если приложением долго не пользуются, система может выполнить **dexopt downgrade** и удалить AOT-артефакты, чтобы освободить хранилище. Поэтому первый запуск после долгого простоя медленнее.
- Рефлексия и динамическая загрузка скрывают код от компилятора и мешают оптимизациям — аргумент в пользу кодогенерации (KSP) вместо рефлексии в DI.
- Требование выравнивания нативных библиотек под **16 КБ страницы** — проверьте, если в проекте есть NDK или сторонние `.so`.

| StrictMode | I/O на main-потоке, а также `detectLeakedClosableObjects` и `detectLeakedRegistrationObjects` — незакрытые курсоры и незаснятые ресиверы |

Про тесты стоит сказать отдельно, потому что это тот самый «системный» ответ, который отличает
senior от крепкого middle. Вопрос «как вы боретесь с утечками» большинство закрывает через
«ставлю LeakCanary и смотрю уведомления». Сильный ответ — что детект утечек встроен в CI:
`DetectLeaksAfterTestSuccess` как правило JUnit в инструментальных тестах роняет сборку, если после
успешного теста Activity или Fragment остались достижимыми. Тогда утечка не доезжает до релиза,
и разговор идёт не про поиск, а про предотвращение.

Рабочий метод, который стоит описать как процесс: снять heap dump в чистом состоянии → выполнить
подозрительный сценарий N раз → снять второй дамп → сравнить количество экземпляров.
Гипотеза без двух снимков — это гадание.

# 9. «Что не так с этим кодом»

## 9.1

```kotlin
class Cache {
    companion object { private val map = HashMap<String, Bitmap>() }   // ❌
}
```

Статическая неограниченная мапа битмапов: живёт всё время процесса, растёт бесконечно, до OOM.
Нужен `LruCache` с лимитом.

## 9.2

```kotlin
class MyActivity : Activity() {
    override fun onCreate(b: Bundle?) {
        LocationProvider.subscribe { location -> updateMap(location) }  // ❌ нет отписки
    }
}
```

Лямбда захватывает `this` (через `updateMap`), провайдер живёт дольше экрана. Утечёт вся Activity.

## 9.3

```kotlin
class UserViewModel(private val activity: Activity) : ViewModel()   // ❌
```

ViewModel переживает пересоздание Activity — гарантированная утечка. Нужен `applicationContext`
или вообще отсутствие Context в ViewModel.

## 9.4

```kotlin
val ref = WeakReference(activity)
GlobalScope.launch { while (true) { delay(1000); ref.get()?.update() } }   // ❌
```

`WeakReference` замаскировала симптом: Activity собирается, но корутина работает вечно,
жжёт батарею и держит остальные захваченные объекты. Проблема не в ссылке, а в отсутствии владельца.

## 9.5

```kotlin
override fun onTrimMemory(level: Int) {
    if (level == ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW) clearCaches()   // ❌
}
```

Этот уровень не доставляется приложениям начиная с API 34. Код мёртвый.

## 9.6

```kotlin
class Heavy {
    protected fun finalize() { nativeFree(ptr) }    // ❌
}
```

Устаревший механизм с недетерминированным моментом вызова и риском `TimeoutException`
от watchdog-демона. Нужен явный `close()` (и `use { }`), либо `NativeAllocationRegistry`/`Cleaner`.

## 9.7

```kotlin
fun loadAvatar(path: String): Bitmap =
    BitmapFactory.decodeFile(path)      // ❌ полное разрешение в ImageView 48dp
```

Декодирование без `inSampleSize`/целевого размера. Одно фото с камеры — десятки МБ native-памяти.
