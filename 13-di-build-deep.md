# 1. Зачем DI и что такое граф

Инъекция зависимостей — это способ **не создавать зависимости внутри класса**, а получать их
снаружи. Всё остальное (аннотации, кодогенерация, контейнеры) — реализация.

Что даёт, если формулировать через выгоду, а не через определение:

- **Тестируемость.** Класс, который сам создаёт `Retrofit`, невозможно протестировать без сети.
- **Управление временем жизни.** Один `OkHttpClient` на приложение, один репозиторий на экран —
  это решение о скоупах, и его надо принимать явно.
- **Сборка графа в одном месте.** Иначе порядок инициализации размазан по коду и ломается в
  неожиданных местах.

**Граф зависимостей** — направленный граф, где узлы это типы, а рёбра «А нужен B». Задача
DI-фреймворка — по описанию графа уметь построить любой узел. Отсюда главное различие между
подходами: **когда граф проверяется** — при компиляции или в рантайме.

# 2. Dagger: что происходит при компиляции

Hilt — надстройка над Dagger: он задаёт стандартный набор компонентов, привязанных к жизненным
циклам Android, чтобы не писать их руками. Поэтому «как работает Hilt» — это всегда «как работает
Dagger» плюс «какие компоненты Hilt создал за вас». Начинаем с Dagger.

## 2.1. Что генерируется

Dagger — процессор аннотаций (KSP или KAPT). Он **не использует рефлексию**: на каждый элемент
графа он выписывает класс, который вы могли бы написать руками. Это стоит сказать вслух на
интервью — и добавить, что всё сгенерированное можно открыть в `build/generated` и прочитать.

| Что написали вы | Что появилось в `build/generated` |
| --- | --- |
| `@Inject constructor` у `Foo` | `Foo_Factory` — реализация `Factory<Foo>`, дёргает конструктор |
| `@Inject`-поля у `Foo` | `Foo_MembersInjector` — присваивает поля |
| `@Provides fun bar()` в модуле `M` | `M_BarFactory` — вызывает метод модуля |
| `@Component interface AppComponent` | `DaggerAppComponent` — сборка всего графа |
| `@Binds` | **ничего**: биндинг переписывается на провайдер реализации |

Последняя строка — готовый ответ на «чем `@Binds` отличается от `@Provides`, кроме синтаксиса»:
для `@Binds` не создаётся класс-фабрика и не остаётся вызова метода, Dagger просто подставляет на
место запроса интерфейса провайдер реализации.

## 2.2. Компонент — это объект с полями

Самое полезное представление, которое стоит держать в голове: **сгенерированный компонент —
обычный класс, в полях которого лежат провайдеры**. Упрощённо (в реальном коде при `fastInit`
картина другая, см. 2.3):

```java
public final class DaggerAppComponent implements AppComponent {

  private Provider<OkHttpClient> okHttpProvider;
  private Provider<UserRepository> userRepositoryProvider;

  private void initialize() {
    // @Singleton-биндинг: обёрнут в DoubleCheck — объект будет создан один раз
    this.okHttpProvider = DoubleCheck.provider(NetworkModule_ProvideOkHttpFactory.create());

    // биндинг без скоупа: фабрика как есть, новый объект на каждый get()
    this.userRepositoryProvider = UserRepositoryImpl_Factory.create(okHttpProvider);
  }

  @Override public UserRepository userRepository() {
    return userRepositoryProvider.get();
  }
}
```

Отсюда два вывода, вокруг которых крутится весь раздел 4: **скоуп — это поле в компоненте**, а
**время жизни скоупа — это время жизни объекта компонента**.

## 2.3. `fastInit` и `SwitchingProvider`

При наивной генерации на каждый биндинг нужен свой класс-провайдер. На большом графе это сотни
классов, которые грузятся при старте, — а загрузка класса на Android не бесплатна.

`fastInit` решает это так: вместо класса на биндинг генерируется **один вложенный класс
`SwitchingProvider` на компонент**, который умеет отдавать все типы, переключаясь по числовому id:

```java
private static final class SwitchingProvider<T> implements Provider<T> {
  private final int id;

  @Override public T get() {
    switch (id) {
      case 0: return (T) new UserRepositoryImpl(component.okHttpProvider.get());
      case 1: return (T) NetworkModule.provideApi(component.retrofit());
      default: throw new AssertionError(id);
    }
  }
}
```

Формулировка документации: «обычно число классов, загружаемых при инициализации компонента,
растёт с числом биндингов; в режиме fastInit — не растёт». Для Hilt это «улучшает производительность
старта, избегая загрузки классов при инициализации», и это **рекомендованный режим для
Android-приложений**. С Gradle-плагином Hilt он **включён по умолчанию**; выключить можно только
Gradle-свойством `-Pdagger.hilt.fastInit=false` — попытка задать флаг через опции процессора
аннотаций начиная с Dagger 2.60 приводит к ошибке сборки. Без плагина Hilt (чистый Dagger) режим
**не включён по умолчанию** и активируется флагом процессора `dagger.fastInit`.

**Чем платят — и это неочевидная часть.** В обычном режиме каждый `Provider` держит ссылки только на
провайдеры своих транзитивных зависимостей. В fastInit `SwitchingProvider` держит ссылку на **весь
компонент**, включая все скоупнутые объекты. Документация формулирует последствие прямо: в режиме
fastInit «утечка одного `Provider` эквивалентна утечке всего компонента». То есть выбор здесь не
«старт против пропускной способности» (замедления запросов документация не обещает), а «старт против
поверхности утечек» — и это стоит помнить вместе с разделом 4.10.

Две детали, которые хорошо показывают глубину, если разговор ушёл в кодогенерацию:

- switch режется на методы **по 100 case**, чтобы не упереться в лимит «huge method», после
  которого метод перестаёт компилироваться AOT;
- очень большие компоненты Dagger разбивает на **шарды** — вложенные классы, по которым
  раскладываются поля, потому что в один класс граф уже не влезает по лимитам.

## 2.4. Что реально означает «граф проверяется на компиляции»

Процессор видит граф целиком, поэтому ошибками компиляции становятся: отсутствующий биндинг
(`[Dagger/MissingBinding]`), дубликат, цикл (`[Dagger/DependencyCycle]`) и несовпадение скоупов
(раздел 4.5). Цена — та самая кодогенерация, про неё раздел 6.

Сдвиг, который стоит знать, если в проекте старый Dagger: флаг `dagger.useBindingGraphFix`
включён по умолчанию с 2.57, и с ним валидация строже — биндинг, установленный не в тот компонент
(например, требующий `Activity`, но объявленный в `SingletonComponent`), стал ошибкой, а не
молча работающим кодом.

# 3. Способы объявить биндинг

«Какими способами объект попадает в граф» — типовой вопрос, на который обычно отвечают двумя
пунктами из шести. Ниже полный набор с указанием, когда что.

## 3.1. `@Inject`-конструктор — способ по умолчанию

```kotlin
class UserRepositoryImpl @Inject constructor(
    private val api: UserApi,
    private val dao: UserDao,
) : UserRepository
```

Больше ничего писать не нужно: Dagger умеет создать этот класс. Правило простое: **свои классы —
через конструктор, чужие — через `@Provides`**.

Инъекция в поля нужна только там, где объект создаёте не вы: `Activity`, `Fragment`, `Service`,
`BroadcastReceiver`. Поле не может быть `private` (Dagger присваивает его снаружи) и не может быть
`val`. В Hilt эту инъекцию за вас вызывает `@AndroidEntryPoint`, в чистом Dagger вы делаете это
сами: `component.inject(this)` — и именно для этого генерируется `_MembersInjector`.

Мелочь на случай вопроса про версии: Dagger понимает и `javax.inject`, и `jakarta.inject` —
внутренний `dagger.internal.Provider` наследует оба интерфейса.

## 3.2. `@Provides` — когда объект надо собрать

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {

    // @Provides — когда объект нужно СОБРАТЬ: чужой класс, билдер, параметры.
    @Provides
    @Singleton
    fun provideOkHttp(): OkHttpClient = OkHttpClient.Builder()
        .callTimeout(30, TimeUnit.SECONDS)
        .build()
}
```

Деталь про производительность, которую редко называют: **модулю, у которого все `@Provides`
статические, экземпляр не нужен вообще** — Dagger его не создаёт. В Kotlin «статический» это `object`
или `companion object`, поэтому для модулей из одних `@Provides` правильный дефолт — `object`. В FAQ
Dagger та же мысль про Java: сделать метод `static` — самое простое улучшение, и такие методы «часто
работают лучше, чем instance-методы модуля». Смешивать `@Binds` и `@Provides` в одном модуле можно:
`@Binds` в самом интерфейсе, `@Provides` — в его `companion object`.

## 3.3. `@Binds` — когда нужно только «интерфейс → реализация»

```kotlin
@Module
@InstallIn(SingletonComponent::class)
interface RepositoryModule {

    // Абстрактный метод: Dagger не генерирует тело, только запись в графе.
    @Binds
    fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
}
```

Разница с `@Provides` не стилистическая: `@Binds` **дешевле** (см. таблицу в 2.1), поэтому для
простого «интерфейс → реализация» правильно всегда использовать его. Ограничения, они же источник
большинства ошибок компиляции:

- метод **абстрактный** — значит модуль должен быть `interface` или `abstract class`;
- **ровно один параметр**, и его тип должен быть присваиваем к возвращаемому;
- скоуп и квалификатор ставить можно, как на `@Provides`.

Новое в Dagger 2.60 — **`@Binds` без параметров**. Он не связывает интерфейс с реализацией, а
**явно объявляет в модуле биндинг класса, у которого есть `@Inject`-конструктор**:

```kotlin
@Module
interface FeatureModule {
    // у CartAnalytics есть @Inject constructor; биндинг был неявным, теперь он виден в модуле
    @Binds fun cartAnalytics(): CartAnalytics
}
```

Зачем это нужно — формулировка документации: обычно классы с `@Inject`-конструктором находятся
неявно, а явное объявление в модуле означает, что биндинг **больше нельзя перекрыть другим
биндингом из модуля**. То есть смысл в защите от подмены: случайный `@Provides` для того же типа
станет ошибкой «duplicate bindings» вместо молчаливой победы над неявным биндингом.

Ограничения жёсткие: нельзя ни квалификатор, ни скоуп, ни мультибиндинг-аннотацию, ни `@MapKey`;
тип не может быть параметризованным, у него должен быть ровно один `@Inject`-конструктор, и этот
конструктор не может быть скоупнутым. Кстати, javadoc самого `@Binds` про эту форму ещё не обновлён и
по-прежнему требует «ровно один параметр» — сверяться нужно с dev-guide.

## 3.4. Квалификаторы: два объекта одного типа

```kotlin
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthorizedClient

@Module
@InstallIn(SingletonComponent::class)
object ClientModule {
    @Provides @Singleton
    fun plainClient(): OkHttpClient = OkHttpClient()

    @Provides @Singleton @AuthorizedClient
    fun authorizedClient(auth: AuthInterceptor): OkHttpClient =
        OkHttpClient.Builder().addInterceptor(auth).build()
}

class ProfileApi @Inject constructor(@AuthorizedClient private val client: OkHttpClient)
```

`@Named("auth")` делает то же самое строкой, и это хуже: опечатка в строке в лучшем случае даст
`MissingBinding`, а в худшем — не тот объект. Свои квалификаторы проверяет компилятор.

Про ретеншен честный ответ такой: Dagger читает аннотации на компиляции, поэтому `BINARY` работает —
именно так написаны официальные примеры Android. Но **спека JSR-330 требует `RUNTIME`** и для
квалификаторов, и для скоупов, и проверка Error Prone `MissingRuntimeRetention` считает `BINARY`
ошибкой. Для квалификаторов у этого есть и практическое основание: в проекте, где рядом живёт другой
DI-фреймворк, непроретейненный квалификатор может привести к выбору не того биндинга. Если Error
Prone в проекте включён — ставьте `RUNTIME` и не спорьте.

## 3.5. `@BindsInstance`: как в граф попадает то, чего в графе нет

`Application`, `Context`, id пользователя, `orderId` — объекты, которые Dagger не может создать,
но которые нужны графу. Их передают при создании компонента:

```kotlin
@Singleton
@Component(modules = [NetworkModule::class])
interface AppComponent {

    @Component.Factory
    interface Factory {
        fun create(@BindsInstance application: Application): AppComponent
    }
}

val component = DaggerAppComponent.factory().create(application)
```

`@Component.Factory` (появилась в 2.22) против `@Component.Builder`: у фабрики ровно один метод и все
параметры сразу, причём **обязательны все** — даже те модули, которые Dagger умеет создать сам;
поэтому забыть что-то нельзя. У билдера сеттеры для таких модулей можно не вызывать, и он нужен, когда
часть параметров опциональна. Одновременно объявить и то и другое нельзя. Для нового кода выбирайте
фабрику.

В Hilt всё это спрятано: `@HiltAndroidApp` сам передаёт `Application`, а `@ApplicationContext` и
`@ActivityContext` — уже готовые квалификаторы.

## 3.6. `Lazy`, `Provider` и разрыв циклов

| Что просите | Что получаете |
| --- | --- |
| `Foo` | объект создан к моменту инъекции |
| `Lazy<Foo>` | объект создаётся при первом `get()`, дальше — **тот же** (мемоизация) |
| `Provider<Foo>` | `get()` **повторяет запрос к графу**: новый объект каждый раз, если биндинг без скоупа |

Ключевой нюанс про `Provider`: он не «делает новый объект», а именно повторяет запрос. Если
биндинг скоупнут, каждый `get()` вернёт один и тот же экземпляр — а `Provider<Builder>` для
сабкомпонента, наоборот, даёт новый билдер и новый экземпляр компонента. И ещё одна тонкость: новый
экземпляр гарантирован только для `@Inject`-конструктора; что вернёт тело `@Provides`, Dagger не
контролирует.

Ключевой нюанс про `Lazy`: **`Lazy` — это не скоуп**. Каждый инжектнутый `Lazy` независим и
запоминает своё значение отдельно от остальных, так что два места инъекции получат два разных
объекта. Формулировка javadoc: `@Singleton` — чтобы разделить один экземпляр между всеми клиентами,
`Lazy` — чтобы отложить создание внутри одного клиента.

Ловушка Kotlin: `dagger.Lazy` — это **не** `kotlin.Lazy`. У первого `get()`, у второго `value`;
перепутанный импорт даёт неочевидную ошибку компиляции.

**Разрыв циклов.** Цикл `A → B → A` Dagger ловит на компиляции. Разрывают его вставкой `Lazy` или
`Provider` в одно из звеньев — тогда в конструкторе объект ещё не нужен:

```kotlin
class A @Inject constructor(private val b: B)

class B @Inject constructor(private val a: Provider<A>) {
    // важно: get() вызывается при использовании, а НЕ в конструкторе/init
    fun doWork() = a.get().something()
}
```

Если это правило нарушить, вы увидите рантайм-падение из `DoubleCheck` с текстом
`Scoped provider was invoked recursively returning different results` — сообщение прямо
подсказывает круговую зависимость.

Цикл разрывают не только `Provider` и `Lazy`: валидатор считает «разрывающими» также
`Provider<Lazy<T>>`, `Map<K, Provider<V>>` и `Optional<Provider<T>>`. И структурный факт, который
хорошо звучит как понимание устройства: **все биндинги цикла обязательно лежат в одном компоненте** —
иначе цикла бы не получилось, потому что родитель не может зависеть от ребёнка.

## 3.7. Мультибиндинги

Механизм, без которого не работает модульная архитектура: несколько модулей вносят вклад в **одну**
коллекцию, не зная друг о друге.

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object CartInitializerModule {
    @Provides
    @IntoSet                       // добавляет в Set<AppInitializer>, а не заменяет его
    fun provideCartInitializer(impl: CartInitializer): AppInitializer = impl
}
```

Так собирают список инициализаторов, набор обработчиков deep link, карту `ViewModel`-фабрик и —
самое практичное — регистрацию навигационных маршрутов фич (пример в `12-architecture-deep.md`,
раздел 7).

Полный набор инструментов:

| Аннотация | Что делает |
| --- | --- |
| `@IntoSet` | добавляет **один** элемент в `Set<T>` |
| `@ElementsIntoSet` | добавляет **сразу несколько**: метод возвращает `Set<T>` |
| `@IntoMap` + ключ | добавляет запись в `Map<K, V>` |
| `@Multibinds` | **объявляет** пустую коллекцию (см. ниже) |

Ключи для карты: готовые `@StringKey`, `@ClassKey`, `@IntKey`, `@LongKey`, а для своего типа ключа
(например enum) — своя аннотация, помеченная `@MapKey`. Если ключ не помещается в один параметр,
ставится `@MapKey(unwrapValue = false)`, и ключом становится вся аннотация целиком.

Классическая карта фабрик ViewModel (то, что `@HiltViewModel` делает сейчас за вас, — см. 7.5):

```kotlin
@Module
interface ViewModelModule {
    @Binds @IntoMap @ClassKey(CartViewModel::class)
    fun bindCartViewModel(vm: CartViewModel): ViewModel
}

// одна общая фабрика вместо фабрики на каждую ViewModel
class MultibindingViewModelFactory @Inject constructor(
    private val creators: Map<Class<out ViewModel>, @JvmSuppressWildcards Provider<ViewModel>>,
) : ViewModelProvider.Factory {

    override fun <T : ViewModel> create(modelClass: Class<T>): T {
        @Suppress("UNCHECKED_CAST")
        return creators.getValue(modelClass).get() as T
    }
}
```

Что важно знать про мультибиндинги, кроме синтаксиса:

- **`@Multibinds` нужен для коллекций, которые могут остаться пустыми.** Если ни один модуль не
  сделал вклад, `Set<T>` просто нет в графе и вы получите `MissingBinding`. Абстрактный метод с
  `@Multibinds` объявляет коллекцию заранее — Dagger такие методы никогда не вызывает. Это ровно
  тот случай, когда фича-модуль отключён флагом сборки, и набор его вкладов пуст.
- **Дубликаты ведут себя по-разному.** В `Set` дубликаты допустимы и молча отбрасываются по
  правилам `java.util.Set`. В `Map` **одинаковый ключ — ошибка компиляции**.
- **Можно просить `Map<K, Provider<V>>`** (а с Dagger 2.58 — и `Map<K, Lazy<V>>`), и это часто то,
  что нужно: значения не создаются все сразу, а только то, которое достали по ключу. Именно так
  работают карты ViewModel-фабрик. Обратное неверно: `Set<Provider<T>>` попросить нельзя.
- **Ловушка Kotlin с wildcard.** Kotlin превращает `Set<Foo>` в `Set<? extends Foo>`, и Dagger не
  находит биндинг: `Set<? extends Foo> cannot be provided…`. Лечится `@JvmSuppressWildcards` в
  месте инъекции: `Set<@JvmSuppressWildcards AppInitializer>`. Это один из самых частых
  «непонятных» сбоев мультибиндингов в Kotlin-проектах. Вторая kotlin-специфика: с Dagger 2.56 в
  `@Multibinds` и `@ElementsIntoSet` нужно использовать `Set`/`Map` из `kotlin.collections`, а не из
  `java.util`.
- **Мультибиндинг-аннотации нельзя ставить на `@Inject`-конструктор** — только на методы модуля.
  Причина по FAQ: иначе Dagger пришлось бы сканировать весь classpath, чтобы найти вклады.
- **`@LazyClassKey` вместо `@ClassKey`, если карта большая.** С `@ClassKey` при построении карты
  загружаются **все** классы-ключи; `@LazyClassKey` генерирует под капотом карту со строковыми
  ключами, и класс загружается только при обращении. Цена: нельзя брать `keySet()`/`entrySet()`
  (это загрузит всё и обнулит смысл) и нельзя смешивать с `@ClassKey` для того же типа.
- **Сабкомпонент может дополнять коллекцию родителя.** Внутри сабкомпонента будет
  «родительские + свои» элементы, в родителе — только свои. Это удобный способ добавлять
  обработчики на уровне экрана, но и источник удивления «почему в разных местах разный Set».

## 3.8. `@BindsOptionalOf`: зависимость, которой может не быть

```kotlin
@Module
@InstallIn(SingletonComponent::class)
interface AnalyticsModule {
    @BindsOptionalOf
    fun optionalPremiumTracker(): PremiumTracker
}

class Analytics @Inject constructor(
    private val premium: Optional<PremiumTracker>,   // пусто, если биндинга нет
)
```

Смысл: граф собирается, даже когда биндинга нет, — например когда фича-модуль не подключён в этом
варианте сборки. Метод должен быть абстрактным, без параметров, и не может возвращать тип с
`@Inject`-конструктором (такой тип есть всегда, и `Optional` был бы бессмысленным). Просить можно
`Optional<Foo>`, `Optional<Provider<Foo>>`, `Optional<Lazy<Foo>>`. Тонкость: если биндинг существует,
но помечен `@Nullable`, то `Optional<Foo>` — ошибка компиляции, потому что `Optional` не хранит
`null`; в этом случае берут `Optional<Provider<Foo>>`. И ещё: отсутствующий в компоненте биндинг
может присутствовать в сабкомпоненте.

Альтернатива в Kotlin-проектах — мультибиндинг-`Set` с `firstOrNull()`; она часто удобнее, потому
что не требует `Optional`.

## 3.9. Assisted-инъекция: часть параметров из графа, часть с места вызова

Классическая проблема: `orderId` известен только в рантайме, остальные зависимости — из графа.
Раньше под это писали фабрику руками, с Dagger 2.31 её генерируют:

```kotlin
class ReportGenerator @AssistedInject constructor(
    private val repository: ReportRepository,      // из графа
    @Assisted private val reportId: String,        // с места вызова
) {
    @AssistedFactory
    interface Factory {
        fun create(reportId: String): ReportGenerator
    }
}

class ReportScreenModel @Inject constructor(private val factory: ReportGenerator.Factory) {
    fun open(id: String) = factory.create(id)
}
```

Если assisted-параметров несколько и они одного типа, их различают именем:
`@Assisted("from") from: LocalDate` — причём метка ставится **и на параметр фабрики, и на параметр
конструктора** (по именам параметров Dagger ориентироваться не может: они не всегда сохраняются).

Два ограничения, которые спрашивают именно как проверку на внимательность:

- **сам `@AssistedInject`-тип инжектить нельзя** — только его `@AssistedFactory`, даже если
  assisted-параметров в конструкторе нет вовсе;
- **`@AssistedInject`-тип нельзя скоупить.** Это логично: объект зависит от аргумента вызова, и
  «один на компонент» для него не имеет смысла.

Метод фабрики должен возвращать этот тип и принимать все `@Assisted`-параметры в том же порядке.

Для ViewModel у Hilt есть отдельная поддержка — она закрывает старую боль «как передать аргумент
экрана в ViewModel через DI»:

```kotlin
@HiltViewModel(assistedFactory = OrderViewModel.Factory::class)
class OrderViewModel @AssistedInject constructor(
    private val repository: OrderRepository,
    @Assisted private val orderId: String,
) : ViewModel() {
    @AssistedFactory
    interface Factory {
        fun create(orderId: String): OrderViewModel
    }
}

// в Compose
val viewModel = hiltViewModel<OrderViewModel, OrderViewModel.Factory>(
    creationCallback = { factory -> factory.create(orderId) },
)
```

Стоит знать и границу применимости: обычно аргументы экрана лучше брать из `SavedStateHandle`,
потому что они тогда переживают убийство процесса. Assisted нужен там, где значение не является
частью состояния навигации (разбор компромисса — в 7.5).

# 4. Скоупы в Dagger 2

Самый частый вопрос по DI после «зачем он нужен» — и самый частый источник неточных ответов вроде
«Dagger хранит объекты в скоупе». Ниже — что происходит на самом деле.

## 4.1. `@Scope` — это метка для компилятора, а не механизм рантайма

`@Scope` — мета-аннотация из `javax.inject` (Dagger понимает и `jakarta.inject`). Своим скоупом
вы объявляете **новую аннотацию**, помеченную `@Scope`. `@Singleton` из `javax.inject` — ровно
такая же аннотация, ничем не привилегированная.

Главное, что стоит проговорить: **в рантайме никакого «реестра скоупов» не существует**. У
аннотации всего два читателя, и оба работают на этапе компиляции:

1. **валидатор** — проверяет, что биндинг лежит в компоненте с тем же скоупом (4.5);
2. **генератор кода** — решает, надо ли кэшировать объект в поле компонента (4.2).

Прямой цитаты «реестра нет» в документации не найти, но доказательство простое и его удобно привести:
в сгенерированном коде скоупнутый объект лежит в обычном поле компонента, никакой карты по аннотациям
нет, — а собственные скоупы Hilt объявлены с `@Retention(CLASS)`, то есть в рантайме их в байткоде
физически нет. Читать в рантайме нечего.

Из этого сразу следует ответ на «а что мешает написать свой DI со скоупами руками»: ничего,
скоуп — это соглашение плюс кэш.

## 4.2. Что генерируется для скоупнутого биндинга: `DoubleCheck`

Формулировки из документации Dagger, в переводе: «реализация компонента гарантирует, что на
**экземпляр компонента** существует только одна поставка каждого скоупнутого биндинга» и
«реализация компонента держит ссылки на все скоупнутые объекты, чтобы их можно было
переиспользовать».

Технически это одна вещь: провайдер оборачивается в `DoubleCheck` и кладётся в поле компонента.
`DoubleCheck` из `dagger.internal` — дважды проверенная блокировка, вот её суть (упрощён только
nullability-обвес):

```java
public final class DoubleCheck<T> implements Provider<T>, Lazy<T> {
  private static final Object UNINITIALIZED = new Object();

  private volatile Provider<T> provider;
  private volatile Object instance = UNINITIALIZED;

  @Override public T get() {
    Object result = instance;
    if (result == UNINITIALIZED) {     // быстрый путь: без блокировки
      result = getSynchronized();
    }
    return (T) result;
  }

  private synchronized Object getSynchronized() {
    Object result = instance;
    if (result == UNINITIALIZED) {     // вторая проверка — уже под блокировкой
      result = provider.get();
      instance = reentrantCheck(instance, result);
      provider = null;                 // фабрика больше не нужна — отдаём её GC
    }
    return result;
  }
}
```

Что здесь стоит уметь заметить:

- **`volatile` + двойная проверка** ⇒ скоупнутый биндинг **потокобезопасен**: два потока не создадут
  два объекта. Это ответ на follow-up «что будет, если запросить `@Singleton` из двух потоков».
- **`provider = null` после создания** — ссылка на фабрику обнуляется, чтобы фабрика и её
  зависимости стали доступны сборщику мусора. Хорошая деталь: показывает, что вы читали исходники.
- `DoubleCheck` реализует **и `Provider`, и `Lazy`** — то есть `Lazy<Foo>` из 3.6 использует ровно
  тот же механизм мемоизации.
- `DoubleCheck.provider()` **не оборачивает повторно** то, что уже `DoubleCheck` — случай
  скоупнутого `@Binds`, делегирующего в скоупнутый биндинг.
- `reentrantCheck` — источник рантайм-исключения про рекурсивный вызов скоупнутого провайдера
  (см. 3.6).

## 4.3. Главное следствие: скоуп — это время жизни экземпляра компонента

Если скоуп это просто поле в компоненте, то дальше всё выводится механически.

- **`@Singleton` не означает «один на процесс».** Он означает «один на экземпляр компонента».
  Создали два `DaggerAppComponent` — получили два «синглтона», и оба валидны с точки зрения
  Dagger. Это самая популярная ловушка про скоупы.
- **Выход из скоупа — это не вызов метода, а потеря ссылки.** Документация говорит прямо:
  «поскольку компоненты самодостаточны, выйти из скоупа так же просто, как отпустить все ссылки на
  экземпляр компонента». Никакого `component.destroy()` не существует.
- **За время жизни отвечаете вы.** Оттуда же: «получить правильное поведение, связанное с
  аннотацией скоупа, — обязанность вызывающего кода», который создаёт экземпляры компонента в
  нужные моменты. `@ActivityScope` ничего не знает про `Activity`; связь возникает только потому,
  что вы создали компонент в `onCreate` и отпустили в `onDestroy`.

Именно так и стоит отвечать на «как работает скоуп»: не «Dagger хранит объекты в скоупе», а
«скоуп — это указание кэшировать объект в поле компонента, а временем жизни компонента управляет
код, который его создал».

## 4.4. Без скоупа и `@Reusable`

Биндинг **без скоупа не кэшируется вообще**: каждый запрос — новый объект. Это правильный дефолт, и у
документации Hilt на этот счёт есть прямая формулировка, которую полезно уметь процитировать:
**«скоупирование биндинга стоит и размера сгенерированного кода, и производительности в рантайме,
поэтому используйте скоупы экономно» — скоуп ставят тогда, когда он нужен для корректности**, а не
для «оптимизации». Плюс скоупнутый объект живёт до конца жизни компонента, даже когда он давно не
нужен.

Между «всегда новый» и «один на компонент» есть третий вариант — `@Reusable`:

```kotlin
@Reusable
class JsonParser @Inject constructor()
```

Javadoc: «скоуп, который указывает, что объект, возвращаемый биндингом, **может быть (а может и
не быть)** переиспользован»; полезен, «когда вы хотите ограничить количество созданий типа, но нет
конкретного времени жизни, в течение которого экземпляр должен быть один».

| | Обычный скоуп (`@Singleton` и свои) | `@Reusable` |
| --- | --- | --- |
| Привязан к компоненту | да, только к компоненту с этой аннотацией | нет, годится для любого |
| Реализация | `DoubleCheck` | `SingleCheck` |
| Потокобезопасность создания | да | **нет**: два потока могут создать два объекта |
| Гарантия «один экземпляр» | в пределах компонента — да | нет: кэширует каждый компонент, который биндинг использует |

Точная механика кэширования у `@Reusable`: объект кэширует **тот компонент, который биндинг реально
использует**. Если предок уже закэшировал — сабкомпонент переиспользует его; если биндинг используют
два сабкомпонента без общего предка, у каждого будет свой объект.

`SingleCheck` в исходниках описан как «мемоизация простой ленивой инициализацией, **не** паттерном
double-checked lock». Отсюда правило: `@Reusable` годится для **stateless и дешёвых в дублировании**
объектов, где важно лишь не создавать их на каждый чих. Для чего-то с состоянием — кэш, счётчик,
соединение — `@Reusable` ошибка.

Ещё деталь: валидатор скоупов **пропускает** `@Reusable`, поэтому такой биндинг не конфликтует ни с
одним компонентом.

## 4.5. Правила скоупов, которые знает компилятор

Знать формулировки сообщений полезно: это звучит как опыт, а не как теория.

**1. Скоупнутый биндинг в компоненте без такого скоупа.** Правило: компонент со скоупом может
содержать только биндинги без скоупа или биндинги того же скоупа — в любом месте графа. Сообщения:

- `<Component> (unscoped) may not reference scoped bindings:` — у компонента вообще нет скоупа;
- `<Component> scoped with @Singleton may not reference bindings with different scopes:` — скоуп
  есть, но не тот.

**2. Одинаковый скоуп у сабкомпонента и его предка — ошибка:**
`<Child> has conflicting scopes: <Parent> also has @Singleton`. Причина не формальная: было бы
неоднозначно, в чьём поле хранить объект. При этом **сиблинги могут иметь одинаковый скоуп** —
они не достижимы друг из друга, и каждый держит свой экземпляр. Документация: «два сабкомпонента,
не достижимые друг из друга, могут быть связаны с одним скоупом… фактически у них разные экземпляры
скоупа, даже если аннотация одна». Практический вывод: один `@ScreenScope` на все экраны — это
нормально, если компоненты экранов сиблинги.

**3. У компонента может быть больше одного скоупа — но это не «две разные жизни».** Документация:
«компоненты могут иметь несколько аннотаций скоупа; это объявляет, что все они **относятся к одному и
тому же скоупу**, и компонент может содержать биндинги с любым из объявленных скоупов». То есть
аннотации становятся синонимами одного хранилища, а не отдельными временами жизни. Реальный
сценарий — миграция: компонент временно помечают и `@Singleton`, и легаси-`@ApplicationScope`, пока
переписывают биндинги. В сообщениях об ошибке Dagger перечисляет весь набор через пробел.

**4. `@Inject`-конструктор со скоупом — «неявный биндинг».** Он доступен компоненту с этим скоупом
**и всем его потомкам**, а объект хранится в том компоненте, где скоуп объявлен. Поэтому
`@FeatureScope class CartManager @Inject constructor(...)` работает без единой строчки в модулях.

**5. Один и тот же модуль в компоненте и его сабкомпоненте:**
`<Component> repeats modules with scoped bindings or declarations:`. Заодно полезно знать, что
повторяющийся модуль автоматически переиспользует один экземпляр, а попытка передать его в билдер
сабкомпонента падает в рантайме с `UnsupportedOperationException`.

Строгость проверки конфликтующих скоупов регулируется флагом процессора
(`dagger.disableInterComponentScopeValidation`) — знать это стоит только чтобы не удивляться, если
в чужом проекте собирается то, что собираться не должно.

## 4.6. Свой скоуп: как сделать

Объявление — три строки:

```kotlin
@Scope
@MustBeDocumented
@Retention(AnnotationRetention.RUNTIME)
annotation class FeatureScope
```

Про ретеншен то же, что и для квалификаторов в 3.4: Dagger читает аннотацию на компиляции, поэтому
`CLASS` работает — собственные скоупы Hilt (`@ActivityRetainedScoped` и остальные) объявлены именно
так. Но спека JSR-330 требует `RUNTIME`, и Error Prone это проверяет; в Kotlin `RUNTIME` к тому же
дефолт, так что писать его — бесплатно.

Про имя есть хорошее правило из документации Android: **скоуп называют по времени жизни, а не по
задаче** — `@ActivityScope`, а не `@LoginScope`. Причина практическая: одну и ту же аннотацию будут
переиспользовать сиблинг-компоненты (это разрешено, см. правило 2 в 4.5), и имя «про задачу» станет
врать при первом же переиспользовании.

Дальше — чистый Dagger, три шага:

```kotlin
// 1. Сабкомпонент с этим скоупом
@FeatureScope
@Subcomponent(modules = [CheckoutModule::class])
interface CheckoutComponent {

    fun cartManager(): CartManager

    @Subcomponent.Factory
    interface Factory {
        fun create(@BindsInstance orderId: String): CheckoutComponent
    }
}

// 2. Устанавливаем в родителя модулем — так Dagger видит, запрашивают ли сабкомпонент вообще
@Module(subcomponents = [CheckoutComponent::class])
interface CheckoutInstallModule

// 3. Биндинг, который должен быть один на фичу. Больше ничего писать не нужно:
//    скоупнутый @Inject-конструктор — это неявный биндинг (правило 4 из 4.5)
@FeatureScope
class CartManager @Inject constructor(private val api: CartApi)
```

И самый важный, четвёртый шаг, которого Dagger за вас не сделает: **кто-то должен держать экземпляр
компонента ровно столько, сколько живёт фича**.

```kotlin
@Singleton
class CheckoutComponentHolder @Inject constructor(
    private val factory: CheckoutComponent.Factory,
) {
    private var component: CheckoutComponent? = null

    fun open(orderId: String): CheckoutComponent =
        component ?: factory.create(orderId).also { component = it }

    // выход из скоупа — это буквально потеря ссылки
    fun close() {
        component = null
    }
}
```

Забыли `close()` — получили утечку (4.10). Позвали `open()` дважды без `close()` — получили два
разных `CartManager`, каждый «единственный» в своём компоненте.

Про способ установки: `@Module(subcomponents = ...)` предпочтительнее абстрактного фабричного
метода в родителе, потому что во втором случае Dagger обязан сгенерировать сабкомпонент, даже если
его никогда не запрашивают, — сам метод считается запросом.

## 4.7. Сабкомпонент против зависимости компонентов

Второй способ связать компоненты — `@Component(dependencies = [OtherComponent::class])`. Разница
важна и её спрашивают:

| | `@Subcomponent` | `dependencies = [...]` |
| --- | --- | --- |
| Что видит | **весь** граф родителя | только то, что родитель **явно объявил** методами |
| Знание о родителе | генерируется внутри родителя, связь жёсткая | зависит лишь от интерфейса — можно подменить |
| Изоляция | слабая: «случайно» доступно всё | сильная: явный контракт |
| Код | компактнее | нужны provision-методы в родителе |
| Модульность | родитель и ребёнок компилируются вместе | ребёнок может жить в отдельном модуле, не видя реализацию родителя |

Практика: **внутри одного модуля — сабкомпоненты** (меньше писанины), **между Gradle-модулями —
зависимость компонентов**, потому что она не требует, чтобы фича видела граф приложения целиком.
Аргумент про изоляцию Dagger приводит и в документации: то, что не выставлено методом, недоступно
принципиально — а не «доступно, но так не принято». Универсального «предпочитайте вот это» в
документации нет: сабкомпоненты названы «самым простым способом связать компоненты», а зависимости —
альтернативой ради инкапсуляции.

Правила видимости, которые полезно назвать: ребёнок видит родителя и всех предков; родитель ребёнка
не видит; сиблинги не видят друг друга.

**Правила скоупов у зависимостей компонентов другие**, чем у сабкомпонентов, и это хороший вопрос на
глубину:

- **компонент без скоупа не может зависеть от скоупнутого** — `<Component> (unscoped) cannot depend
  on scoped components:`;
- **`@Singleton`-компонент не может зависеть ни от одного скоупнутого** — `@Singleton` считается
  самым длинным временем жизни, поэтому зависеть ему не от чего;
- **скоупнутый не-`@Singleton` компонент зависеть от скоупнутого может**, если скоупы разные и
  выстраиваются в иерархию, замыкающуюся на `@Singleton`. Повтор скоупа где-то по цепочке даёт
  `depends on scoped components in a non-hierarchical scope ordering:`.

Последний пункт шире, чем обычно учат: «скоупнутый компонент не может зависеть от скоупнутого» —
неверно, запрещены только неиерархические цепочки и два случая выше.

## 4.8. Скоупы Hilt: что физически держит компонент

Hilt — это готовая иерархия компонентов плюс код, создающий и отпускающий их в нужные моменты.
Полезно знать не только «сколько живёт», но и **кто держит ссылку**:

| Компонент | Скоуп | Ссылку держит | Умирает, когда |
| --- | --- | --- | --- |
| `SingletonComponent` | `@Singleton` | ваш `Application` (`@HiltAndroidApp`) | процесс завершён |
| `ActivityRetainedComponent` | `@ActivityRetainedScoped` | **`ViewModel`** в `ViewModelStore` активити | активити уходит окончательно (не поворот) |
| `ViewModelComponent` | `@ViewModelScoped` | конкретная `ViewModel` | `onCleared()` этой ViewModel |
| `ActivityComponent` | `@ActivityScoped` | сам экземпляр `Activity` | активити пересоздана или уничтожена |
| `FragmentComponent` | `@FragmentScoped` | экземпляр фрагмента | `onDestroy` фрагмента (создан в `onAttach`) |
| `ViewComponent` | `@ViewScoped` | экземпляр `View` | view уничтожена |
| `ViewWithFragmentComponent` | `@ViewScoped` | view внутри фрагмента | то же |
| `ServiceComponent` | `@ServiceScoped` | экземпляр сервиса | `onDestroy` сервиса |

Строка про `ActivityRetainedComponent` — самая интересная. В исходниках Hilt это буквально
`ActivityRetainedComponentViewModel extends ViewModel`, который держит компонент в поле и достаётся
через `ViewModelProvider(activity)`. То есть Hilt не изобретал механизм «переживает поворот», а
**переиспользовал `ViewModelStore`** (разобран в `10-android-sdk-deep.md`, раздел 3.2). Когда
ViewModel очищается, Hilt в её `onCleared()` рассылает `ActivityRetainedLifecycle.onCleared` — на
это событие можно подписаться.

Здесь же уместно повторить вывод из 4.3, потому что документация Hilt выносит его отдельным
предупреждением: «распространённое заблуждение — что все экземпляры фрагмента разделяют один объект,
скоупнутый `@FragmentScoped`. Это не так: **каждый экземпляр фрагмента получает новый экземпляр
компонента, а значит и новые экземпляры всех его скоупнутых биндингов**». Ровно та же логика, что и с
двумя `DaggerAppComponent`.

Два уточнения про то, у чего компонента **нет**:

- `@HiltWorker` — воркеры собираются из `SingletonComponent` через `HiltWorkerFactory`, а `Context` и
  `WorkerParameters` приходят assisted-инъекцией (3.9);
- `BroadcastReceiver` — единственный из поддерживаемых Android-классов, у которого нет своего
  компонента: он тоже инжектится прямо из `SingletonComponent`. `ContentProvider` не поддерживается
  вовсе, потому что его `onCreate` вызывается слишком рано, — для него используют entry point.

Мелочь для отладки: компоненты Hilt генерируются вложенными в `<Root>_HiltComponents`, причём
окончание `Component` в имени сокращается до `C` — `SingletonComponent` становится `SingletonC`.
Сделано это, чтобы длинные имена вложенных сабкомпонентов не пробивали лимит в 256 символов; знание
полезно, когда читаешь стектрейс или сгенерированный код.

## 4.9. Свой компонент в Hilt: `@DefineComponent`

То же, что в 4.6, но средствами Hilt — чтобы в компонент могли вносить биндинги разные модули
через `@InstallIn`:

```kotlin
@DefineComponent(parent = SingletonComponent::class)
@FeatureScope
interface CheckoutComponent

@DefineComponent.Builder
interface CheckoutComponentBuilder {
    fun orderId(@BindsInstance orderId: String): CheckoutComponentBuilder
    fun build(): CheckoutComponent
}

@EntryPoint
@InstallIn(CheckoutComponent::class)
interface CheckoutEntryPoint {
    fun cartManager(): CartManager
}
```

Дальше инжектите `CheckoutComponentBuilder`, создаёте компонент и достаёте из него зависимости
через `EntryPoints.get(component, CheckoutEntryPoint::class.java)`.

Ограничения, которые надо назвать, если предлагаете это решение:

- компонент обязан быть прямым или косвенным потомком `SingletonComponent`;
- **нельзя вставить свой компонент между стандартными** — например между `ActivityComponent` и
  `FragmentComponent`;
- у компонента ровно **один родитель**: иерархия не может быть «ромбом», и именно в это упираются,
  когда custom-компонентов становится много;
- методы на самом `@DefineComponent`-интерфейсе запрещены — доступ только через `@EntryPoint`
  (чтобы зависимости билдера не стали транзитивными для всех модулей компонента);
- держать и отпускать экземпляр — снова ваша задача.

Честный ответ на «нужен ли свой компонент» документация Hilt формулирует сама: сначала подумайте,
не достаточно ли передать пару объектов аргументами. Каждый компонент — это когнитивная нагрузка,
комбинаторика с `ViewWithFragmentComponent` и риск упереться в «ромб». Свой компонент оправдан,
когда у времени жизни есть чёткие границы **и** в него должны вносить вклад разные модули.

## 4.10. Утечка скоупа (вопрос 77)

**Правило:** зависимость с более коротким временем жизни нельзя держать в объекте с более
длинным. Все типовые утечки в DI — нарушения этого правила:

- `@Singleton`, которому инжектят `Activity`-контекст → Activity живёт вечно;
- `@Singleton`, держащий репозиторий с состоянием экрана → состояние не сбрасывается между
  входами на экран, и пользователь видит чужие данные;
- скоуп, привязанный к фиче, который никто не закрывает → память растёт при каждом входе.

Теперь понятно и почему это происходит механически: скоупнутый объект лежит в поле компонента
(4.2), а компонент жив, пока на него есть ссылка (4.3). Утечка скоупа — это всегда утечка
**компонента**, и искать надо того, кто его держит.

Hilt защищает от первого случая на компиляции: инжектить `ActivityContext` в `SingletonComponent`
он просто не даст. В рантайм-контейнере такой ошибки компилятор не увидит — ещё один аргумент в
сравнении из 7.1.

# 5. Hilt в тестах

`@TestInstallIn` заменяет продовый модуль тестовым на уровне всего теста:

```kotlin
@Module
@TestInstallIn(components = [SingletonComponent::class], replaces = [NetworkModule::class])
object FakeNetworkModule {
    @Provides fun provideApi(): Api = FakeApi()
}
```

Это чище, чем `@UninstallModules` на каждом тесте, и работает для всего набора. Для точечной
подмены в одном тесте есть `@BindValue`.

Полезная деталь про скорость тестов: Hilt по умолчанию **переиспользует один сгенерированный
компонент** между тестами, у которых нет `@BindValue`-полей и вложенных модулей, — это заметно
сокращает объём генерируемого кода. Отсюда требования, о которые спотыкаются: методы `@EntryPoint`
должны быть публичными и уникально названными, потому что общий компонент генерируется в отдельном
пакете. Отключается флагом `dagger.hilt.shareTestComponents=false`, но правильнее исправить
видимость и имена.

# 6. Цена Dagger на сборке

Главное, ради чего задают вопрос: **Dagger — это кодогенерация, а кодогенерация стоит
времени сборки**. Причём стоит не равномерно:

- на **изменении ABI** (поменяли сигнатуру, добавили зависимость в конструктор) пересобирается
  и перегенерируется много — это самый дорогой сценарий;
- на изменении **внутри тела метода** разница с любым другим подходом почти исчезает.

Второй нюанс — **KSP против KAPT**. KAPT генерирует Java-стабы для всего кода Kotlin, и это
основная его стоимость; KSP работает с Kotlin напрямую. Практический вывод, который важнее
любых процентов: **выигрыш появляется, только когда из модуля убран последний KAPT-процессор** —
один оставшийся заставляет генерировать стабы, и экономия исчезает. Поэтому миграция «наполовину»
почти ничего не даёт, и это стоит проговорить, если спросят про KSP (вопрос 80).

Отдельно: **Hilt не работает в KMP-модулях** — Dagger привязан к JVM-байткоду, и поддержки
Kotlin/Native нет. Стандартный обход: интерфейсы в общем коде, а биндинги Hilt — только в
Android-модуле (разбор — в `15-kmp-deep.md`, раздел 5).

Два требования свежих версий, на которые стоит посмотреть перед обновлением: Gradle-плагин Hilt с
2.58 требует **AGP 9**, а с 2.60 minSdk Hilt — **23**, и поддержка multidex из него убрана.

# 7. Альтернативы и сравнение (вопрос 76)

## 7.1. Три подхода

| | Compile-time кодогенерация (Dagger/Hilt) | Compile-time компиляторный плагин (Metro и подобные) | Runtime-контейнер (Koin) |
| --- | --- | --- | --- |
| Когда проверяется граф | при компиляции | при компиляции | **в рантайме** |
| Ошибка «нет зависимости» | не собирается | не собирается | падает при первом обращении |
| Цена сборки | высокая на ABI-изменениях | ниже: нет отдельного прохода генерации | почти нулевая |
| Цена старта | ~нулевая | ~нулевая | заметная: граф строится в рантайме |
| KMP | нет (Hilt) | да | да |
| Порог входа | высокий | средний | низкий |

## 7.2. Как отвечать

Сильный ответ строится не на «что лучше», а на том, **чем платят**:

> Компромисс здесь между тем, когда вы узнаёте об ошибке, и тем, сколько это стоит. Dagger
> ловит ошибку графа на компиляции — за это платится временем сборки, и на большом проекте это
> самая заметная статья. Koin переносит проверку в рантайм: сборка быстрая, но «забыл
> зарегистрировать зависимость» превращается из ошибки компиляции в падение, и ловить это
> должны тесты, а не компилятор. Компиляторные плагины пытаются взять и то и другое: проверка
> на компиляции без отдельного прохода кодогенерации.

Дальше стоит назвать, что изменилось за последнее время, — это показывает, что вы следите:

- **Компиляторные плагины стали рабочей опцией.** DI, реализованный как плагин к компилятору
  Kotlin (FIR/IR) вместо процессора аннотаций, не порождает отдельного прохода генерации
  исходников и лучше дружит с инкрементальной компиляцией. Крупные компании перевели на такой
  подход кодовые базы в тысячи модулей; сообщавшиеся выигрыши — **порядка 40–60 % на
  инкрементальных сборках, меняющих ABI, и 10–25 % на чистых сборках**, тогда как на изменениях,
  не затрагивающих ABI, разницы почти нет. Именно такое распределение — «выигрыш там, где
  раньше было дороже всего» — и стоит называть вместо одной усреднённой цифры.
- **Anvil задепрекейчен** его авторами в пользу такого подхода — это заметное событие, потому
  что Anvil много лет был стандартом для больших Dagger-проектов.
- **Koin ушёл от KSP к собственному плагину компилятора**, который умеет валидировать граф на
  этапе компиляции. То есть граница «compile-time против runtime» размывается: у Koin появилась
  часть проверок на компиляции, оставив резолв в рантайме.

## 7.3. Стоимость Koin на старте (follow-up к вопросу 76)

Follow-up спрашивает про граф в 500 биндингов. Правильная структура ответа:

1. **Что именно стоит.** Регистрация модулей (создание описаний биндингов) и последующий резолв
   при первом обращении. Регистрация линейна по числу биндингов и происходит на старте.
2. **Порядок величины.** Разница с compile-time решениями измеряется десятками миллисекунд —
   в бенчмарках инициализация рантайм-контейнера занимает десятки миллисекунд против сотых
   долей у сгенерированного кода. Для многих приложений это приемлемо, для приложения, борющегося
   за TTID, — нет.
3. **Как измерить.** Не спорить, а померить: трейс-секция вокруг `startKoin`, Macrobenchmark на
   холодный старт с `CompilationMode.None`/`Full`, сравнение с пустым модулем. Это ровно тот
   ответ, которого ждут: senior не оценивает на глаз, а ставит эксперимент.
4. **Как чинить, если дорого.** Ленивые модули (загружаются параллельно и не на критическом
   пути старта), дробление графа так, чтобы на старте регистрировалось только нужное для первого
   экрана, и перенос тяжёлых объектов в `factory`/`lazy` вместо `single`.

## 7.4. Ручной DI

Не забывайте назвать его как реальный вариант — это признак зрелости, а не наивности. Для
небольшого приложения или для общего KMP-модуля ручная сборка графа в одном классе-контейнере
работает, не требует зависимостей, ничего не стоит на сборке и полностью прозрачна. Ломается
она на масштабе: с ростом графа контейнер превращается в тысячу строк, а скоупы приходится
изобретать заново.

## 7.5. Как давать зависимости ViewModel (вопрос 75)

Проблема: ViewModel создаёт система, через `ViewModelProvider.Factory`, и по умолчанию она
умеет только пустой конструктор.

Варианты, от старого к современному:

1. **Своя фабрика** — руками реализовать `ViewModelProvider.Factory`. Работает всегда, но
   boilerplate на каждую ViewModel.
2. **Фабрика с мультибиндингом** — карта `Map<Class<out ViewModel>, Provider<ViewModel>>`,
   одна общая фабрика. Классический доDagger-Hilt подход (механика — в 3.7).
3. **`@HiltViewModel`** — Hilt делает всё сам: конструктор с `@Inject`, инъекция
   `SavedStateHandle` из коробки. Внутри это `ViewModelComponent` со скоупом
   `@ViewModelScoped` (4.8).
4. **`CreationExtras`** — современный механизм, позволяющий передать данные в фабрику при
   создании, не заводя отдельную фабрику на каждый случай. Поверх него работает
   `@HiltViewModel(assistedFactory = ...)` из 3.9: рантайм-аргумент экрана передаётся через
   `creationCallback`.

Про выбор между `SavedStateHandle` и assisted-аргументом: если значение — часть состояния
навигации (id открытой сущности), берите `SavedStateHandle`, потому что оно переживёт убийство
процесса. Assisted оправдан для того, что восстанавливать не нужно.

**Чего делать не надо:** передавать в конструктор ViewModel `Context`, `Activity` или что-либо
из UI. Причина — не «так принято», а время жизни: ViewModel переживает Activity, и такая
ссылка утекает (механика — в `09-jvm-memory-deep.md`, раздел 4).

# 8. Gradle: что действительно ускоряет сборку

## 8.1. Сначала измерить

Вопрос «как ускорить сборку» без измерения — ловушка. Правильный первый шаг:

- **Build scan** (`--scan`) — что заняло время, что не попало в кэш и почему;
- **Build Analyzer** в Android Studio — то же самое в IDE, плюс плагины-виновники;
- `--profile` для быстрой локальной картины.

Ключевое различие, которое надо провести в ответе: **что вы оптимизируете**. Чистая сборка,
инкрементальная сборка с изменением ABI, инкрементальная без изменения ABI и configuration
phase — это четыре разные задачи с разными решениями. «Ускорить сборку» без уточнения сценария
— неответ.

## 8.2. Кэши

- **Build cache** переиспользует результаты задач. Локальный включается почти всегда;
  **удалённый** (общий на команду и CI) — самая большая одиночная победа для команды, потому
  что после `git pull` большинство модулей берётся из кэша, а не собирается.
- **Configuration cache** кэширует результат configuration phase — то есть выполнение
  `build.gradle`. На проекте из сотен модулей эта фаза занимает секунды на **каждой** сборке,
  и её устранение ощущается сильнее всего. Важная деталь для точности: он **не включён по
  умолчанию**, это осознанно выбираемый режим, и его включение требует привести скрипты в
  совместимый вид (никакого обращения к `Project` во время выполнения задач).

## 8.3. Version catalogs и convention plugins (вопрос 79)

**Version catalog** (`libs.versions.toml`) — единое место для версий зависимостей. Решает
проблему «в двадцати модулях двадцать разных версий одной библиотеки» и даёт автодополнение.

**Convention plugins** — это способ не копировать одинаковые куски `build.gradle.kts` в каждый
модуль. Вместо копипасты пишется свой плагин в `buildSrc` или (лучше) в отдельном включённом
билде, и модуль выглядит так:

```kotlin
plugins {
    id("myapp.android.feature")     // внутри: android {}, compose, testing, общие зависимости
}

dependencies {
    implementation(projects.core.data)
}
```

Зачем это в мультимодуле, кроме красоты:

- **Единообразие принудительно.** Нельзя «случайно» собрать модуль с другим `compileSdk` или
  забыть подключить тестовые зависимости.
- **Изменение в одном месте.** Поднять версию Java во всех 200 модулях — правка одного файла.
- **Точка контроля.** В convention plugin удобно централизованно включать статический анализ,
  правила R8 и ограничения на зависимости.

Важная практическая деталь: **`buildSrc` инвалидирует всю сборку при любом своём изменении**.
Поэтому convention plugins сегодня выносят в отдельный включённый билд (`build-logic`), а не в
`buildSrc` — это заметная разница на большом проекте, и её упоминание выдаёт практический опыт.

## 8.4. Остальное, что реально помогает

- **Убрать KAPT полностью** — см. раздел 6: наполовину не считается.
- **Резать графы, а не только модули.** Плоский граф, где все зависят от всех, не даёт
  параллелизма. Полезно смотреть не только число модулей, но и высоту графа.
- **`implementation` вместо `api`** — сокращает транзитивную пересборку. Это же и архитектурная
  граница (см. `12-architecture-deep.md`, раздел 5.4).
- **`isMinifyEnabled` только в release.** R8 в debug-сборке — распространённая случайность,
  которая незаметно удваивает время локальной итерации.
- **Не включать всё подряд в CI.** Полный набор проверок на каждый пуш — самая частая причина
  двадцатиминутного пайплайна. Разделение на быстрый gate и полный ночной прогон дешевле.

# 9. Варианты сборки и поставка

**Build types** (`debug`/`release`) отвечают за то, **как** собрано: минификация, отладка,
подпись. **Product flavors** — за то, **что** собрано: окружение, брендирование, платная и
бесплатная версии. Их произведение даёт варианты (`freeDebug`, `paidRelease`), и число вариантов
растёт мультипликативно — это стоит держать в голове, потому что каждый вариант это время сборки
и время CI.

**App Bundle** — обязательный формат публикации: разработчик загружает `.aab`, а Play собирает
APK под конкретное устройство (плотность, ABI, язык). Прямое следствие: пользователь скачивает
меньше, но **вы больше не контролируете финальный APK** — поэтому тестировать надо то, что
Play реально соберёт (для этого есть `bundletool` и внутренние треки).

**Play App Signing:** ключ подписи приложения хранится у Google, у вас остаётся ключ загрузки.
Плюс — потеря ключа больше не фатальна; минус — вы делегируете подпись. Важно понимать, что
именно поэтому Play может пересобрать и переподписать ваш bundle.

# 10. R8

## 10.1. Что делает

R8 в одном проходе выполняет: **shrinking** (удаление недостижимого кода), **optimization**
(инлайн, упрощения, удаление проверок), **obfuscation** (переименование) и **desugaring**
(поддержка новых языковых конструкций на старых API). Про «R8 против ProGuard»: R8 — замена
ProGuard в тулчейне Android, он совместим с его форматом правил, но это другой движок.

## 10.2. Keep-правила и главная современная ошибка

Правило `-keep` говорит «этот код нужен, не трогай». Нужны они там, где R8 не может увидеть
использование статически: рефлексия, JNI, десериализация, классы, создаваемые по имени.

**Что изменилось и о чём стоит сказать:** современные библиотеки поставляют свои правила
вместе с артефактом (consumer rules). Поэтому лишние ручные правила из старых гайдов стали
**вредны** — широкий `-keep class androidx.**` или `-keep class * extends RoomDatabase` не
защищают ни от чего, а просто запрещают R8 оптимизировать большие куски кода. Правильная
позиция: начинать с нуля правил, добавлять только то, что доказано сломалось, и держать список
минимальным.

Что действительно требует правил: доступ по рефлексии, поля, существующие только ради
сериализации, и обобщённые сигнатуры для `suspend`-функций.

## 10.3. `mapping.txt`

Обфускация ломает стектрейсы. `mapping.txt` — соответствие исходных имён обфусцированным; он
**обязан** загружаться в систему крэш-репортинга при каждом релизе, иначе крэши нечитаемы.
Файл привязан к конкретной сборке: потеряли — стектрейсы этой версии восстановлению не подлежат.
Для ручной расшифровки есть `retrace`.

## 10.4. Связь с производительностью старта

R8 нужен не только ради размера: **Startup Profiles работают только при включённой минификации**,
потому что они управляют раскладкой классов по DEX-файлам, а раскладку делает R8. Это хорошая
связка для ответа, показывающая, что сборка и производительность — не изолированные темы
(подробнее про профили — в `09-jvm-memory-deep.md`, раздел 7).

# 11. CI/CD

Каркас пайплайна на PR, от быстрого к медленному, — важен именно порядок, потому что дешёвые
проверки должны отсекать раньше:

1. компиляция и статический анализ (lint, detekt) — минуты;
2. unit-тесты — минуты;
3. скриншот-тесты на JVM — минуты;
4. инструментальные тесты — десятки минут, поэтому обычно урезанный набор на PR и полный ночью.

Что отличает senior-ответ:

- **Пайплайн — это продукт с SLA.** Если он идёт 40 минут, разработчики начинают складывать
  изменения в один большой PR, и качество ревью падает. Время пайплайна — метрика, за которой
  надо следить так же, как за крэшами.
- **Флаки — блокер, а не неудобство.** Тест, падающий раз в десять запусков, обучает команду
  нажимать «перезапустить», и тогда пайплайн перестаёт что-либо гарантировать.
- **Релизные поезда** (регулярная дата вместо «когда будет готово») предсказуемее и снижают
  давление на впихивание фичи в последний момент.
- **Staged rollout обязателен**: раскатка процентами с наблюдением за крэшами и ANR, и
  заранее отрепетированный откат. Про Play Vitals и пороги — в `10-android-sdk-deep.md`.
- **Changelog и версионирование автоматизируются** — не ради красоты, а чтобы можно было
  однозначно связать крэш с коммитом.
