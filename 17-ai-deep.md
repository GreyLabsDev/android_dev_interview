# 1. Gemini Nano и AICore (вопрос 151)

## 1.1. Как это устроено

**AICore** — системный сервис Android, который держит на устройстве компактную модель
(**Gemini Nano**) и выдаёт к ней доступ приложениям. Ключевая архитектурная идея: модель
**не бандлится в приложение**.

Почему это правильно — и это ровно то, что проверяет вопрос:

- **Вес.** Модель занимает существенное место. Если бы каждое приложение носило свою копию,
  на устройстве с пятью такими приложениями это было бы неприемлемо. Одна общая модель
  используется всеми.
- **Обновления.** Модель обновляется системой, а не через релиз приложения. Вам не нужно
  выпускать новую версию, чтобы пользователь получил улучшенную модель.
- **Железо.** AICore умеет использовать ускорители конкретного устройства. Приложение об этом
  не думает.

Практическое следствие, которое стоит назвать: **приложение не может рассчитывать на наличие
модели**. Nano доступен на ограниченном круге устройств, причём существуют разные варианты
модели с разными возможностями. Значит, любая фича на Nano обязана иметь путь «модели нет».

## 1.2. Ограничения, о которых обычно не знают

Это хороший материал для follow-up, потому что он показывает, что вы читали не только анонс:

- **Инференс работает, только когда ваше приложение на переднем плане.** Фоновое использование
  блокируется — в том числе из foreground service. То есть «саммаризировать всё ночью в фоне»
  на Nano не построить.
- **Есть квоты на приложение.** И на частоту, и на суммарное потребление. При превышении вы
  получаете ошибку и должны отступить с backoff.
- **Устройства с разблокированным загрузчиком не поддерживаются**, эмулятор — тоже. Последнее
  практически неприятно: разрабатывать и тестировать можно только на реальном железе.

# 2. ML Kit GenAI (вопрос 152)

Высокоуровневые API поверх Nano: саммаризация, вычитка, переписывание, описание изображений,
распознавание речи и произвольный промпт. Важная деталь для честного ответа: **это не GA** —
API находятся в бете и альфе, часть из них не обновлялась заметное время. Говорить о них как о
production-ready не стоит.

## 2.1. Проверка доступности и догрузка

Обязательный паттерн, и его логику стоит уметь объяснить:

```kotlin
when (summarizer.checkFeatureStatus().await()) {
    FeatureStatus.AVAILABLE -> runSummary()

    // Модель есть в системе, но конкретный адаптер для этой фичи ещё не скачан
    FeatureStatus.DOWNLOADABLE -> summarizer.downloadFeature(object : DownloadCallback {
        override fun onDownloadStarted(bytesToDownload: Long) { showProgress() }
        override fun onDownloadCompleted() { runSummary() }
        override fun onDownloadFailed(e: GenAiException) { fallbackToCloud() }
    })

    FeatureStatus.DOWNLOADING -> waitAndRetry()
    FeatureStatus.UNAVAILABLE -> fallbackToCloud()   // это устройство модель не потянет
}
```

Что здесь важно:

- **Загружается не вся модель, а небольшой адаптер под конкретную задачу**, если базовая модель
  уже есть в системе. Это прямое следствие архитектуры из раздела 1.
- Если пропустить явную загрузку, она произойдёт при первом инференсе — но тогда пользователь
  увидит непонятную задержку вместо прогресса. Поэтому явный вызов лучше.
- `UNAVAILABLE` — не ошибка, а нормальная ветка. Проектировать фичу надо от неё.
- Объект нужно закрывать (`close()`): это ресурс.

## 2.2. Ограничения на вход

У задач есть жёсткие рамки, и на интервью полезно знать, что они вообще существуют: ограничение
на длину входа (порядка нескольких тысяч токенов для саммаризации), минимальная осмысленная
длина текста, ограниченный набор поддерживаемых языков. Последнее особенно важно для
русскоязычного продукта: если языка нет в списке, вся фича на Nano отпадает, и вопрос выбора
«on-device или облако» решается за вас.

# 3. On-device или облако (вопрос 153)

Сценарий из банка: продукт хочет саммаризацию переписки. Ответ должен быть про критерии, а не
про предпочтение.

| Критерий | On-device | Облако |
| --- | --- | --- |
| Приватность | данные не покидают устройство | нужно согласие и договор с провайдером |
| Работа офлайн | да | нет |
| Стоимость за вызов | нулевая | платите за каждый |
| Латентность | нет сетевой задержки, но зависит от железа | стабильнее на слабых устройствах |
| Доступность | **только на части устройств** | везде, где есть сеть |
| Качество и размер входа | компактная модель, ограниченный вход | модели крупнее, вход больше |

**Как отвечать на конкретный сценарий с перепиской:**

1. **Начать с приватности как с аргумента за on-device.** Личная переписка — как раз тот случай,
   где «данные не уходят с устройства» является продуктовым преимуществом, а не технической
   деталью. Это же снимает часть вопросов с юристами и с декларацией в Play.
2. **Сразу назвать блокер: покрытие устройств.** Фича, работающая у меньшинства пользователей, —
   это не фича. Значит, нужен гибридный вариант.
3. **Предложить гибрид как основное решение.** On-device там, где доступно; облако — фолбэк.
   Для этого существуют библиотеки с явными режимами предпочтения (сначала пробовать
   устройство, иначе облако). Важная тонкость, которую стоит знать: такой фолбэк обычно **не
   скачивает модель сам** — если её нет, он просто уходит в облако.
4. **Проговорить UX разницы.** Пользователь не должен видеть, что на его телефоне фича работает
   иначе. Но если для облачного варианта нужно согласие на отправку данных — оно обязано быть
   явным.
5. **Назвать деградацию.** Нет сети и нет модели — фича должна честно отсутствовать, а не
   висеть в бесконечной загрузке.

Ответ уровня senior отличается тем, что в нём есть **решение о покрытии**: «эта фича будет
доступна примерно такой-то доле аудитории, и вот что мы показываем остальным».

# 4. Собственные модели: LiteRT

Если нужна своя модель, а не готовая задача, — это **LiteRT** (бывший TensorFlow Lite) в составе
Google AI Edge. Что достаточно знать:

- Работает на CPU везде, на GPU почти везде, на NPU — на Android и с ограниченным кругом
  вендоров. Есть автоматический откат на CPU для частей графа, которые ускоритель не тянет.
- Главный практический вопрос — **не скорость инференса, а старт**. Компиляция модели под
  ускоритель может происходить на устройстве при первой инициализации, и это заметная задержка;
  для крупных моделей рекомендуется компиляция заранее и кэширование.
- **Вес модели — это вес приложения.** В отличие от Nano, свою модель вы бандлите или
  докачиваете. Для докачки существуют механизмы доставки, чтобы не раздувать APK.
- Ограничение по бюджету: инференс имеет смысл делать на переднем плане и с явным индикатором;
  тяжёлая модель на слабом устройстве съест батарею и вызовет троттлинг.

# 5. AI-ассистенты в разработке (вопрос 154)

Практически самый важный пункт блока: это уже стандартный вопрос, и на нём легко потерять
очки. Плохие ответы — оба крайних: «не пользуюсь» (читается как «не слежу за инструментами»)
и «пользуюсь везде» (читается как «не отвечаю за код, который коммичу»).

## 5.1. Структура сильного ответа

**Где применяю и почему это выгодно:**

- рутинный код с понятной структурой: маппинг DTO в доменные модели, boilerplate тестов,
  парсинг, обвязка;
- разбор незнакомого кода и библиотек — быстро получить карту, а потом проверить по исходникам;
- тесты, особенно генерация краевых случаев, которые легко забыть перечислить руками;
- ускорение рутины вокруг кода: коммиты, описания PR, черновики документации;
- обсуждение вариантов решения как «резиновая уточка», которая ещё и возражает.

**Где не доверяю и почему:**

- **Конкурентность и корутины.** Код выглядит правдоподобно и содержит гонки, которые не
  видны на ревью и не воспроизводятся в тестах.
- **Всё, что связано с безопасностью и деньгами.** Цена ошибки несимметрична.
- **Специфика версий платформы.** Модель уверенно предлагает API, устаревшие или не
  существующие в вашей `minSdk`; это самая частая категория ошибок в Android-контексте.
- **Производительность.** Предлагается «оптимизация», которая на деле ничего не меняет или
  ухудшает; здесь нужны замеры, а не правдоподобие.
- **Архитектурные решения.** Модель охотно соглашается с вами, а архитектура требует
  возражений и знания контекста проекта.

**Как ревьюю сгенерированное — это ключевая часть ответа:**

- Отношусь к нему как к коду от незнакомого разработчика: не доверяю по умолчанию, читаю целиком.
- Не принимаю то, чего не понимаю. Если не могу объяснить строку на ревью — она не идёт в PR.
- Обязательно проверяю, что API существует и доступен на нашей `minSdk`.
- Тесты пишу или проверяю сам: сгенерированный тест, написанный под сгенерированный код,
  проверяет согласованность двух ошибок, а не корректность.
- Ответственность за код остаётся моей. «Так предложил ассистент» — не объяснение на разборе
  инцидента.

## 5.2. Что добавляет ответу вес

Если есть, приведите **конкретный случай**, когда ассистент ошибся, и как вы это поймали.
Это единственная часть ответа, которую невозможно сымитировать, и она сразу показывает,
что вы действительно работаете с инструментом, а не рассуждаете о нём.

Второй сильный ход — сказать про **командный аспект**: договорённости о том, что сгенерированный
код проходит обычное ревью, что в PR не должно быть кода, который автор не может объяснить, и
что чувствительный код (ключи, персональные данные) не отправляется во внешние сервисы без
проверки политики компании.
