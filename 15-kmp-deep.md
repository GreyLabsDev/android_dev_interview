# Kotlin Multiplatform: теория и ответы

Закрывает блок 11 чеклиста, в банке вопросов — блок 10 (вопросы 136–142).

Отдельная оговорка про этот блок. KMP почти никогда не бывает решающим на интервью на Android-позицию,
если в вакансии он прямо не заявлен. Но вопрос «что вы думаете про KMP» задают часто — как проверку
кругозора и способности оценить технологию, а не как проверку опыта. Поэтому цель этого материала —
не научить писать KMP-код, а дать возможность **осмысленно рассуждать**: что шарится, чем платят,
как внедрять и когда отказаться. Ответ «не работал, но вот как я бы это оценивал» здесь абсолютно
нормален и часто сильнее, чем поверхностный пересказ документации.

---

# 1. Что это такое и чем не является

KMP — это способ компилировать **общий Kotlin-код** под несколько платформ: JVM/Android, iOS
(через Kotlin/Native), десктоп, веб (через Wasm/JS), сервер. Общий код лежит в `commonMain`,
платформенный — в `androidMain`, `iosMain` и так далее.

Ключевое отличие от кроссплатформенных фреймворков, и это прямой ответ на вопрос 140:

| | KMP | Flutter / React Native |
| --- | --- | --- |
| Что шарится | выбираете вы: от одного модуля до всего | как правило, всё приложение целиком |
| UI | по умолчанию **нативный** на каждой платформе (Compose Multiplatform — опция) | свой движок рендеринга (Flutter) или мост к нативным вью (RN) |
| Рантайм | код компилируется в нативный бинарник, своего рантайма нет | свой рантайм/движок в приложении |
| Интеграция в существующее приложение | естественная: обычная библиотека | возможна, но травматична |
| Доступ к платформенным API | прямой, без моста | через плагины/мосты |

Главное следствие, которое стоит произнести: **KMP — это не «написать приложение один раз»**.
Это способ не писать одну и ту же бизнес-логику дважды, сохранив нативный UI и нативные
возможности. Кандидат, который описывает KMP как замену Flutter, показывает, что не разбирался.

---

# 2. Что шарить, а что нет (вопрос 136)

Практическая иерархия, от бесспорного к спорному:

**Шарить почти всегда стоит:**

- **Модели данных и сериализация.** Один контракт с бэкендом вместо двух. Это же убирает целый
  класс багов «на Android поле опциональное, на iOS обязательное».
- **Сетевой слой.** Один клиент, одни ретраи, одна обработка ошибок и токенов.
- **Бизнес-логика и валидация.** Правила расчёта скидки, лимиты, машина состояний заказа.
  Это то место, где расхождение платформ стоит дороже всего: баг воспроизводится только на
  одной платформе, и его чинят дважды.
- **Работа с локальной БД** и кэширование.

**Шарить спорно:**

- **Презентационный слой** (ViewModel/state holder). Технически возможно и даёт много, но
  привязывает iOS-команду к чужой модели состояния и усложняет использование нативных
  UI-паттернов.

**Шарить обычно не стоит:**

- **UI**, если у продукта важен нативный внешний вид и поведение.
- **Всё, что глубоко платформенное:** виджеты, системные интеграции, работа с уведомлениями,
  специфичные для платформы возможности.

Формулировка, по которой видно опыт: шарить надо то, где **расхождение реализаций является
багом**, а не то, где просто похожий код. Внешний вид кнопки на двух платформах может и должен
отличаться. Формула расчёта цены — не может.

# 3. `expect`/`actual` и альтернатива (вопрос 137)

`expect`/`actual` — способ объявить в общем коде то, что реализуется по-разному на платформах:

```kotlin
// commonMain
expect class PlatformUuid() {
    fun generate(): String
}

// androidMain
actual class PlatformUuid actual constructor() {
    actual fun generate(): String = java.util.UUID.randomUUID().toString()
}
```

Что важно знать помимо синтаксиса:

- Механизм жёсткий: сигнатуры обязаны совпадать точно, и компилятор проверяет наличие
  реализации для **каждого** таргета. Забыли реализацию для одного таргета — не соберётся.
- Он плохо расширяется: добавить реализацию «снаружи» модуля нельзя, всё должно быть в одном
  модуле, разложенном по source set'ам.

**Альтернатива, которую стоит назвать, — обычные интерфейсы плюс DI.** В `commonMain`
объявляется интерфейс, платформенные реализации инжектируются:

```kotlin
// commonMain
interface UuidGenerator {
    fun generate(): String
}
```

Она почти всегда лучше для прикладного кода: тестируется подстановкой фейка (в отличие от
`actual`, который не подменишь), не требует раскладки по source set'ам и позволяет иметь
несколько реализаций. `expect`/`actual` разумно оставить для низкоуровневых вещей и для случаев,
когда нужен именно тип, а не объект (например, `expect` для платформенного типа даты).

Умение сказать «`expect`/`actual` — не единственный и часто не лучший способ» — это ровно то,
что отличает человека, который писал KMP, от человека, который прочитал введение.

# 4. Интероп со Swift и главная боль

Kotlin-код компилируется в фреймворк, который Swift видит через Objective-C-совместимый
интерфейс. Отсюда все ограничения, и о них стоит знать, потому что именно они определяют, как
iOS-команда будет относиться к проекту:

- **Дженерики теряются или упрощаются** при проходе через Objective-C — в Swift многое приходит
  как `Any`.
- **Sealed-иерархии** не превращаются в Swift enum, поэтому исчерпывающий `switch` на стороне
  Swift не работает: нужен каскад проверок типа.
- **`suspend`-функции** видны в Swift как функции с колбэком (или как async/await в современных
  версиях), а `Flow` требует обёртки, чтобы его удобно было потреблять.
- **Имена конфликтуют:** классы получают префиксы, а перегрузки могут схлопываться.

Практический вывод, который стоит произнести: **публичный API общего модуля надо проектировать
под Swift**, а не «как удобно в Kotlin». Плоские типы, минимум дженериков, явные обёртки для
асинхронности. Общий модуль с богатым Kotlin-API, неудобным из Swift, — самая частая причина,
по которой iOS-команда начинает сопротивляться.

# 5. Стек (вопрос 142)

Типовой набор для общего слоя данных:

| Задача | Библиотека |
| --- | --- |
| HTTP-клиент | Ktor Client |
| Сериализация | `kotlinx.serialization` |
| Асинхронность | `kotlinx.coroutines` |
| Локальная БД | SQLDelight или Room (Room умеет KMP) |
| Настройки | DataStore (умеет KMP) или `multiplatform-settings` |
| DI | Koin или один из compile-time вариантов; **Hilt не работает** (вопрос 141) |
| Навигация в шаренном UI | Decompose или встроенная навигация Compose Multiplatform |
| Дата и время | `kotlinx-datetime` |

**Почему Hilt не работает в `commonMain` (вопрос 141):** Hilt построен на Dagger, а Dagger —
это процессор аннотаций поверх JVM-байткода, генерирующий Java-код. У него нет и не планируется
поддержки Kotlin/Native. Варианты для KMP: Koin (рантайм-резолв, работает везде), compile-time
решения на компиляторных плагинах Kotlin, или ручной DI — который в KMP встречается чаще, чем
принято думать, потому что общий модуль обычно имеет небольшой граф и его сборка руками
абсолютно посильна.

Типовой data-слой выглядит так: `Ktor` тянет и десериализует через `kotlinx.serialization`,
результат пишется в SQLDelight/Room, наружу отдаётся `Flow` из базы — то есть ровно тот
offline-first, что разобран в `14-data-network-deep.md`, только код один на две платформы.

**Отдельный факт, который сильно обновляет ответ:** Google официально называет KMP
поддерживаемым способом шарить бизнес-логику, и значительная часть Jetpack уже мультиплатформенная —
Room, DataStore, SQLite, Paging, Lifecycle и ViewModel, SavedState, Annotation, Collection, а
также обе навигационные библиотеки. То есть аргумент «в KMP нет привычных библиотек» устарел:
сегодня общий слой данных собирается почти из тех же кирпичей, что и Android-приложение.
Полезная деталь для точности: у Jetpack есть уровни поддержки платформ — Android, JVM и iOS
покрыты полноценно, остальные таргеты тестируются слабее, а у Room, например, нет поддержки веба.

# 6. Compose Multiplatform: отдельное решение

Важно не путать два решения, и на интервью это различение само по себе ценно:

1. **Взять KMP** — шарить логику, оставить нативный UI. Обратимо, малорисково.
2. **Взять Compose Multiplatform** — шарить ещё и UI. Существенно более серьёзное решение.

Второе имеет смысл, когда UI действительно одинаков (внутренние и B2B-приложения, приложения с
сильным собственным брендированием, где нативные гайдлайны и так не соблюдаются) и когда команда
готова к тому, что часть платформенных мелочей придётся доделывать руками.

Статус на середину 2026 года, который стоит знать для вопроса 138: Android, iOS и десктоп у
Compose Multiplatform стабильны — **iOS получил статус стабильного весной 2025 года**, — а
**веб (Wasm) до сих пор в бете**, и это важная деталь, потому что про веб часто спрашивают как
про решённый вопрос.

Против шаренного UI стоит назвать конкретику, а не «неродной вид»:

- **Вес приложения на iOS.** Здесь стоит быть точным, потому что цифра часто цитируется
  неверно. Официально заявлялось про **порядка 9 МБ** прироста по сравнению с эквивалентным
  нативным приложением, но независимые замеры дают заметно больше — реалистично планировать
  **пятнадцать-тридцать мегабайт**, потому что в бинарник едут графический движок, рантайм
  Kotlin/Native и рантайм Compose. Если у продукта есть жёсткий бюджет размера, это может
  оказаться решающим.
- Поведенческие мелочи (скролл, жесты возврата, работа клавиатуры, доступность), которые на
  iOS ожидаются именно нативными и по которым пользователи чувствуют разницу.
- Интеграция со SwiftUI/UIKit возможна, но это дополнительный слой, который надо поддерживать.
- Нанимать iOS-разработчиков в проект с Kotlin-UI сложнее.

# 7. Как де-рискнуть внедрение (вопрос 139)

Сценарий: есть нативный Android и нативный iOS, команда хочет KMP. Ответ должен быть про процесс,
а не про технологию.

**Шаг 1. Начать с одного модуля, не с фичи целиком.** Лучший кандидат — что-то с чистой логикой,
без UI и без платформенных зависимостей: валидация, форматирование, расчёт, машина состояний.
Его можно подключить как обычную зависимость и в любой момент выбросить.

**Шаг 2. Выбрать не критичную для бизнеса область.** Первый модуль должен доказать схему сборки,
поставки и отладки, а не героически спасать релиз.

**Шаг 3. Отладить именно поставку.** Самое недооценённое: как iOS получает артефакт (собирает из
исходников или тянет готовый фреймворк/пакет), как это работает в их CI, как отлаживать
Kotlin-код из Xcode, кто чинит сборку, когда она красная. Технические проблемы KMP решаются;
организационные — вот эти — губят внедрения.

**Шаг 4. Договориться о владении заранее.** Кто пишет общий код, кто ревьюит, к кому идти
iOS-разработчику, если общий модуль ведёт себя не так. Без явного ответа общий модуль становится
ничьим.

**Шаг 5. Задать критерий отката.** Например: «если через квартал iOS-команда тратит на общий
модуль больше времени, чем экономит, — сворачиваем и переписываем обратно». Наличие
сформулированного условия отката — сильный senior-сигнал.

**Follow-up «iOS-команда через два месяца говорит, что Kotlin им мешает».** Плохой ответ —
убеждать их, что они не правы. Хороший:

1. Выяснить, что конкретно мешает. Обычно это одна из трёх вещей: неудобный из Swift API,
   боль со сборкой и отладкой, ощущение потери контроля. Первые две — технические и решаются
   (упростить API, спрятать асинхронность за удобными обёртками, наладить поставку бинарником).
2. Признать, что третья причина — не техническая и переубеждением не лечится. Если команда не
   хочет, общий код будет деградировать независимо от его качества.
3. Принять решение по критерию из шага 5, а не по спору. И зафиксировать, что откат — это
   нормальный исход эксперимента, а не чьё-то поражение.

# 8. Когда KMP не нужен

Полезно иметь готовый список — вопрос «когда бы вы отказались» задают почти всегда:

- **Приложение только под Android.** Тогда KMP — чистые накладные расходы.
- **Логики мало, а UI много.** Если приложение — это в основном экраны над CRUD, шарить почти
  нечего, а сложность добавится.
- **Команды работают независимо и по разным roadmap.** Общий код требует синхронизации; если её
  нет организационно, он превратится в узкое место.
- **Жёсткие требования к размеру приложения** на iOS.
- **Нет ни одного человека, готового разбираться в Kotlin/Native.** Когда сборка сломается —
  а она сломается — нужен кто-то, кто это чинит.
